01 / FOUNDATIONS

Zero → Hero: LangChain, LangGraph & LangSmith

A complete path from first LLM call to a production banking AI platform — agents, RAG, MCP tool servers, multi-agent orchestration, and everything needed to run it safely at scale.

🧒 EXPLAIN LIKE YOU'RE IN CLASS 7

Think about learning to cook. First you learn simple things — how to hold a knife, how to turn on the stove. Then you learn to follow a recipe with steps in order. Later, you learn to taste your food and fix it if something's missing before you serve it. This whole page is like that, but for building a helpful AI robot for a bank: we start with the easiest tools, and slowly build up to a team of robots that can safely answer questions about people's money.

Why these three tools, together

LangChain gives you the building blocks — model wrappers, prompt templates, retrievers, output parsers — glued together with a composition syntax called LCEL. LangGraph sits on top and gives you control flow: state machines with branches, loops, retries and human checkpoints, which is what a real agent needs instead of a single straight-line chain. LangSmith is the operational layer — it traces every run, lets you build evaluation datasets, and watches quality and cost once you're live.

Think of it as backend engineering for language models: LangChain is your libraries, LangGraph is your orchestrator/state machine, and LangSmith is your APM and test suite. We'll build every example against a single running scenario — a retail and commercial banking assistant — so the concepts stay grounded instead of abstract.

The running scenario

SCENARIO

A regional bank is building an internal + customer-facing AI layer: a customer service assistant, a loan eligibility advisor, a fraud-review copilot for analysts, and a policy/KYC question-answering tool for compliance staff. It has to connect to core banking APIs, internal PDFs (credit policy, KYC manuals), and must be auditable, cost-controlled, and safe to put in front of real customers and real money.

The roadmap

LangChain fundamentals

Models, prompt templates, output parsers, LCEL chains, memory, and tool/function calling — the vocabulary everything else is built from.

LangGraph fundamentals

State graphs, nodes and edges, conditional routing, cycles, checkpointing/persistence, human-in-the-loop interrupts, and streaming.

LangSmith

Tracing every call, building evaluation datasets, running automated + LLM-as-judge evals, and monitoring production quality.

Agent architectures

ReAct, tool-calling agents and plan-and-execute agents — built as a Banking Loan Advisor.

Chunking, embeddings, vector stores, hybrid retrieval, reranking and citation-grounded answers over KYC and credit policy PDFs.

MCP tool servers

Exposing core banking systems (accounts, transactions, credit bureau) as a standardized Model Context Protocol server any agent can call.

Multi-agent systems

A supervisor agent routing between specialist agents — fraud, loans, support — each with its own tools and guardrails.

Production hardening

Deployment, CI/CD, guardrails, observability, cost control, security and LLM routing — the difference between a demo and a system you can trust with money.

What "hero" looks like

Correct

Grounded in real data, evaluated against a golden dataset, with measured hallucination and citation-accuracy rates.

Governed

Every output passes through guardrails: PII redaction, policy checks, and human approval on high-risk actions like fund transfers.

Observable

Every trace, token, and dollar is visible — you can answer "why did it say that" and "what did it cost" for any request.

02 / FOUNDATIONS

LangChain fundamentals

Models, prompts, output parsers, and LCEL — the composition syntax that turns individual pieces into a chain.

🧒 EXPLAIN LIKE YOU'RE IN CLASS 7

LangChain is like a box of LEGO blocks made for talking to AI. There's a block for asking a question, a block for the AI's answer, a block for remembering what you said earlier, and a block for using tools like a calculator. You snap these blocks together with a simple connector (the | symbol you'll see below) to build something bigger — just like joining LEGO pieces to build a house.

Chat models

Everything starts with a model wrapper. LangChain normalizes chat models from different providers behind one interface, so swapping Anthropic for OpenAI is a one-line change.

python · model.py
from langchain_anthropic import ChatAnthropic

llm = ChatAnthropic(
    model="claude-sonnet-4-6",
    temperature=0,          # deterministic — important for financial answers
    max_tokens=1024,
)

response = llm.invoke("Explain a fixed deposit in one sentence.")
print(response.content)

temperature=0 matters more in banking than in most domains: you want the same question to produce the same eligibility answer every time.

Prompt templates

Never format prompts with raw f-strings in production — templates keep variables typed, reusable, and versionable in LangSmith's Prompt Hub.

python · prompts.py
from langchain_core.prompts import ChatPromptTemplate

loan_prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a loan eligibility assistant for {bank_name}. "
               "Only use the policy facts provided. Never invent interest rates."),
    ("human", "Customer profile: {profile}\n\nPolicy excerpt:\n{policy}\n\n"
              "Question: {question}"),
])

chain = loan_prompt | llm
result = chain.invoke({
    "bank_name": "Meridian Bank",
    "profile": "Salaried, monthly income ₹85,000, credit score 742",
    "policy": "Personal loans require credit score >= 700 and income >= ₹25,000/mo.",
    "question": "Is this customer eligible for a personal loan?",
})

LCEL — the pipe operator

LangChain Expression Language (LCEL) lets you compose runnables with |. Every piece — prompt, model, parser, retriever — implements the same Runnable interface, so it composes like Unix pipes.

python · lcel_chain.py
from langchain_core.output_parsers import JsonOutputParser
from pydantic import BaseModel, Field

class EligibilityResult(BaseModel):
    eligible: bool = Field(description="Whether the customer qualifies")
    reason: str = Field(description="One-sentence justification citing the policy")

parser = JsonOutputParser(pydantic_object=EligibilityResult)

chain = loan_prompt | llm | parser

# Same object, but now .invoke / .batch / .stream all work for free
result = chain.invoke({...})
batch_results = chain.batch([{...}, {...}, {...}])   # concurrent, built in
for chunk in chain.stream({...}):                     # token-level streaming
    print(chunk, end="")
WHY IT MATTERS

LCEL gives you .batch(), .stream(), async variants, retries, and fallbacks on every chain automatically — you don't hand-roll concurrency or streaming logic per endpoint.

Structured output

For anything that flows into another system — like an eligibility decision hitting a core banking API — skip free-text parsing and force structured output directly against the model.

python · structured_output.py
structured_llm = llm.with_structured_output(EligibilityResult)
result: EligibilityResult = structured_llm.invoke(loan_prompt.format(...))
print(result.eligible, result.reason)

Tools and function calling

Tools are typed Python functions the model can choose to call. This is the primitive every agent in this course is built from.

python · tools.py
from langchain_core.tools import tool

@tool
def get_account_balance(account_id: str) -> dict:
    """Fetch the current balance and currency for a bank account."""
    return core_banking_api.get_balance(account_id)

@tool
def check_credit_score(customer_id: str) -> int:
    """Look up a customer's latest bureau credit score."""
    return bureau_api.get_score(customer_id)

llm_with_tools = llm.bind_tools([get_account_balance, check_credit_score])
ai_msg = llm_with_tools.invoke("What's the credit score for customer C-4021?")
print(ai_msg.tool_calls)  # [{'name': 'check_credit_score', 'args': {'customer_id': 'C-4021'}, ...}]

Memory

Modern LangChain manages conversation memory as explicit message state rather than a hidden object — this is also the bridge into LangGraph, which persists that state for you.

03 / FOUNDATIONS

LangGraph fundamentals

LangChain gives you chains — straight lines. Real agents need branches, loops, and memory across turns. That's what LangGraph adds: a state machine for LLM applications.

🧒 EXPLAIN LIKE YOU'RE IN CLASS 7

LangGraph is like a board game with a map instead of one straight path. In a board game, depending on what happens, you might move forward, go back a step, or take a shortcut. LangGraph lets the AI decide "what should I do next?" based on what just happened — check something again, ask a question, or stop — instead of always doing the exact same steps in the exact same order every time.

State, nodes and edges

A LangGraph app is a graph over a shared state object. Each node is a function that reads state and returns updates to it; edges decide which node runs next.

python · basic_graph.py
from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages

class SupportState(TypedDict):
    messages: Annotated[list, add_messages]   # auto-appends instead of overwriting
    customer_id: str
    escalated: bool

def classify_intent(state: SupportState) -> dict:
    last = state["messages"][-1].content
    escalate = "fraud" in last.lower() or "dispute" in last.lower()
    return {"escalated": escalate}

def answer_faq(state: SupportState) -> dict:
    reply = llm.invoke(state["messages"])
    return {"messages": [reply]}

def escalate_to_human(state: SupportState) -> dict:
    return {"messages": [AIMessage(content="Connecting you to a fraud specialist now.")]}

graph = StateGraph(SupportState)
graph.add_node("classify", classify_intent)
graph.add_node("answer", answer_faq)
graph.add_node("escalate", escalate_to_human)

graph.add_edge(START, "classify")
graph.add_conditional_edges(
    "classify",
    lambda s: "escalate" if s["escalated"] else "answer",
    {"escalate": "escalate", "answer": "answer"},
)
graph.add_edge("answer", END)
graph.add_edge("escalate", END)

app = graph.compile()
result = app.invoke({"messages": [HumanMessage("I think there's a fraudulent charge on my card")], "customer_id": "C-4021"})

Cycles: the loop that makes agents work

A tool-calling agent is really just a loop: call the model, if it wants a tool run the tool, feed the result back, repeat until it answers. LangGraph expresses this as a cycle instead of special-casing it.

python · react_loop.py
from langgraph.prebuilt import ToolNode

def call_model(state):
    return {"messages": [llm_with_tools.invoke(state["messages"])]}

def should_continue(state):
    last = state["messages"][-1]
    return "tools" if last.tool_calls else END

graph = StateGraph(SupportState)
graph.add_node("agent", call_model)
graph.add_node("tools", ToolNode([get_account_balance, check_credit_score]))
graph.add_edge(START, "agent")
graph.add_conditional_edges("agent", should_continue, {"tools": "tools", END: END})
graph.add_edge("tools", "agent")   # ← the cycle: tool result goes back to the model
app = graph.compile()

Checkpointing & persistence

Checkpointers snapshot state after every node, so a conversation — or a stalled loan application — survives process restarts and can resume exactly where it left off.

python · checkpointing.py
from langgraph.checkpoint.postgres import PostgresSaver

checkpointer = PostgresSaver.from_conn_string(POSTGRES_URL)
app = graph.compile(checkpointer=checkpointer)

config = {"configurable": {"thread_id": "loan-application-88213"}}
app.invoke({"messages": [HumanMessage("I'd like to apply for a car loan")]}, config)
# ...customer closes the app, comes back next day...
app.invoke({"messages": [HumanMessage("continuing my application from yesterday")]}, config)

Human-in-the-loop

interrupt() pauses the graph before a sensitive step — like actually moving money — and waits for a human to approve, edit, or reject before continuing.

python · human_in_the_loop.py
from langgraph.types import interrupt, Command

def initiate_transfer(state):
    decision = interrupt({
        "action": "wire_transfer",
        "amount": state["amount"],
        "to_account": state["to_account"],
    })
    if decision["approved"]:
        return {"status": core_banking_api.execute_transfer(state)}
    return {"status": "cancelled_by_reviewer"}

# Analyst-side, after reviewing the paused graph in a queue:
app.invoke(Command(resume={"approved": True}), config)

Streaming

LangGraph streams at three granularities — full state updates, individual node outputs, or raw LLM tokens — so a UI can show "thinking" progress rather than a blank screen during a multi-step agent run.

python · streaming.py
for event in app.stream({"messages": [...]}, config, stream_mode="updates"):
    print(event)   # {'agent': {...}} then {'tools': {...}} as each node completes

04 / FOUNDATIONS

LangSmith: trace, evaluate, monitor

You can't fix what you can't see. LangSmith is the observability and evaluation layer that turns "it seemed to work" into measured, versioned confidence.

🧒 EXPLAIN LIKE YOU'RE IN CLASS 7

LangSmith is like a CCTV camera plus a report card for your AI robot. The camera records everything the robot said and did, so if something goes wrong, you can rewind and watch exactly what happened and why. The report card gives the robot marks on practice tests, so you know if it's actually getting better or worse before you let it talk to real customers.

Tracing — turn it on first

Tracing needs zero code changes to your chains — it's environment variables. Every prompt, tool call, token count, latency and dollar cost is captured automatically.

bash · .env
export LANGCHAIN_TRACING_V2=true
export LANGCHAIN_API_KEY="ls__..."
export LANGCHAIN_PROJECT="meridian-bank-prod"

Every run becomes a trace tree: agent → tool calls → sub-chains, each with input/output, latency, and token usage — essential when a customer disputes what the loan bot told them.

Datasets and evaluation

Build a "golden set" of representative banking questions with expected answers, then run it against every prompt or model change before it ships.

Running evaluations

Combine deterministic checks (does the JSON schema match?) with an LLM-as-judge grader for qualities like "does the answer cite the policy correctly?"

python · run_eval.py
from langsmith.evaluation import evaluate

def correctness(run, example):
    predicted = run.outputs["eligible"]
    expected = example.outputs["eligible"]
    return {"key": "eligibility_correct", "score": int(predicted == expected)}

def no_fabricated_rate(run, example):
    # LLM-as-judge: did the model invent a number not present in the policy excerpt?
    verdict = judge_llm.invoke(f"Policy: {example.inputs['policy']}\nAnswer: {run.outputs}\n"
                                "Does the answer cite ONLY figures present in the policy? yes/no")
    return {"key": "grounded", "score": 1 if "yes" in verdict.content.lower() else 0}

results = evaluate(
    lambda inputs: loan_chain.invoke(inputs),
    data="loan-eligibility-golden-set",
    evaluators=[correctness, no_fabricated_rate],
    experiment_prefix="loan-agent-v3",
)
PRACTICE

Run this evaluation in CI on every prompt or model change (see Section 10). A prompt tweak that improves one test case can silently break another — the golden set is your regression suite for language, not just code.

Production monitoring

  • Online evaluators — sample a percentage of live traffic and score it automatically (toxicity, groundedness, refusal rate).
  • Feedback — attach thumbs-up/down or analyst overrides directly to a trace to build a review queue of low-confidence runs.
  • Dashboards — track P50/P95 latency, cost per conversation, and error rate by agent, model, and prompt version.
  • Alerts — trigger on regressions: e.g. groundedness score dropping below 0.9 for the RAG assistant.

Prompt versioning

Push prompts to the LangSmith Prompt Hub instead of hardcoding them, so a prompt change is a reviewable diff and a rollback is one click, not a redeploy.

05 / AGENTS & ADVANCED PATTERNS

Agent architectures

Three shapes cover almost every real agent: ReAct, direct tool-calling, and plan-and-execute. We'll build a Banking Loan Advisor with each.

🧒 EXPLAIN LIKE YOU'RE IN CLASS 7

There are different kinds of helpers. One kind thinks out loud step by step before answering — like showing your working for a maths problem. Another kind just knows the answer instantly and says it right away — like answering "what is 2+2" without needing to think. A third kind makes a full plan first, like writing a to-do list before starting your homework, and then ticks off each task one by one.

ReAct — reason, act, observe, repeat

The model narrates a thought, picks a tool, observes the result, and loops until it has enough information to answer. It's the most general pattern and the easiest to debug because the reasoning is explicit.

python · react_loan_advisor.py
from langgraph.prebuilt import create_react_agent

tools = [check_credit_score, get_account_balance, calculate_emi, fetch_loan_policy]

loan_advisor = create_react_agent(
    model=llm,
    tools=tools,
    prompt=("You are Meridian Bank's loan eligibility advisor. Always check the "
            "customer's credit score and current policy before giving a verdict. "
            "Never state an interest rate you have not retrieved from a tool."),
)

result = loan_advisor.invoke({
    "messages": [("user", "Customer C-4021 wants a ₹12,00,000 car loan over 5 years — eligible?")]
})

Under the hood this expands into the exact agent/tools cycle you built by hand in Section 3 — create_react_agent is a prebuilt shortcut for that same graph.

Direct tool-calling agent (single-pass)

When you know a request needs exactly one lookup, skip the reasoning loop and call the tool deterministically — cheaper, faster, and easier to test.

python · direct_balance_check.py
def balance_lookup_node(state):
    account_id = extract_account_id(state["messages"][-1].content)  # regex or small classifier
    balance = get_account_balance.invoke({"account_id": account_id})
    return {"messages": [AIMessage(content=f"Your available balance is {balance['amount']} {balance['currency']}.")]}
DESIGN CALL

Not every request needs an LLM to decide which tool to call. Route simple, high-volume intents (balance check, branch locator) to deterministic code paths, and reserve the reasoning loop for genuinely ambiguous requests. This is also your first cost-optimization lever — see Section 13.

Plan-and-execute

For multi-step tasks — like a full loan application — have the model draft a plan up front, then execute each step with room to replan if a step fails or reveals new information.

python · plan_and_execute.py
class PlanState(TypedDict):
    request: str
    plan: list[str]
    past_steps: list[tuple]
    response: str

def planner(state: PlanState) -> dict:
    plan = planning_llm.invoke(
        f"Break this into ordered steps: {state['request']}\n"
        "Available capabilities: credit check, income verification, policy lookup, EMI calculation."
    )
    return {"plan": parse_steps(plan.content)}

def executor(state: PlanState) -> dict:
    step = state["plan"][0]
    result = loan_advisor.invoke({"messages": [("user", step)]})
    return {"past_steps": state["past_steps"] + [(step, result)], "plan": state["plan"][1:]}

def replan_or_finish(state: PlanState) -> dict:
    if not state["plan"]:
        summary = llm.invoke(f"Summarize the final decision from: {state['past_steps']}")
        return {"response": summary.content}
    return {}

graph = StateGraph(PlanState)
graph.add_node("planner", planner)
graph.add_node("executor", executor)
graph.add_node("replan", replan_or_finish)
graph.add_edge(START, "planner")
graph.add_edge("planner", "executor")
graph.add_edge("executor", "replan")
graph.add_conditional_edges("replan", lambda s: END if s.get("response") else "executor", {END: END, "executor": "executor"})

RAG: grounding answers in banking documents

A compliance officer asking "can we waive the processing fee for a salaried customer switching from another bank?" needs an answer traceable to a specific clause — not a plausible-sounding guess.

🧒 EXPLAIN LIKE YOU'RE IN CLASS 7

This is like an open-book exam. Instead of the AI trying to remember bank rules from its own memory (where it could easily get something wrong), it opens the actual "rule book" (the bank's documents), finds the right page, and reads the answer from there before replying. That way, it's answering from the book, not just guessing.

Pipeline overview

  1. Ingest — load KYC manuals, credit policy PDFs, product T&Cs.
  2. Chunk — split into overlapping passages that preserve clause boundaries.
  3. Embed — convert chunks to vectors capturing semantic meaning.
  4. Index — store in a vector database with metadata (document, section, effective date).
  5. Retrieve — fetch the top-k relevant chunks for a query, often combined with keyword search.
  6. Rerank — re-score candidates for precision before they hit the prompt.
  7. Generate — answer using only retrieved context, with citations.

Ingest & chunk

python · ingest.py
from langchain_community.document_loaders import PyPDFLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter

loader = PyPDFLoader("credit_policy_2026.pdf")
docs = loader.load()

splitter = RecursiveCharacterTextSplitter(
    chunk_size=800, chunk_overlap=120,
    separators=["\n\n", "\n", ". ", " "],
)
chunks = splitter.split_documents(docs)
for c in chunks:
    c.metadata["doc_type"] = "credit_policy"
    c.metadata["effective_date"] = "2026-01-01"

Embed & index

python · index.py
from langchain_anthropic import AnthropicEmbeddings
from langchain_community.vectorstores import PGVector

embeddings = AnthropicEmbeddings(model="claude-embed-v1")   # or a dedicated embedding provider
vectorstore = PGVector.from_documents(
    documents=chunks,
    embedding=embeddings,
    connection_string=POSTGRES_URL,
    collection_name="bank_policy_docs",
)

Hybrid retrieval + reranking

Vector search alone misses exact terms like account codes or regulation numbers. Combine it with keyword (BM25) search, then rerank the merged candidates.

python · retrieve.py
from langchain.retrievers import EnsembleRetriever, ContextualCompressionRetriever
from langchain_community.retrievers import BM25Retriever
from langchain_cohere import CohereRerank

bm25 = BM25Retriever.from_documents(chunks)
bm25.k = 10
vector_retriever = vectorstore.as_retriever(search_kwargs={"k": 10})

hybrid = EnsembleRetriever(retrievers=[bm25, vector_retriever], weights=[0.4, 0.6])
compressor = CohereRerank(model="rerank-english-v3.0", top_n=4)
retriever = ContextualCompressionRetriever(base_compressor=compressor, base_retriever=hybrid)

Grounded generation with citations

python · rag_chain.py
RAG_PROMPT = ChatPromptTemplate.from_messages([
    ("system", "Answer strictly from the provided policy excerpts. Cite the source "
               "document and section for every claim. If the excerpts don't cover the "
               "question, say you don't have enough information — never guess."),
    ("human", "Excerpts:\n{context}\n\nQuestion: {question}"),
])

def format_docs(docs):
    return "\n\n".join(f"[{d.metadata['doc_type']} §{d.metadata.get('section','?')}]\n{d.page_content}" for d in docs)

rag_chain = (
    {"context": retriever | format_docs, "question": lambda x: x}
    | RAG_PROMPT | llm | StrOutputParser()
)

answer = rag_chain.invoke("Can the processing fee be waived for a salary-account switch?")
GROUNDING CHECK

Run an LLM-as-judge evaluator (Section 04) that flags any claim in the answer not traceable to a retrieved chunk — this is your primary defense against hallucinated policy terms.

Keeping the index current

  • Re-index on document version changes; tag chunks with effective_date and filter at query time so a superseded policy never surfaces.
  • Use metadata filters (product line, region, customer segment) to keep retrieval scoped — a savings-account policy shouldn't answer a mortgage question.
  • Track retrieval quality (recall@k, MRR) in LangSmith the same way you track generation quality.
07 / AGENTS & ADVANCED PATTERNS

MCP: exposing core banking systems as tools

The Model Context Protocol standardizes how an agent discovers and calls external tools — one server, callable from any MCP-compatible client, instead of re-wiring bespoke tools into every agent.

🧒 EXPLAIN LIKE YOU'RE IN CLASS 7

MCP is like a universal remote control. Normally, every TV brand needs its own special remote. A universal remote works with any TV. MCP lets any AI robot talk to any bank tool — checking a balance, checking a credit score — using the same simple "remote control," instead of needing a different plug for every single tool.

Why MCP instead of ad-hoc tools

The @tool decorator from Section 02 works, but it ties tools to one Python process. A bank typically has many consumers — the customer chatbot, the internal analyst copilot, a batch reconciliation agent — that all need the same underlying capabilities: look up an account, list transactions, check a credit bureau score. MCP lets you build that capability once, as a server, and expose it everywhere.

Standardized

Any MCP-aware agent framework can discover and call your tools without custom glue code.

Centralized governance

Auth, rate limits and audit logging live in one server instead of scattered across agent codebases.

Reusable

The same core-banking server backs the customer bot, the fraud copilot, and internal tooling.

Building an MCP server

python · core_banking_mcp_server.py
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("core-banking")

@mcp.tool()
def get_account_summary(account_id: str) -> dict:
    """Return balance, account type and status for an account."""
    _authorize(account_id)               # RBAC check — see Security section
    return core_banking_api.summary(account_id)

@mcp.tool()
def list_recent_transactions(account_id: str, days: int = 30) -> list[dict]:
    """List transactions on an account for the last N days (max 90)."""
    days = min(days, 90)
    return core_banking_api.transactions(account_id, days)

@mcp.tool()
def check_bureau_score(customer_id: str, consent_token: str) -> int:
    """Fetch a credit bureau score. Requires a valid customer consent token."""
    if not consent_service.is_valid(consent_token, customer_id):

08 / AGENTS & ADVANCED PATTERNS

Multi-agent systems: a banking supervisor

One agent trying to be a fraud analyst, a loan officer and a customer service rep at once accumulates conflicting instructions and an unmanageable tool list. Splitting by domain keeps each agent focused, testable, and separately guardrailed.

🧒 EXPLAIN LIKE YOU'RE IN CLASS 7

Think of a hospital. You don't ask one doctor to do everything — there's a receptionist who listens to your problem first and then sends you to the right doctor: eye doctor, dentist, or bone doctor. In this bank AI, there's a "receptionist" robot (the supervisor) that decides if your question is about fraud, loans, or general help, and sends you to the specialist robot trained for exactly that job.

The pattern: supervisor + specialists

A lightweight supervisor classifies intent and hands off; each specialist owns its own tools, prompt, and guardrails, and reports back through shared state.

python · supervisor_graph.py
from typing import Literal
from langgraph.graph import StateGraph, START, END

class BankState(TypedDict):
    messages: Annotated[list, add_messages]
    next_agent: str

fraud_agent = create_react_agent(model=llm, tools=[flag_transaction, freeze_card, list_recent_transactions],
    prompt="You are a fraud triage specialist. Be conservative — when uncertain, escalate to a human analyst rather than freezing an account.")

loan_agent = create_react_agent(model=llm, tools=[check_credit_score, calculate_emi, fetch_loan_policy],
    prompt="You are a loan eligibility specialist. Cite policy figures exactly; never state a rate you didn't retrieve.")

support_agent = create_react_agent(model=llm, tools=[get_account_summary, get_branch_locations],
    prompt="You are a general customer support specialist for routine, non-sensitive queries.")

def supervisor(state: BankState) -> dict:
    intent = router_llm.invoke(
        f"Classify this banking request into exactly one label: fraud, loan, support.\n"
        f"Request: {state['messages'][-1].content}"
    ).content.strip().lower()
    return {"next_agent": intent if intent in ("fraud", "loan", "support") else "support"}

def route(state: BankState) -> Literal["fraud", "loan", "support"]:
    return state["next_agent"]

graph = StateGraph(BankState)
graph.add_node("supervisor", supervisor)
graph.add_node("fraud", fraud_agent)
graph.add_node("loan", loan_agent)
graph.add_node("support", support_agent)
graph.add_edge(START, "supervisor")
graph.add_conditional_edges("supervisor", route, {"fraud": "fraud", "loan": "loan", "support": "support"})
graph.add_edge("fraud", END)
graph.add_edge("loan", END)
graph.add_edge("support", END)

app = graph.compile(checkpointer=checkpointer)

ConcernSingle agentSupervisor + specialists

GuardrailsOne-size-fits-all, hard to tuneFraud agent stays conservative; support agent stays fast
EvaluationOne noisy golden set for everythingSeparate golden sets per domain (Section 04)
Blast radius of a bad prompt changeAffects all conversationsContained to one specialist

Handoffs mid-conversation

Real conversations cross domains — a support chat that reveals a fraud pattern needs to hand off without losing context. Specialists can return a routing signal instead of ending the turn.

def support_with_handoff(state: BankState) -> dict:

    if "possible fraud" in result["messages"][-1].content.lower():
        return {**result, "next_agent": "fraud"}

graph.add_conditional_edges("support", lambda s: s.get("next_agent", END), {"fraud": "fraud", END: END})

Checkpointer & state store in production

  • Use a managed Postgres or Redis-backed checkpointer, not the in-memory one — pods are ephemeral and get rescheduled.
  • Set a TTL/archival policy on conversation threads to satisfy data-retention requirements (Section 14).
  • Separate the checkpoint store per environment (dev/staging/prod) — never point a staging agent at production customer state.

CI/CD & release strategy

The extra step beyond normal software CI/CD: prompts and models are also releasable artifacts, and every release needs an evaluation gate, not just a test-pass gate.

🧒 EXPLAIN LIKE YOU'RE IN CLASS 7

This is like a quality-check line in a toy factory. Before a toy is sent to a shop, workers check that no parts are broken, everything works properly, and it's safe to play with. CI/CD does this for every update to our AI robot — it tests each change carefully before letting real customers use it, and can undo the change quickly if something turns out to be wrong.

Pipeline stages

Unit & integration tests

Standard code tests: tool functions, parsers, API contracts — fast, deterministic, run on every commit.

Golden-set evaluation

Run the LangSmith evaluation suite from Section 04 against the changed prompt/graph/model. Block merge on regression.

Guardrail & red-team tests

Adversarial prompts (jailbreaks, injection attempts, PII exfiltration attempts) must be caught — see Section 11.

Staging canary

Deploy to staging with production-shaped traffic replay; watch cost, latency, groundedness for a burn-in window.

Progressive production rollout

5% → 25% → 100% traffic with automatic rollback triggers on quality or error-rate regression.

Automatic rollback triggers

  • Groundedness or eligibility-accuracy score drops below threshold on live-traffic sampling.
  • Guardrail block rate spikes (could mean a prompt regression is provoking more unsafe outputs, or a legitimate feature broke).
  • P95 latency or provider error rate exceeds SLO for N consecutive minutes.
  • Cost-per-conversation exceeds budget ceiling (Section 13) — catches a routing bug sending everything to the expensive model.

Guardrails & safety

In banking, a guardrail failure isn't a bad joke — it's a wrong balance, a leaked account number, or an unauthorized transfer. Guardrails run on both sides of the model: input and output.

🧒 EXPLAIN LIKE YOU'RE IN CLASS 7

Guardrails are like the safety fences and seatbelts on an amusement park ride. They stop the AI robot from doing something dangerous — like giving away someone's private information, or sending someone's money without permission — even if a clever person tries to trick it into breaking the rules.

Layered defense

Input guardrails

Prompt-injection detection, jailbreak classifiers, topic/scope restriction, rate limiting per user.

Output guardrails

PII/PAN redaction, groundedness checks, policy-compliance checks, toxicity/refusal validation.

Input validation

python · input_guardrails.py
from guardrails_lib import PromptInjectionClassifier, ScopeClassifier

injection_guard = PromptInjectionClassifier()
scope_guard = ScopeClassifier(allowed_topics=["banking products", "account queries", "loan eligibility"])

def guarded_entry(state: BankState) -> dict:
    user_msg = state["messages"][-1].content
    if injection_guard.score(user_msg) > 0.8:
        return {"messages": [AIMessage(content="I can't process that request.")], "next_agent": "blocked"}
    if not scope_guard.in_scope(user_msg):
        return {"messages": [AIMessage(content="I can only help with banking-related questions.")], "next_agent": "blocked"}
    return {"next_agent": None}

Output validation & PII redaction

python · output_guardrails.py
import re

PAN_PATTERN = re.compile(r"\b\d{4}[- ]?\d{4}[- ]?\d{4}[- ]?\d{4}\b")   # card numbers
AADHAAR_PATTERN = re.compile(r"\b\d{4}\s?\d{4}\s?\d{4}\b")

def redact_pii(text: str) -> str:
    text = PAN_PATTERN.sub("[CARD NUMBER REDACTED]", text)
    text = AADHAAR_PATTERN.sub("[ID NUMBER REDACTED]", text)
    return text

def output_guard_node(state: BankState) -> dict:
    reply = state["messages"][-1]
    clean = redact_pii(reply.content)
    grounded = groundedness_judge.invoke({"answer": clean, "context": state.get("retrieved_context", "")})
    if grounded.score < 0.7:
        clean = "I don't have enough verified information to answer that confidently — let me connect you with an agent."
    return {"messages": [AIMessage(content=clean)]}

Guardrailing high-risk actions

Any tool call that moves money, changes account status, or alters customer data should require an explicit policy check plus, for anything above a threshold, human approval via the interrupt() pattern from Section 03.

python · action_policy.py
HIGH_RISK_TOOLS = {"execute_transfer", "freeze_card", "close_account"}
TRANSFER_AUTO_APPROVE_LIMIT = 5000  # in local currency

def enforce_action_policy(tool_name: str, args: dict) -> str:
    if tool_name == "execute_transfer" and args["amount"] > TRANSFER_AUTO_APPROVE_LIMIT:
        return "requires_human_approval"
    if tool_name in HIGH_RISK_TOOLS:
        return "requires_dual_control"   # two-person authorization, common in banking ops
    return "auto_approved"

What to guard against

ThreatMitigation
Prompt injection via retrieved documents or tool outputTreat all retrieved/tool content as untrusted data, never as instructions; sanitize before including in context
Jailbreaks asking the model to ignore its system promptInjection classifier + system prompt reinforcement + refusal evaluator
Hallucinated interest rates or eligibility criteriaStructured output constrained to retrieved facts; groundedness scoring; deterministic calculation tools instead of model arithmetic
PII/account data leakage in responsesOutput redaction; role-scoped tool access; least-privilege data retrieval
Unauthorized high-value transactionsHuman-in-the-loop approval; dual control; hard limits enforced in code, not prompt instructions
NEVER RELY ON THE PROMPT ALONE

"Never transfer more than $5,000" in a system prompt is a suggestion to the model, not a control. Hard limits, authorization checks, and approval gates belong in code that runs regardless of what the model decides to do.

13 / PRODUCTION & OPERATIONS

Cost optimization

Token costs scale with usage in a way traditional compute doesn't — a viral support flow can 10x your bill overnight. Cost control is an architecture decision, not a finance afterthought.

🧒 EXPLAIN LIKE YOU'RE IN CLASS 7

This is about saving pocket money. If a question is easy, ask the cheap, fast helper. If it's a really hard question, ask the more expensive, smarter helper. Also, if the same question gets asked again and again, just remember the answer instead of working it out from scratch every single time — that saves both time and money.

Levers, cheapest to hardest

Caching

Exact-match and semantic caching for repeated questions ("what are your savings account rates" gets asked hundreds of times a day).

Model routing by complexity

Send simple lookups to a small/cheap model, reserve the frontier model for genuinely hard reasoning (see Section 15).

Prompt & context trimming

Summarize long conversation history instead of resending it in full every turn; trim retrieved context to what's actually relevant.

Batching

Non-interactive workloads (nightly compliance re-checks) use batch APIs at a fraction of real-time pricing.

Deterministic shortcuts

Skip the LLM entirely for pure lookups — a balance check doesn't need reasoning, just a tool call.

Tracking cost per unit of value

Raw dollar spend means little without a denominator. Track cost per resolved conversation, per agent, and per customer segment — a fraud investigation costing $2 in tokens is cheap next to the fraud it prevents; the same $2 on a routine balance check is a routing bug.

ROLE_TOOL_ACCESS = {
    "customer_chatbot": {"get_account_summary", "get_branch_locations"},
    "fraud_specialist":  {"get_account_summary", "list_recent_transactions", "flag_transaction", "freeze_card"},
    "loan_specialist":   {"check_credit_score", "fetch_loan_policy", "calculate_emi"},
}

def authorize_tool_call(caller_role: str, tool_name: str, account_owner: str, requester_id: str):
    if tool_name not in ROLE_TOOL_ACCESS.get(caller_role, set()):
        raise PermissionError(f"{caller_role} is not permitted to call {tool_name}")
    if caller_role == "customer_chatbot" and account_owner != requester_id:
        raise PermissionError("Customers may only access their own account data")

Data handling

  • Minimize what reaches the model — pass only the fields a tool call needs, not entire customer records.
  • Encrypt in transit and at rest — TLS to all model/MCP endpoints; encrypted checkpoint and vector stores.
  • Data residency — route requests through model deployments in the required region for customer data that can't leave a jurisdiction.
  • Retention limits — expire conversation threads and traces per your regulatory retention schedule, not indefinitely.
  • Vendor data-use terms — confirm whether the model provider trains on your data and disable it contractually where required (zero-data-retention agreements).

Circuit breaker for a degrading provider

python · circuit_breaker.py
class CircuitBreaker:
    def __init__(self, failure_threshold=5, cooldown_seconds=60):
        self.failures, self.threshold, self.cooldown = 0, failure_threshold, cooldown_seconds
        self.open_until = None

    def call(self, fn, *args, **kwargs):
        if self.open_until and time.time() < self.open_until:
            raise ProviderUnavailable("circuit open — using fallback")
        try:
            result = fn(*args, **kwargs)
            self.failures = 0
            return result
        except Exception:
            self.failures += 1
            if self.failures >= self.threshold:
                self.open_until = time.time() + self.cooldown
            raise

Why routing is also a cost and safety control

Cost

Most traffic is simple — routing it away from the frontier model is the single biggest lever in Section 13.

Latency

Small models respond faster; route latency-sensitive intents (live chat) accordingly.

Resilience

Multi-provider fallback means a single vendor outage doesn't take down customer-facing banking services.

EVALUATE EACH ROUTE SEPARATELY

A cheaper model routed to "simple" traffic still needs its own golden-set evaluation (Section 04) — complexity classification is imperfect, and a misrouted eligibility question answered by the small model is a quality bug, not a cost win.

Checklist before going live

Correctness

Golden evaluation set covering common, edge, and adversarial cases, run in CI on every change with a hard quality gate.

Grounding

Every factual claim about rates, policy, or eligibility traceable to a retrieved source or a deterministic tool call — never free-form model arithmetic.

Guardrails

Input and output guardrails independent of the model's own judgment; hard limits on high-risk actions enforced in code.

Human-in-the-loop

An approval or escalation path for anything above a defined risk threshold, and an always-available route to a human.

Observability

Trace-level, metric-level, and log-level visibility, correlated, with alerts tied to written runbooks.

Cost control

Caching, tiered model routing, and hard per-conversation budget ceilings enforced in code, not just tracked in a dashboard.

Security

Secrets in a vault, RBAC on every tool, encryption in transit and at rest, and durable audit logs for every high-risk action.

Resilience

Multi-provider fallback, circuit breakers, and a rollback path tested before it's needed in an incident.

Compliance

Explainable decisions, bias-tested eval slices, enforced consent, and a defined data retention policy.

Release discipline

Prompts and models versioned like code, canaried before full rollout, with automatic rollback triggers.

Where to go from here

  • Start with a single narrow use case (Section 05's loan advisor) fully hardened end-to-end, rather than a broad but shallow assistant.
  • Build the golden evaluation set (Section 04) before writing the second version of any prompt — you'll need it immediately.
  • Add specialists and MCP tool servers incrementally (Sections 07-08); resist building one large agent that does everything.
  • Treat Sections 09-15 as non-optional — they're the difference between a convincing demo and a system a bank can actually run.
CLOSING NOTE

LangChain, LangGraph and LangSmith give you the primitives; the discipline in Sections 09 through 16 is what turns those primitives into something a risk committee will actually approve. Build the boring parts — evaluation, guardrails, observability, cost ceilings — at the same time as the exciting parts, not after.
