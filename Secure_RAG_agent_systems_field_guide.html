Building secure, measurable RAG and agent systems

A single reference covering MCP servers, keeping documents fresh, protecting sensitive data, per-user access, guardrails, multi-agent designs, and evaluation with RAGAS and LLM judges.

Why create MCP servers

A model on its own can only use its prompt and training data. An MCP (Model Context Protocol) server is the connector to something outside: files, a database, GitHub, Slack, or an internal API.

The problem it solves

Without a standard, 5 AI apps and 20 tools could mean up to 100 custom integrations. With MCP you wrap each tool once, and any compatible client (Claude, an IDE, your own agent) can use it. Think USB-C instead of a drawer of proprietary cables.

Your systems aren't covered

Internal databases and company APIs have no ready-made server, so you build one.

Control and safety

Expose read-only queries instead of raw database access, add authentication, validate inputs, log everything.

Cleaner interfaces

A few well-described tools like search_orders work better for a model than a sprawling REST API.

Reuse

Build once, use from many clients. Retrieval and actions live in the server, not in every prompt.

A server offers three things: tools (actions the model can invoke), resources (data it can read), and prompts (reusable workflow templates).

Skip building one if a ready-made server exists, or if a single app with one integration is simpler calling the API directly. MCP pays off with several tools, several clients, or a need for a controlled boundary.

Re-ingesting a revised document efficiently

You ingested 100 docx files and one revision changed three lines. Re-embed only what changed.

  1. Stable identity. Store doc_id, chunk_index, chunk_hash (SHA-256 of the text), and a version or timestamp on each chunk. Keep a document-level hash in a small registry.
  2. Detect change. Hash the new file. If it matches the registry, skip it. Otherwise parse, chunk, and hash each chunk.
  3. Diff by chunk hash. Unchanged hash: keep. New hash: embed and insert. Old hash missing from the new version: delete. Three edited lines usually means one to three chunks re-embedded.
  4. Update safely. Upsert and delete by doc_id plus hash, ideally atomically or with a version flag, so queries never see a half-updated document.
The catch: with fixed-size chunking, an edit shifts every later chunk and all their hashes change. Chunk on structure (headings, paragraphs, sections), hash normalized text, and derive chunk IDs from content rather than position.

Simplest fallback: delete all chunks where doc_id = X and re-ingest that one file. LlamaIndex's hashing document store and LangChain's record manager do the diffing for you.

Preventing sensitive data leaks and attacks

There is no single fix. Layer controls on what goes in, what comes out, and what the system can do if something goes wrong.

Keep data from the model

  • Classify chunks at ingestion
  • Detect and redact PII and secrets (Presidio, DLP)
  • Mask with tokens like <PERSON_1>, restore after
  • Use private or zero-retention deployments for sensitive data

Enforce access in retrieval

  • Permissions as chunk metadata
  • Filter in the query using the user's identity
  • Isolate tenants
  • Never let the model decide who is authorized

Defend against injection

  • Treat retrieved text as untrusted data
  • Strip hidden text, comments, odd metadata from docx
  • Run an injection classifier on input and chunks
  • No secrets in the system prompt

Least privilege

  • Minimal, read-only tool permissions
  • Human approval for sensitive actions
  • Restrict outbound links and images (data exfiltration)
  • Short-lived scoped credentials

Filter the output

  • Scan for PII, secrets, over-clearance content
  • Validate structured output against a schema
  • Add citations for audit

Protect the pipeline

  • Encrypt vector DB (embeddings can leak text)
  • Secrets manager for keys
  • Rate limits, redacted logs, retention limits
  • Vet plugins and MCP servers
Priority order: per-user filtering in retrieval, then PII redaction, then untrusted-content handling with an injection filter, then tool and output restrictions, then logging and red-team tests (Garak, PyRIT). Assume the model can be tricked, and make sure it has nothing it shouldn't expose.

Documents only some people may access

Rule: enforce permissions at retrieval time with the end user's identity, before anything reaches the LLM.

Capture permissions at ingestion

{
  "doc_id": "hr-policy-2024",
  "chunk_id": "hr-policy-2024#12",
  "allowed_groups": ["hr", "executives"],
  "allowed_users": ["alice@corp.com"],
  "tenant_id": "acme"
}

Pull ACLs from the source of truth (SharePoint, Drive, Confluence) so they match what employees already have.

Query flow

User query→Authenticate, resolve groups→Vector search with ACL filter→LLM

Filter inside the vector query (pre-filtering). Retrieving the top 10 and discarding forbidden ones leaves too few results and can leak through counts or scores.

PatternWhen it fits
Metadata filtering, one indexMost cases; the common default
Index or namespace per tenant or departmentStrong isolation, few access groups
Check the source system's permission API at runtimeVery dynamic permissions; slower but always current
HybridNamespace per tenant plus metadata filters for roles

Keep it correct

  • Store group names on chunks and resolve membership at query time, so team changes apply without re-indexing.
  • Re-sync ACLs on change (webhooks or scheduled jobs); metadata updates need no re-embedding. Treat revocations as high priority.
  • Key caches by user or permission set; don't carry content across users in memory or history; don't show titles or snippets of forbidden documents; protect logs.
  • Default deny: missing or malformed permission metadata means inaccessible.
  • Test with users of different roles asking questions answerable only from restricted documents, and re-test after grants, revocations, and group moves.

Security rules for guardrails

LayerRules
InputPrompt-injection and jailbreak detection (including encoded payloads); PII and secret redaction; length and format validation; topic scope limits; authentication and rate limiting
RetrievalACL filtering inside the query; scan chunks for injected instructions; source allowlists; sensitivity ceiling for external models
OutputScan for PII and secrets; harmful-content filtering; grounding checks with citations and "I don't know"; strip or allowlist links and images; schema validation; sanitize output before it touches HTML, SQL, or a shell
Actions and toolsLeast privilege; allowlist tools and validate every argument in code; human approval for high-impact actions; egress controls; short-lived credentials; step and cost limits
SystemSystem prompt is not a security boundary; defense in depth; fail closed; enforce policy in code outside the LLM; audit logs with retention limits; monitoring and alerts
GovernanceRegular red-teaming; guardrail policies versioned and tested like code; vetted third parties; documented rules for which data classes may go to which models

Common tools: NeMo Guardrails, Guardrails AI, LLM Guard, Llama Guard, Prompt Guard, Azure Content Safety, AWS Bedrock Guardrails, Presidio, Garak, PyRIT.

Classifier-based filters can be evaded. The strongest protection is the hard controls: access filtering, least privilege, egress limits, and human approval.

Multi-agent design patterns

Multi-agent designs split work across several LLM-powered agents. Here are ten patterns with their typical uses.

Coordinator or deciderWorker agentInput, output, human, or shared data

Choosing a pattern

NeedPattern
Complex task, unclear subtasksOrchestrator-worker
Fixed, repeatable stepsSequential pipeline
Independent subtasks, speed mattersParallel fan-out
Different domains, one answer neededRouter
Quality or correctness criticalReflection and critic
High stakes, reduce errorsDebate and consensus
Risky actionsHuman-in-the-loop
When not to use them: multi-agent systems cost more calls, add latency, and are harder to debug. If one agent with good tools can do the job, start there. Give each agent least-privilege tools and its own access scope, and treat messages between agents as untrusted input.

Evaluating RAG with RAGAS and LLM-as-judge

Retrieval and generation fail independently, so score them separately. Most RAGAS metrics use an LLM as the grader.

Evaluation dataset

Each row has user_input, retrieved_contexts, response, and optionally reference (needed only for context recall). Start with 50 to 200 rows: real user questions, multi-document questions, unanswerable questions (the bot should say it doesn't know), and past failures.

Metrics with a worked example

Question: "How many days of annual leave?" Context says 24 days and 5 carry-over days, plus an irrelevant canteen chunk. The answer claims 24 days, 10 carry-over days, and a birthday day off.

MetricStageHow it's computedExample
FaithfulnessGenerationSplit the answer into claims, check each against the context; supported / total1 of 3 supported (24 days only), so 0.33
Context precisionRetrievalJudge marks each chunk relevant or not; rewards relevant chunks ranked earlyRelevant chunks ranked 1 and 2, so 1.0. Canteen chunk first would give about 0.58
Context recallRetrievalShare of reference statements found in the contexts2 of 2, so 1.0
Response relevancyGenerationQuestions generated from the answer are compared to the original by embeddingsMeasures on-topic, not truth

Running it

from ragas import evaluate, EvaluationDataset
from ragas.metrics import (Faithfulness, ResponseRelevancy,
    LLMContextPrecisionWithReference, LLMContextRecall)

dataset = EvaluationDataset.from_list(rows)
result = evaluate(dataset=dataset, metrics=[
    Faithfulness(llm=judge),
    ResponseRelevancy(llm=judge, embeddings=emb),
    LLMContextPrecisionWithReference(llm=judge),
    LLMContextRecall(llm=judge)])
df = result.to_pandas()
print(df.sort_values("faithfulness").head(10))

RAGAS is changing its API (the 0.4.x line adds a ragas.metrics.collections module and deprecates older class names), so check the docs for your installed version.

Custom LLM-as-judge

For business rules RAGAS doesn't know (must cite the policy, must refuse out-of-scope questions, must not reveal restricted documents), write a rubric judge that returns JSON.

  • Ask for reasoning before the score, use narrow rubrics with anchors, and prefer binary or 1 to 5 scales.
  • Run at temperature 0 with structured output; repeat runs if scores are noisy.
  • For comparing two versions, use pairwise judging and swap the order to cancel position bias.
  • Use a strong judge, ideally from a different model family than the system under test.

Validate the judge

Hand-label 50 to 100 items, run the judge on them, and measure agreement with a chance-corrected statistic such as Cohen's kappa rather than raw percent agreement. Also check consistency across repeated runs and bias toward longer answers. Re-check after every judge or rubric change.

Make it routine

  • Run the eval set in CI on every prompt, chunking, embedding, or model change, and fail on a drop below your threshold.
  • Change one thing at a time, and read the ten lowest-scoring rows, not just averages.
  • Log retrieved contexts, or a low faithfulness score can't tell you which stage failed.
  • Keep the judge model fixed when comparing scores, and include unanswerable and adversarial questions.
  • Pair LLM judges with deterministic checks: valid citations, valid JSON, no restricted-document leaks, latency, cost.
