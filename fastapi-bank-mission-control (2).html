Station 00

What's an API, really?

Before FastAPI, before banks, before Kubernetes — one idea underneath all of it: computers asking each other for things.

Explain it like I'm in 7th grade

Imagine a restaurant. You (the customer) don't walk into the kitchen and cook your own food. You tell the waiter what you want from the menu. The waiter takes your order to the kitchen, the kitchen makes it, and the waiter brings it back.

An API (Application Programming Interface) is the waiter. Your phone app is the customer. The server (a powerful computer somewhere) is the kitchen. The "menu" is the list of things you're allowed to ask for — like "get my bank balance" or "send $10 to my friend."

The technical version

An API is a contract: a set of URLs ("endpoints"), the data you must send, and the data you'll get back. The most common style on the web is REST, which uses HTTP methods to mean different actions:

HTTP MethodMeaningBank example
GETRead dataGET /accounts/42 → view account 42
POSTCreate something newPOST /transfers → make a new transfer
PUT/PATCHUpdate somethingPATCH /accounts/42 → update account details
DELETERemove somethingDELETE /cards/9 → cancel a card

A request and response usually travel as JSON — plain text formatted so both humans and computers can read it easily:

Example: what your phone sends and gets back
// Request:  POST /transfers
{
  "from_account": "42",
  "to_account": "77",
  "amount": 10.00
}

// Response: 201 Created
{
  "transfer_id": "tx_9F2A",
  "status": "completed",
  "amount": 10.00
}
Why FastAPI?

FastAPI is a Python tool for building these APIs fast — it's fast to write, and the resulting API is fast to run. It also automatically builds you a live, clickable "menu" of your API (called Swagger/OpenAPI docs), so you never have to write that menu by hand.

Python Quick Refresher

Just enough Python to read every example on this page. Skip this if you already know Python.

Explain it like I'm in 7th grade

Python is a language for talking to computers using words that look a lot like English. A variable is a labeled box that holds a value. A function is a mini-recipe you can reuse. A class is a blueprint for making similar objects — like a cookie cutter for cookies.

Variables & types

name = "Asha"        # a piece of text (string)
age = 13              # a whole number (int)
balance = 249.50       # a decimal number (float)
is_active = True       # True or False (bool)
pets = ["cat", "dog"]  # a list, ordered, can change

Functions

def add_interest(balance: float, rate: float) -> float:
    """Adds interest to a balance and returns the new balance."""
    return balance + (balance * rate)

new_balance = add_interest(1000, 0.05)   # 1050.0

The : float and -> float bits are type hints — they tell Python (and FastAPI!) what kind of data goes in and comes out. FastAPI uses these hints to validate data automatically, which is why they matter so much here.

Async / await — doing many things at once

Explain it like I'm in 7th grade

Imagine you put toast in the toaster. A bad cook stares at the toaster doing nothing until it pops. A good cook starts the toast, then chops fruit while waiting. async code is the good cook — while one task is waiting (like fetching data from a database), Python can work on other tasks instead of just standing still.

import asyncio

async def get_balance(account_id: str) -> float:
    await asyncio.sleep(1)   # pretend this is a slow database call
    return 1050.0

async def main():

    print(balance)

FastAPI is built around async def endpoints so it can handle thousands of waiting requests (like slow database calls) without getting stuck.

Explain it like I'm in 7th grade

FastAPI lets you write a Python function, stick a "sign" above it saying which web address it answers to, and it becomes a real website API. It also checks that anyone sending you data followed the rules — like a bouncer checking IDs at a door — before your code ever runs.

Request bodies with Pydantic — the "ID checker"

Explain it like I'm in 7th grade

A Pydantic model is a form you make someone fill out correctly before you accept their request — every field has a required type, so if they send "ten dollars" instead of 10.0, FastAPI rejects it automatically, before your code even sees it.

schemas.py
from pydantic import BaseModel, Field

class TransferRequest(BaseModel):
    from_account: str
    to_account: str
    amount: float = Field(gt=0, description="Must be positive")

class TransferResponse(BaseModel):
    transfer_id: str
    status: str
main.py
from fastapi import FastAPI
from schemas import TransferRequest, TransferResponse
import uuid

app = FastAPI()

@app.post("/transfers", response_model=TransferResponse, status_code=201)
def create_transfer(payload: TransferRequest):
    # payload.amount is guaranteed to be a positive float here
    return TransferResponse(transfer_id=str(uuid.uuid4()), status="completed")
Try it yourself

Run the server, then open /docs in your browser. FastAPI reads your type hints and Pydantic models and builds a full interactive test page for you — no extra work.

Station 03

Design Patterns

Reusable solutions to problems every programmer eventually hits. We'll use bank examples for every one.

Explain it like I'm in 7th grade

A design pattern is like a LEGO instruction booklet. It doesn't give you the finished castle — it gives you a proven way to assemble certain pieces so the castle doesn't fall over. Programmers reuse these patterns instead of inventing a new way to solve the same old problem every time.

Singleton — only one of something must exist

Used for things like a single shared database connection pool.

class DBConnectionPool:
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._instance.connections = []
        return cls._instance

# Both variables point to the exact same object
pool_a = DBConnectionPool()
pool_b = DBConnectionPool()
assert pool_a is pool_b

Factory — a "maker" that decides which object to build

class SavingsAccount: ...
class CheckingAccount: ...

def account_factory(kind: str):
    if kind == "savings":
        return SavingsAccount()
    if kind == "checking":
        return CheckingAccount()
    raise ValueError("Unknown account type")

acc = account_factory("savings")

Strategy — swap the "how" without changing the "what"

Great for interest calculation rules that change per account type.

class SimpleInterest:
    def calculate(self, balance, rate): return balance * rate

class CompoundInterest:
    def calculate(self, balance, rate): return balance * ((1 + rate) - 1)

class Account:
    def __init__(self, interest_strategy):
        self.interest_strategy = interest_strategy

    def apply_interest(self, balance, rate):
        return self.interest_strategy.calculate(balance, rate)

Repository — hide the database behind a simple interface

class AccountRepository:
    def __init__(self, db_session):
        self.db = db_session

    def get(self, account_id: str):
        return self.db.query(Account).filter_by(id=account_id).first()

    def save(self, account):
        self.db.add(account)
        self.db.commit()

# Your business logic calls repo.get(), never writes raw SQL directly.
# Swap Postgres for MongoDB later without touching business logic.

Dependency Injection — hand in what's needed, don't build it inside

Explain it like I'm in 7th grade

Instead of a chef growing their own vegetables inside the kitchen (hard to test, hard to swap), someone delivers fresh vegetables to the door every morning. The kitchen just uses whatever arrives. FastAPI's Depends() is exactly this delivery system, covered next.

PatternBank problem it solves
SingletonOne shared DB connection pool app-wide
FactoryCreating the right account type from a string
StrategySwapping interest/fee rules per product
RepositoryIsolating business logic from the database
Unit of WorkMaking a group of DB changes succeed/fail together
Circuit BreakerStop hammering a downstream service that's down
CQRSSeparate "read fast" paths from "write safely" paths

We'll use several of these for real in the Bank Capstone and Microservices stations.

Explain it like I'm in 7th grade

Instead of writing every rule of a school in one giant book, you split it into a Math handbook, a Sports handbook, and a Lunch handbook. A FastAPI router is one of those handbooks — a file full of related endpoints that plugs into the main app.

Dependency Injection with Depends()

from fastapi import Depends, FastAPI
from sqlalchemy.orm import Session

app = FastAPI()

def get_db():
    db = SessionLocal()
    try:
        yield db          # "deliver" the db session
    finally:
        db.close()          # always clean up after the request

@app.get("/accounts/{account_id}")
def get_account(account_id: str, db: Session = Depends(get_db)):
    return db.query(Account).filter_by(id=account_id).first()

This same pattern is used later to inject the current logged-in user from a JWT token into any endpoint that needs it.

Middleware — code that runs around every request

import time
from fastapi import Request

@app.middleware("http")
async def add_timing_header(request: Request, call_next):
    start = time.time()
    response = await call_next(request)
    response.headers["X-Process-Time"] = str(time.time() - start)
    return response

Background tasks — reply first, finish the chore later

Explain it like I'm in 7th grade

You tell a friend "done!" for a chore, then actually finish tidying up after they leave, so they don't have to stand around waiting. Sending a "transfer confirmation" email doesn't need to block the API response.

Station 05

SQL, MongoDB & Data Synchronization

Two very different filing cabinets, when to use each, and how to keep them in sync.

Explain it like I'm in 7th grade

SQL (like PostgreSQL) is a filing cabinet with strict labeled folders — every folder has the exact same tabs (columns), so nothing gets misplaced. Great for money, where every row must follow the same strict rules.

MongoDB is a big box where each item can be wrapped differently — one product might have 5 fields, another 12. Great for things that change shape often, like product catalogs or activity logs.

SQL (PostgreSQL)MongoDB
StructureFixed schema, tables & rowsFlexible schema, documents (JSON-like)
RelationshipsStrong (foreign keys, joins)Weaker, often embedded/denormalized
TransactionsRock-solid ACID by defaultSupports ACID too, but usually used differently
Best for bankingLedgers, balances, transactionsAudit logs, notifications, device sessions

SQL with FastAPI (SQLAlchemy / SQLModel)

models.py
from sqlmodel import SQLModel, Field
from decimal import Decimal

class Account(SQLModel, table=True):
    id: str = Field(primary_key=True)
    owner: str
    balance: Decimal = Field(default=0)

class Transaction(SQLModel, table=True):
    id: str = Field(primary_key=True)
    account_id: str = Field(foreign_key="account.id")
    amount: Decimal
    kind: str   # "deposit" | "withdrawal" | "transfer"
main.py
from sqlmodel import Session, select

@app.get("/accounts/{account_id}/transactions")
def list_transactions(account_id: str, session: Session = Depends(get_session)):
    stmt = select(Transaction).where(Transaction.account_id == account_id)
    return session.exec(stmt).all()
Always use Decimal, never float, for money

Floats round money incorrectly (0.1 + 0.2 isn't exactly 0.3 in binary). Use Python's Decimal type and your database's NUMERIC column type for anything involving currency.

Data synchronization techniques

Explain it like I'm in 7th grade

If you write your homework in two different notebooks, you have to make sure both notebooks say the same thing, or you'll get confused about what's actually true. Keeping two databases in agreement is the same problem, just for computers.

1. Dual write (simple, but risky)

def create_transfer(data):
    save_to_postgres(data)     # if this succeeds...
    save_to_mongo_audit(data)  # ...but this fails, they disagree!
Why this is dangerous

If the second write fails, your two data stores now disagree, and nothing tells you. Avoid dual writes for anything that must always match, like money.

2. Outbox pattern (reliable)

Outbox Pattern 1. Write transaction + an "outbox" row in ONE Postgres transaction (both succeed together, or both fail together) 2. A separate worker reads unsent outbox rows 3. Worker publishes an event → message queue (Kafka / Azure Service Bus) 4. Mongo-writing service consumes the event → updates MongoDB 5. Worker marks the outbox row as "sent"

Because step 1 uses a single database transaction, the transaction and the "I need to sync this" note are saved atomically — nothing can succeed halfway.

3. Change Data Capture (CDC)

Tools like Debezium watch Postgres's internal write-ahead log and automatically stream every row change out as an event — no code changes needed in your app at all.

Postgres --(WAL changes)--> Debezium --(events)--> Kafka --> MongoDB / Search / Cache

4. Event-driven sync (used across microservices)

# Account service publishes an event after committing to SQL
async def transfer_completed(event: dict):
    await kafka_producer.send("transfers.completed", event)

# Notification service (separate microservice) listens and writes to Mongo
async def on_transfer_completed(event: dict):
    await mongo_db.notifications.insert_one({
        "user_id": event["user_id"],
        "message": f"Transfer of {event['amount']} completed",
    })
TechniqueConsistencyComplexityUse when
Dual writeWeakLowNon-critical, toy projects only
Outbox patternStrong (eventual)MediumMoney-related events
CDC (Debezium)Strong (eventual)Medium-HighSyncing without touching app code
Event-drivenEventualMediumMicroservices reacting to each other
Station 06

JWT, OAuth2 & OIDC

Three names that get mixed up constantly. Here's exactly what each one actually does.

Explain it like I'm in 7th grade

JWT is a stamped hall pass — a piece of paper that proves "yes, the teacher already checked this student, they're allowed in." OAuth2 is the rulebook for how you're allowed to ask for, and get handed, that hall pass without giving away your actual password to every hallway monitor. OIDC adds a photo ID to the hall pass — it doesn't just prove you're allowed in, it also proves exactly who you are.

JWT — JSON Web Token

A JWT is a compact, signed string with three parts separated by dots: header.payload.signature.

Anatomy of a JWT eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiI0MiIsImV4cCI6MTcwMDAwfQ.4f8a2c... └──────── header ────────┘└────────── payload ──────────┘└─ signature ─┘ Header: { "alg": "HS256", "typ": "JWT" } Payload: { "sub": "42", "role": "customer", "exp": 1700000000 } Signature: created using a SECRET KEY only the server knows The payload is only ENCODED (base64), not encrypted — anyone can read it. The signature is what proves nobody TAMPERED with it.
Important

Never put secrets (passwords, card numbers) inside a JWT payload — it's readable by anyone who has the token. The signature protects against forgery, not against reading.

Issuing and verifying JWTs in FastAPI

pip install python-jose[cryptography] passlib[bcrypt]
auth.py
from datetime import datetime, timedelta
from jose import jwt, JWTError
from fastapi import Depends, HTTPException
from fastapi.security import OAuth2PasswordBearer

SECRET_KEY = settings.jwt_secret   # from environment, never hard-coded
ALGORITHM = "HS256"
oauth2_scheme = OAuth2PasswordBearer(tokenUrl="token")

def create_access_token(user_id: str, expires_minutes: int = 30):
    payload = {
        "sub": user_id,
        "exp": datetime.utcnow() + timedelta(minutes=expires_minutes),
    }
    return jwt.encode(payload, SECRET_KEY, algorithm=ALGORITHM)

def get_current_user(token: str = Depends(oauth2_scheme)):
    try:
        payload = jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
        user_id = payload.get("sub")
    except JWTError:
        raise HTTPException(status_code=401, detail="Invalid or expired token")
    return user_id
main.py

        raise HTTPException(status_code=401, detail="Bad credentials")

OAuth2 — the rulebook for delegated access

OAuth2 defines roles and flows so an app can act on your behalf without ever seeing your password.

RoleWho they are
Resource OwnerYou, the customer
ClientThe app asking for access (e.g. a budgeting app)
Authorization ServerIssues tokens after you approve (e.g. your bank's login page)
Resource ServerThe API holding your actual data (e.g. the bank's account API)
Authorization Code Flow (the safe, standard one) 1. Budgeting App redirects you --> Bank's login page 2. You log in directly on the Bank's page (app never sees your password) 3. Bank redirects back with a one-time "authorization code" 4. Budgeting App exchanges the code (+ its own client secret) for an access_token at the Bank's token endpoint 5. Budgeting App calls Bank API using: Authorization: Bearer <access_token>

Using FastAPI's built-in OAuth2 password flow (simple case)

from fastapi.security import OAuth2PasswordRequestForm

@app.post("/token")
def login(form: OAuth2PasswordRequestForm = Depends()):
    user = authenticate(form.username, form.password)
    if not user:
        raise HTTPException(status_code=401)
    token = create_access_token(user.id)
    return {"access_token": token, "token_type": "bearer"}
Scopes — fine-grained permission

OAuth2 tokens can carry scopes like accounts:read or transfers:write, so a budgeting app can be granted "read my balance" without ever being allowed to move money.

OIDC — OpenID Connect (identity on top of OAuth2)

OAuth2 alone only proves "this app has permission." It doesn't formally prove who you are. OIDC adds exactly that, with one extra token:

TokenPurpose
Access Token"This app may call the API" (OAuth2)
ID Token"This person is definitely who they claim to be" (OIDC, always a JWT)
Refresh TokenUsed to get a new access token without logging in again
Decoded ID Token (OIDC)
{
  "iss": "https://login.mybank.com",
  "sub": "user_42",
  "aud": "budgeting-app-client-id",
  "email": "asha@example.com",
  "email_verified": true,
  "exp": 1700003600
}

This is exactly how "Sign in with Google" works — Google is the OIDC provider, and it hands the app a verified ID Token proving your identity.

Verifying an external OIDC provider's token in FastAPI

import httpx
from jose import jwt

async def verify_oidc_token(id_token: str):
    jwks = await httpx.AsyncClient().get(
        "https://login.mybank.com/.well-known/jwks.json"
    )
    return jwt.decode(
        id_token, jwks.json(), algorithms=["RS256"], audience="budgeting-app-client-id"
    )
In one sentence

JWT is the token format. OAuth2 is the flow for getting permission. OIDC is OAuth2 plus a signed proof of identity.

Station 07

Capstone: A Bank Backend

Putting FastAPI, SQL, JWT, and design patterns together into a real system: accounts, double-entry ledger, and safe transfers.

Explain it like I'm in 7th grade

A real bank never just changes one number when you send money — it writes down two matching entries: "$10 left account A" and "$10 arrived in account B." This is called double-entry bookkeeping, and it means the bank can always prove where every cent came from and went.

The data model

class Account(SQLModel, table=True):
    id: str = Field(primary_key=True)
    owner_id: str
    currency: str = "USD"
    # NOTE: balance is a DERIVED value, computed from ledger entries,
    # never trusted as the single source of truth

class LedgerEntry(SQLModel, table=True):
    id: str = Field(primary_key=True)
    transfer_id: str
    account_id: str
    amount: Decimal        # negative = debit, positive = credit
    created_at: datetime

Why idempotency matters

Explain it like I'm in 7th grade

If your phone loses signal right after you tap "Send $10" and you tap it again "just in case," the bank must not send $20. Idempotency means doing the same request twice has the same effect as doing it once.

class TransferRequest(BaseModel):
    from_account: str
    to_account: str
    amount: Decimal
    idempotency_key: str   # client generates a unique key per attempt

@app.post("/transfers")
def create_transfer(payload: TransferRequest, db: Session = Depends(get_db)):
    existing = db.exec(
        select(Transfer).where(Transfer.idempotency_key == payload.idempotency_key)
    ).first()
    if existing:
        return existing   # already processed — return the same result, don't redo it
    return process_new_transfer(payload, db)

The transfer itself — atomic and consistent

def process_new_transfer(payload: TransferRequest, db: Session):
    with db.begin():   # everything below succeeds together, or rolls back together
        balance = get_balance(db, payload.from_account)
        if balance < payload.amount:
            raise InsufficientFundsError()

        transfer = Transfer(id=str(uuid4()), idempotency_key=payload.idempotency_key,
                             status="completed")
        db.add(transfer)
        db.add(LedgerEntry(transfer_id=transfer.id, account_id=payload.from_account,
                             amount=-payload.amount))
        db.add(LedgerEntry(transfer_id=transfer.id, account_id=payload.to_account,
                             amount=payload.amount))
        db.add(OutboxEvent(type="transfer.completed", payload=transfer.dict()))
    return transfer

def get_balance(db: Session, account_id: str) -> Decimal:
    total = db.exec(
        select(func.sum(LedgerEntry.amount)).where(LedgerEntry.account_id == account_id)
    ).one()
    return total or Decimal(0)

Notice the OutboxEvent row saved in the same transaction — this is the Outbox Pattern from the Databases station, guaranteeing the event will eventually reach other services (like the notification service) even if the message queue is briefly down.

Wiring in JWT authentication

@app.post("/transfers")
def create_transfer(
    payload: TransferRequest,
    user_id: str = Depends(get_current_user),   # from the JWT, Station 06
    db: Session = Depends(get_db),
):
    account = get_account(db, payload.from_account)
    if account.owner_id != user_id:
        raise HTTPException(status_code=403, detail="Not your account")
    return process_new_transfer(payload, db)
Real bank systems also need

Fraud checks, rate limiting, dual authorization for large amounts, encryption at rest, PCI-DSS compliance, and full audit trails. This capstone shows the architecture skeleton — production banking software has many more layers of safety.

Station 08

Microservices Architecture

Splitting the bank into small, independent services instead of one giant program.

Explain it like I'm in 7th grade

Imagine one kid trying to be the entire school by themselves — teacher, cook, nurse, and janitor all at once. If they get sick, the whole school shuts down. Instead, a real school has separate people for each job who can work at their own pace and be replaced individually. Microservices split a big application the same way: separate small services, each doing one job well.

Splitting the bank

The Saga Pattern — transactions across services

Explain it like I'm in 7th grade

If moving money now means "tell Service A, then Service B, then Service C" and Service C fails, you can't just undo it like closing one notebook — you have to send each earlier service a note saying "please undo your part too." A Saga is that chain of do-this / undo-this steps.

async def transfer_saga(payload):
    try:
        await accounts_service.reserve_funds(payload.from_account, payload.amount)
        await ledger_service.record_transfer(payload)
        await notification_service.notify(payload.to_account)
    except Exception:
        await accounts_service.release_reserved_funds(payload.from_account, payload.amount)
        raise

Circuit Breaker — protecting yourself from a struggling service

from pybreaker import CircuitBreaker

fraud_service_breaker = CircuitBreaker(fail_max=5, reset_timeout=30)

@fraud_service_breaker

    return httpx.post("http://fraud-service/check", json=payload).json()

# After 5 failures, the breaker "opens" and fails fast for 30s

Trade-off to remember

Microservices buy you independent scaling and deployment, at the cost of network complexity, harder debugging, and eventual (not instant) consistency between services. Don't split a small app into 12 services on day one — start simpler, split when a real scaling or team-boundary pain shows up.

Cache carefully with money

Never cache the balance used to authorize a withdrawal — always read the real database for anything that spends money. Caching is fine for "display" reads, dangerous for "decision" reads.

CAP theorem, the short version

Explain it like I'm in 7th grade

If your two best friends are in different classrooms and can't talk to each other right now (a network problem), they each have to choose: either both stop answering questions until they can compare notes (pick Consistency), or both keep answering with maybe-outdated info (pick Availability). You can't have perfectly agreeing, always-answering friends during an actual network split.

CAP theorem: during a network Partition, a distributed system must choose between Consistency (every read sees the latest write) and Availability (every request gets a response). Bank ledgers usually favor consistency for money movement, and availability for things like "show recent activity."

CQRS — separate read and write models

Writes (transfers) go through the strict, validated ledger path. Reads (dashboard, statements) can be served from a pre-computed, denormalized, fast-read copy — updated asynchronously by the events from the Outbox pattern.

Write path: API -> validate -> Postgres ledger -> Outbox event Read path: Event -> projector -> read-optimized table / cache -> API (fast reads)

Backend: password hashing, JWT issue & verify

auth.py
from datetime import datetime, timedelta
from jose import jwt, JWTError
from passlib.context import CryptContext
from fastapi import Depends, HTTPException, status
from fastapi.security import OAuth2PasswordBearer

SECRET_KEY = settings.jwt_secret     # loaded from environment, never hard-coded
ALGORITHM = "HS256"
pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")
oauth2_scheme = OAuth2PasswordBearer(tokenUrl="auth/login")

def hash_password(password: str) -> str:
    return pwd_context.hash(password)

def verify_password(plain: str, hashed: str) -> bool:
    return pwd_context.verify(plain, hashed)

def create_access_token(user_id: str, role: str, expires_minutes: int = 60):
    payload = {
        "sub": user_id,
        "role": role,
        "exp": datetime.utcnow() + timedelta(minutes=expires_minutes),
    }
    return jwt.encode(payload, SECRET_KEY, algorithm=ALGORITHM)

async def get_current_user(token: str = Depends(oauth2_scheme)):
    try:
        payload = jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
    except JWTError:
        raise HTTPException(status_code=401, detail="Invalid or expired token")
    return {"id": payload["sub"], "role": payload["role"]}

def require_role(required_role: str):
    """Authorization: not just logged in, but the RIGHT role."""
    async def checker(user: dict = Depends(get_current_user)):
        if user["role"] != required_role and user["role"] != "admin":
            raise HTTPException(status_code=403, detail="Not authorized for this action")
        return user
    return checker
Authentication vs. authorization in this code

get_current_user only checks "is this a valid token" — that's authentication. require_role("admin") additionally checks "are you the right kind of user" — that's authorization. Secured routes use one or both, depending on what they protect.

Backend: auth routes (register & login)

routers/auth.py
from fastapi import APIRouter, HTTPException
from fastapi.security import OAuth2PasswordRequestForm
from fastapi import Depends
from bson import ObjectId

router = APIRouter(prefix="/auth", tags=["auth"])

@router.post("/register", response_model=UserOut, status_code=201)
async def register(payload: UserCreate):
    existing = await users_collection.find_one({"email": payload.email})
    if existing:
        raise HTTPException(status_code=400, detail="Email already registered")
    doc = {"email": payload.email, "password": hash_password(payload.password), "role": "member"}
    result = await users_collection.insert_one(doc)
    return UserOut(id=str(result.inserted_id), email=payload.email, role="member")

@router.post("/login")
async def login(form: OAuth2PasswordRequestForm = Depends()):
    user = await users_collection.find_one({"email": form.username})
    if not user or not verify_password(form.password, user["password"]):
        raise HTTPException(status_code=401, detail="Incorrect email or password")
    token = create_access_token(str(user["_id"]), user["role"])
    return {"access_token": token, "token_type": "bearer"}

Backend: secured CRUD routes for "notes"

routers/notes.py
from fastapi import APIRouter, Depends, HTTPException
from bson import ObjectId
from auth import get_current_user, require_role
from database import notes_collection
from schemas import NoteCreate, NoteOut

router = APIRouter(prefix="/notes", tags=["notes"])

def serialize(doc) -> NoteOut:
    return NoteOut(id=str(doc["_id"]), title=doc["title"],
                   content=doc["content"], owner_id=doc["owner_id"])

# CREATE — any authenticated user
@router.post("", response_model=NoteOut, status_code=201)
async def create_note(payload: NoteCreate, user: dict = Depends(get_current_user)):
    doc = {**payload.dict(), "owner_id": user["id"]}
    result = await notes_collection.insert_one(doc)
    doc["_id"] = result.inserted_id
    return serialize(doc)

# READ (list) — only your own notes
@router.get("", response_model=list[NoteOut])
async def list_notes(user: dict = Depends(get_current_user)):
    cursor = notes_collection.find({"owner_id": user["id"]})
    return [serialize(doc) async for doc in cursor]

# READ (one) — must be authenticated AND own the note
@router.get("/{note_id}", response_model=NoteOut)
async def get_note(note_id: str, user: dict = Depends(get_current_user)):
    doc = await notes_collection.find_one({"_id": ObjectId(note_id)})
    if not doc or doc["owner_id"] != user["id"]:
        raise HTTPException(status_code=404, detail="Note not found")
    return serialize(doc)

# UPDATE — must own the note
@router.put("/{note_id}", response_model=NoteOut)
async def update_note(note_id: str, payload: NoteCreate, user: dict = Depends(get_current_user)):
    doc = await notes_collection.find_one({"_id": ObjectId(note_id)})
    if not doc or doc["owner_id"] != user["id"]:
        raise HTTPException(status_code=404, detail="Note not found")
    await notes_collection.update_one({"_id": ObjectId(note_id)}, {"$set": payload.dict()})
    doc.update(payload.dict())
    return serialize(doc)

# DELETE — admin-only example of role-based authorization
@router.delete("/{note_id}", status_code=204)
async def delete_note(note_id: str, user: dict = Depends(require_role("admin"))):
    await notes_collection.delete_one({"_id": ObjectId(note_id)})

CORS matters here

Without CORSMiddleware, the browser blocks React (running on one origin, e.g. localhost:5173) from calling FastAPI (running on another, e.g. localhost:8000). This is the browser protecting users from sneaky cross-site requests — you have to explicitly allow your own frontend.

Frontend: a small API client that attaches the JWT

src/api.js
const BASE_URL = "http://localhost:8000";

export async function apiFetch(path, options = {}) {
  const token = localStorage.getItem("token");
  const res = await fetch(BASE_URL + path, {
    ...options,
    headers: {
      "Content-Type": "application/json",
      ...(token ? { Authorization: `Bearer ${token}` } : {}),
      ...options.headers,
    },
  });
  if (res.status === 401) {
    localStorage.removeItem("token");
    window.location.href = "/login";
  }
  if (!res.ok) throw new Error((await res.json()).detail || "Request failed");
  return res.status === 204 ? null : res.json();
}
Explain it like I'm in 7th grade

Every time React asks the backend for something, it slips the JWT "hall pass" into the request's Authorization header. If the pass has expired or is missing, the backend says "401, not allowed," and this helper automatically sends the user back to the login page.

Frontend: a tiny auth context (login state shared across the app)

src/AuthContext.jsx
import { createContext, useContext, useState } from "react";
import { apiFetch } from "./api";

const AuthContext = createContext(null);

export function AuthProvider({ children }) {
  const [token, setToken] = useState(localStorage.getItem("token"));

  async function login(email, password) {
    const form = new URLSearchParams();
    form.append("username", email);
    form.append("password", password);

    const res = await fetch("http://localhost:8000/auth/login", {
      method: "POST",
      headers: { "Content-Type": "application/x-www-form-urlencoded" },
      body: form,
    });
    if (!res.ok) throw new Error("Login failed");
    const data = await res.json();
    localStorage.setItem("token", data.access_token);
    setToken(data.access_token);
  }

  function logout() {
    localStorage.removeItem("token");
    setToken(null);
  }

  return (
    <AuthContext.Provider value={{ token, login, logout, isAuthed: !!token }}>
      {children}
    </AuthContext.Provider>
  );
}

export const useAuth = () => useContext(AuthContext);

Why the backend check still matters (defense in depth)

Never trust the frontend alone

A curious user can open dev tools, delete the JWT check in React's memory, or call the API directly with a tool like curl — completely bypassing your React app. That's why every single FastAPI route above independently re-checks get_current_user or require_role. The frontend route guard is for a smooth experience; the backend check is the actual lock on the door.

Station 14

Kafka Basics + FastAPI

The messaging backbone that lets bank microservices tell each other "this just happened" without calling one another directly.

Explain it like I'm in 7th grade

Imagine a school announcement system instead of one kid running to every classroom to deliver news by hand. Someone speaks into the microphone once — "assembly moved to 2pm" — and every classroom that's listening hears it, whenever they're ready to listen. Kafka is that announcement system for computers. A service doesn't call every other service one by one; it just announces an event once, and any service that cares can tune in.

Core vocabulary

Term7th-grade versionTechnical version
BrokerOne announcement speaker/serverA Kafka server that stores and serves messages
TopicA named channel, like "Sports News"A named stream of related events, e.g. transfers.completed
PartitionSeparate lines within one channel, so many people can listen at once without crowdingA topic is split into partitions for parallelism; order is guaranteed only within a partition
ProducerWhoever speaks into the microphoneAny service that publishes (writes) events to a topic
ConsumerWhoever is listeningAny service that reads events from a topic
Consumer GroupA study group sharing the listening job so no one hears the same announcement twiceConsumers in the same group split partitions between them — each message is processed once per group
OffsetA bookmark in the announcement recordingThe position of a consumer's "last read" message in a partition, so it can resume after a restart
RetentionHow long the recording stays available to replayHow long Kafka keeps messages on disk (e.g. 7 days) before deleting them, regardless of whether they were read

Architecture

Kafka in the bank system Transfers Service (producer) │ │ publish "transfer.completed" event ▼ ┌────────────────────────────────────────────┐ │ Kafka Topic: transfers.completed │ │ ┌───────────┐ ┌───────────┐ ┌───────────┐ │ │ │Partition 0│ │Partition 1│ │Partition 2│ │ │ └───────────┘ └───────────┘ └───────────┘ │ └────────────────────────────────────────────┘ │ │ ▼ ▼ Notification Service Fraud Service (consumer group "notif") (consumer group "fraud") → writes to MongoDB → runs a risk check (each group reads every message independently)

Two different consumer groups (Notification, Fraud) each get their own full copy of every event. Within one consumer group, work is split across partitions so multiple pod replicas can process messages in parallel without duplicating effort.

Why not just call the other service directly (REST)?

Direct REST callKafka event

FastAPI producer — publish an event when a transfer completes

kafka_client.py
import json
from aiokafka import AIOKafkaProducer

producer: AIOKafkaProducer | None = None

async def start_producer():
    global producer
    producer = AIOKafkaProducer(
        bootstrap_servers="kafka:9092",
        value_serializer=lambda v: json.dumps(v).encode("utf-8"),
    )
    await producer.start()

async def stop_producer():
    await producer.stop()

async def publish_event(topic: str, key: str, event: dict):
    await producer.send_and_wait(topic, value=event, key=key.encode("utf-8"))
main.py
from contextlib import asynccontextmanager
from fastapi import FastAPI
from kafka_client import start_producer, stop_producer, publish_event

@asynccontextmanager
async def lifespan(app: FastAPI):
    await start_producer()   # runs once, when the app starts
    yield
    await stop_producer()     # runs once, when the app shuts down

app = FastAPI(lifespan=lifespan)

@app.post("/transfers")
async def create_transfer(payload: TransferRequest):
    transfer = process_new_transfer(payload)
    await publish_event(
        topic="transfers.completed",
        key=transfer.id,                 # same key = same partition = kept in order
        event={"transfer_id": transfer.id, "amount": str(payload.amount),
               "from_account": payload.from_account, "to_account": payload.to_account},
    )
    return transfer
Connecting back to the Outbox Pattern (Station 05)

In production, don't publish to Kafka directly inside the request like above — publish from the Outbox worker instead, after the database transaction has safely committed. That way, a Kafka hiccup can never cause the transfer to succeed in the database but never get announced (or vice versa).

from aiokafka import AIOKafkaConsumer

async def consume_transfers():
    consumer = AIOKafkaConsumer(
        "transfers.completed",
        bootstrap_servers="kafka:9092",
        group_id="notification-service",     # consumer group: shares work, avoids duplicates
        value_deserializer=lambda v: json.loads(v.decode("utf-8")),
        auto_offset_reset="earliest",
        enable_auto_commit=False,             # commit manually, only after success

            try:

                logger.exception("Failed to process event, will retry")
                await asyncio.sleep(2)          # simple backoff before the next poll retries it
    finally:

Handling failures: retries and a dead-letter topic

Explain it like I'm in 7th grade

If a listener keeps mishearing the same announcement and it's clearly broken (not just noisy static), you don't want it stuck repeating that one announcement forever and never hearing new ones. Instead, you set the broken one aside in a "come back to this later" pile — a dead-letter topic — and move on to the next announcement.

MAX_RETRIES = 3

async def handle_with_retry(event: dict):
    for attempt in range(1, MAX_RETRIES + 1):
        try:
            return await handle_transfer_completed(event)
        except Exception:
            if attempt == MAX_RETRIES:
                await publish_event("transfers.completed.dlq", event.get("transfer_id", ""), event)
                return   # give up on this message, move on, don't block the whole partition
            await asyncio.sleep(2 ** attempt)   # exponential backoff: 2s, 4s, 8s

Ordering & idempotency, again

Two things to always assume with Kafka

Order is only guaranteed within a single partition, so always send events that must stay in order (like all events for one account) with the same partition key. At-least-once delivery means a consumer might see the same event twice after a retry or restart — so consumers should be idempotent, exactly like the transfer idempotency_key from the Bank Capstone station.

SettingWhat it controls
group_idWhich "team" this consumer belongs to — same group shares the work, different groups each get every message
auto_offset_resetWhere a brand-new consumer group starts reading: earliest (from the start) or latest (only new messages)
enable_auto_commitWhether offsets commit automatically (simpler, riskier) or manually after real success (safer)
Partition keyGuarantees all events with the same key land in the same partition, preserving their order
