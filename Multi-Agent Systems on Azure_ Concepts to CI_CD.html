Part 1

Concepts: how to build it safely

The analogy

Think of a restaurant

The orchestrator is the manager who takes your order. The agents are specialists: chef, cashier, delivery person. The manager talks to the customer, and the specialists talk to the manager. Each topic below maps to something that can go wrong in that restaurant.

1. Security: locking the doors

Treat one agent's output as untrusted input to the next, so a tricked agent can't trick all the others.

Who are you?Entra ID + Managed Identity, no passwords in codeID badges for staff

2. Guardrails: safety rails on a staircase

Add checks at four points.

Input

Block bad requests

Jailbreaks, hate, self-harm and PII, using Content Safety and Prompt Shields.

Tools

Approved tools only

Risky actions (refund, delete, send email) need human approval.

Output

Check the answer

Harmful content, leaked personal data, and groundedness (is it backed by documents?).

Budget

Set limits

Max steps, tokens and time, so an agent can't loop forever and burn money.

3. Responsible AI

Microsoft's principles: fairness, reliability and safety, privacy and security, inclusiveness, transparency, accountability.

  • Tell users they're talking to AI, and show sources or citations.
  • Keep a human in the loop for high-impact decisions.
  • Test for bias with different kinds of users.
  • Mask or avoid personal data (PII).
  • Log decisions so someone can be held accountable.
  • Red-team your own system before others do.

4. RAGAS: the exam for your AI

An automatic grader, like a teacher checking answers.

ScoreQuestion it answers
FaithfulnessDid the answer stick to the retrieved documents, or make things up?
Answer relevancyDid it actually answer the question?
Context precisionWere the retrieved documents the right ones?
Context recallDid it find all the needed documents?
Agent metricsTool call accuracy, agent goal accuracy, topic adherence
  • Build a golden dataset of 50 to 200 questions with correct answers.
  • Run RAGAS in CI/CD and block deployment if scores drop below a threshold.
  • In production, evaluate a sample (about 5%) of real conversations to save cost.
  • Evaluate each agent separately and the full system end to end. Azure AI Foundry's built-in evaluators can run alongside.

5. Circuit breaker: Agent B isn't responding

Like the fuse in your house: if something keeps failing, cut the connection so the whole house doesn't burn.

Timeout

  • Don't wait forever (say 10 seconds)

Retry with backoff

  • 1s, 2s, 4s plus jitter
  • Only 2 to 3 times

Circuit breaker

  • Closed: calls go through
  • Open: after ~5 failures, fail fast for 30s
  • Half-open: one test call decides

Fallback

  • Cached answer, backup agent, or a clear "temporarily unavailable"

Bulkhead

  • Each agent gets limited resources so a slow one can't hog everything

Async messaging

  • Service Bus queues hold messages while B is down
  • Repeated failures go to the dead-letter queue

Tools: Polly (.NET), tenacity or pybreaker (Python), API Management policies, Dapr resiliency on Container Apps.

6. Avoiding duplicate data to the consumer

Duplicates come from retries: A times out and retries, but B had already finished. Queues also deliver "at least once". The cure is to make everything idempotent: doing it twice has the same effect as once.

  • Give every request a unique idempotency key / correlation ID at the start.
  • Turn on Service Bus duplicate detection (uses MessageId within a time window).
  • Each agent records "I already processed ID X" in Cosmos DB or Redis and returns the saved result on a repeat.
  • Only the orchestrator talks to the consumer.
  • Use the outbox pattern: save the result and the "to send" message together, so nothing is sent twice or lost.
  • The consumer can also check the ID and ignore repeats.
if cache.exists(request_id):
    return cache.get(request_id)       # already done, don't repeat
result = agent_b.process(data)
cache.set(request_id, result, ttl=3600)
return result

7. What if I combine all agents into one?

Single agentMulti-agent
SimplicityEasy to build and debugMore complex
Cost and speedFewer model calls, less delayMore hops, more tokens
Many toolsConfused by a huge prompt and 30+ toolsEach agent has a focused job
SecurityOne agent holds all permissionsLeast privilege per agent
FailureSingle point of failureFailures can be isolated
ScalingScale everything togetherScale only the busy agent
Team workOne codebase everyone editsTeams own separate agents
Advice: start with one agent plus good tools. Split only when you see real problems: the prompt gets too long, tool selection goes wrong, or you need different permissions or scaling.

9. Traceability: CCTV for your AI

You must be able to answer "why did the AI say this to this user?"

  • Create a trace ID per user request and pass it through every agent.
  • Use OpenTelemetry (it has GenAI conventions) and send data to Application Insights. Foundry also has built-in tracing.
  • Record per step: agent, tool, prompt, response, token count, latency, model version, errors.
  • View the whole journey as a timeline in the Application Insights transaction view.
  • Redact PII before logging and set retention periods. Keep audit logs of who approved what.
  • Alert on error rate, latency, cost spikes and guardrail triggers.

10. Best cost approach

  1. Right-size the model. Small cheap models for routing and classification, big ones only for hard reasoning. This is the biggest saving.
  2. Fewer agent hops. Every extra agent means extra tokens.
  3. Short prompts. Trim history, summarize old turns, send only relevant chunks.
  4. Caching. Semantic caching with Redis, plus prompt caching.
  5. Limits. Max tokens, max steps, and API Management token-rate limits per user or agent.
  6. Pricing mode. Pay-as-you-go for unpredictable traffic, provisioned throughput (PTU) for steady high traffic, Batch API for non-urgent jobs.
  7. Scale to zero with Container Apps. Use Spot nodes on AKS for non-critical work.
  8. Visibility. Tag resources per agent or team, set budgets and alerts, track cost per request.
  9. Sample your evaluations instead of evaluating everything.

Part 2

Putting it into practice: LangGraph on Azure with CI/CD

What gets deployed

Each piece has one job, and no passwords are stored in code.

Hosting

Azure Container Apps

Runs the container, scales 1 to 5 replicas on HTTP load, uses health probes before shifting traffic.

State

Postgres checkpointer

LangGraph saves each conversation by thread_id, so replicas share state and restarts lose nothing.

Identity

Managed identity

Logs in to Azure OpenAI and pulls images from the registry without keys.

Images

Container Registry

Each build is tagged with the commit SHA, so every release is traceable and rollback is easy.

Infra

Bicep

Logs, App Insights, registry, identity, environment and app are all defined as code.

Tracing

Application Insights

OpenTelemetry sends traces of every request and model call. A step limit stops runaway agent loops.

Project structure

Both pipelines reuse the same app, Dockerfile and Bicep file.

Pipeline flow

Pull requests only run stage 1. Pushes to main run everything.

Lint and test

  • Install dependencies
  • ruff lint
  • pytest

Deploy staging

  • Bicep infrastructure
  • Build and push image
  • Roll out new revision
  • Smoke test /health
  • RAGAS quality gate

Approval

  • A person approves on the production Environment

Deploy production

  • Same steps as staging
  • No eval gate (already passed)

Container Apps only moves traffic to the new revision after it passes health probes, so deploys cause no downtime. Roll back by pointing traffic at the previous revision.

azure-pipelines.yml

The entry point. The deploy steps live once in templates/deploy-stage.yml.

trigger:
  branches:
    include: [main]

pr:
  branches:
    include: [main]

pool:
  vmImage: ubuntu-latest

stages:
  - stage: Test
    displayName: Lint and test
    jobs:
      - job: test
        steps:
          - task: UsePythonVersion@0
            inputs:
              versionSpec: "3.12"
          - script: pip install -r requirements.txt ruff pytest
          - script: ruff check .
          - script: pytest -q || [ $? -eq 5 ]   # 5 = no tests yet

  - template: templates/deploy-stage.yml
    parameters:
      environment: staging
      serviceConnection: sc-langgraph-staging
      dependsOn: [Test]

  - template: templates/deploy-stage.yml
    parameters:
      environment: production
      serviceConnection: sc-langgraph-production
      dependsOn: [Deploy_staging]

What the deploy template does

Each step is an AzureCLI@2 task that logs in through the service connection.

StepWhat happens
Deploy infrastructureRuns az deployment group create with infra/main.bicep. Reuses the current image so redeploying infra never resets the app.
Build and push imageFinds the registry, builds with Docker, pushes lg-agents:<commit SHA>.
Roll out new revisionaz containerapp update --image creates the new revision.
Smoke testCalls /health up to six times, 10 seconds apart. Fails the stage if it never answers.
Quality gateStaging only. Runs evals/run_ragas.py against the live URL and fails below the faithfulness threshold.

One-time setup in Azure DevOps

Do these once before the first run.

  1. Create two Azure Resource Manager service connections, sc-langgraph-staging and sc-langgraph-production, using workload identity federation. Give each Contributor on its resource group plus permission to create role assignments.
  2. Create variable groups langgraph-staging and langgraph-production with RESOURCE_GROUP, AOAI_ENDPOINT, AOAI_DEPLOYMENT and a secret DATABASE_URL (better: link to Key Vault).
  3. Under Pipelines → Environments, create staging and production. Add Approvals and checks on production.
  4. Create the pipeline from azure-pipelines.yml and add it as build validation on the main branch policy.
  5. Create Azure OpenAI and Postgres Flexible Server. After the first deploy, give the app's managed identity the Cognitive Services OpenAI User role on the OpenAI resource (the Bicep output identityPrincipalId has its ID).
  6. Write evals/run_ragas.py: call the staging URL with your golden dataset and exit non-zero if scores fall below the threshold.

Things to know

Honest caveats from building this starter.

Untested end to end. The files haven't been run against a real subscription, so expect small fixes on the first run.

First deploy may fail once

The registry role assignment can take a moment to propagate. Re-run the pipeline.

Secrets need mapping

Azure DevOps doesn't pass secret variables to scripts automatically, so DATABASE_URL is mapped through env:.

Use Key Vault in production

The Bicep file stores the database URL as a Container Apps secret. Switch to a Key Vault reference for production.

Add API Management

Ingress is external for simplicity. For a hardened setup, make it internal and put API Management in front.

Pin dependencies

requirements.txt is unpinned. Pin versions before production.

Canary rollout

Production uses single-revision mode. For a 10% canary, use multiple-revision mode with traffic weights.
