2. OOP — But at Principal Level

The four classical concepts are:

EncapsulationProtect object invariants and implementation details.
AbstractionExpose what callers need without exposing unnecessary implementation.
InheritanceReuse/extend behavior where the relationship is stable and genuinely “is-a”.
PolymorphismProgram against abstractions and allow implementations to vary.

At your level, pay particular attention to composition, immutability, dependency inversion, separation of concerns, domain modeling, loose coupling and high cohesion.

3. Composition vs Inheritance

Consider a banking system. Deep inheritance can become brittle as business rules evolve.

class BankAccount {}

class SavingsAccount extends BankAccount {}

class PremiumSavingsAccount extends SavingsAccount {}

class InternationalPremiumSavingsAccount
        extends PremiumSavingsAccount {}

Prefer composition when behavior changes independently:

class Account {

    private AccountType type;
    private InterestPolicy interestPolicy;
    private WithdrawalPolicy withdrawalPolicy;
}
Account | ┌───────────────┼────────────────┐ ↓ ↓ ↓ InterestPolicy WithdrawalPolicy FeePolicy ↓ ↓ ↓ SavingsPolicy PremiumPolicy InternationalPolicy
Interview answer: Inheritance creates strong coupling between a parent/child hierarchy. In enterprise systems where business rules evolve frequently, composition provides more flexibility because behavior can change independently. Use inheritance where there is a genuine and stable “is-a” relationship.

4. SOLID in a Real Banking System

A single service that validates payments, performs fraud checks, persists data, sends email, publishes events and generates reports has too many responsibilities.

PaymentService | ├── PaymentValidator ├── FraudService ├── PaymentRepository ├── EventPublisher └── NotificationService
class PaymentService {

    private final PaymentValidator validator;
    private final FraudService fraudService;
    private final PaymentRepository repository;
    private final EventPublisher eventPublisher;

    public PaymentResponse process(PaymentRequest request) {

        validator.validate(request);

        fraudService.check(request);

        Payment payment = repository.save(
            createPayment(request)
        );

        eventPublisher.publish(
            new PaymentCreatedEvent(payment.getId())
        );

        return PaymentResponse.from(payment);
    }
}

5. Immutability

Immutable objects are easier to reason about and safely share between threads.

public final class Customer {

    private final String id;
    private final String name;

    public Customer(String id, String name) {
        this.id = id;
        this.name = name;
    }

    public String getId() { return id; }
    public String getName() { return name; }
}

For simple immutable data carriers, Java records are concise:

public record Customer(
    String id,
    String name
) {}
Thread safetyLess shared mutable state.
PredictabilityState cannot change unexpectedly.
CachingStable values are easier to cache.
Safe sharingMultiple threads can safely reuse immutable values.

6. Java Memory Model

Thread | ├── Program Counter ├── Stack └── Local Variables Shared Memory | └── Heap

Multiple threads accessing shared state create the possibility of race conditions, visibility problems, atomicity problems and instruction reordering concerns.

7. Race Condition

class Counter {

    private int count = 0;

    public void increment() {
        count++;
    }
}

count++ is effectively a read → add → write sequence. Two threads can read the same old value and overwrite each other's update.

Thread A Thread B READ 10 READ 10 ADD 1 ADD 1 WRITE 11 WRITE 11 Expected: 12 Actual: 11

Possible fixes include synchronization or atomic classes:

public synchronized void increment() {
    count++;
}
private final AtomicInteger count =
    new AtomicInteger();

public void increment() {
    count.incrementAndGet();
}
Principal discussion: Choose based on contention, operation complexity, scalability, lock granularity and whether multiple variables must change atomically.

8. volatile

volatile provides visibility guarantees for reads/writes between threads, but it does not make compound operations such as count++ atomic.

private volatile boolean running = true;

while (running) {
    process();
}

A second thread can set running = false, and the volatile declaration helps ensure the worker observes the update.

9. synchronized vs Lock

public synchronized void process() {
    // critical section
}
private final Lock lock =
    new ReentrantLock();

public void process() {
    lock.lock();
    try {
        // critical section
    } finally {
        lock.unlock();
    }
}

ReentrantLock offers features such as tryLock(), timed acquisition and interruptible locking. Use the simplest synchronization primitive that satisfies correctness and performance requirements.

10. Deadlock

Thread A: Lock A ↓ wait for Lock B Thread B: Lock B ↓ wait for Lock A

Typical mitigations:

  • Consistent lock ordering
  • Timeouts and tryLock()
  • Reducing lock scope
  • Avoiding unnecessary nested locks

11. Producer-Consumer

Producer | ↓ BlockingQueue | ↓ Consumer
BlockingQueue<Order> queue =
    new ArrayBlockingQueue<>(1000);

queue.put(order);

Order order = queue.take();

The queue provides a form of backpressure. If consumers cannot keep up, the bounded queue prevents unlimited memory growth.

12. ExecutorService

Avoid creating a new platform thread for every unit of work.

ExecutorService executor =
    Executors.newFixedThreadPool(20);

executor.submit(() -> process());

A 1,000-thread pool is not automatically better. Excessive threads can cause context switching, memory consumption, CPU contention, thread starvation and latency spikes.

13. CompletableFuture

For independent downstream calls, parallel execution can reduce end-to-end latency.

CompletableFuture<Account> account =
    CompletableFuture.supplyAsync(
        () -> accountService.get(customerId)
    );

CompletableFuture<Credit> credit =
    CompletableFuture.supplyAsync(
        () -> creditService.get(customerId)
    );

CompletableFuture<Rewards> rewards =
    CompletableFuture.supplyAsync(
        () -> rewardService.get(customerId)
    );

CompletableFuture.allOf(
    account,
    credit,
    rewards
).join();
Production concerns: timeout, exception handling, cancellation, executor selection, circuit breakers and metrics.

Be careful with blocking I/O on the common ForkJoinPool. A dedicated, appropriately sized executor may be more suitable.

14. Virtual Threads

Traditional: Request ↓ Platform Thread ↓ Blocking I/O ↓ Thread remains occupied Virtual Thread: Request ↓ Virtual Thread ↓ Blocking I/O ↓ Carrier thread can execute other work

Virtual threads are especially useful for high-concurrency workloads dominated by blocking I/O. They do not remove database connection limits, downstream service capacity limits or CPU constraints.

Principal insight: A virtual thread can reduce thread-management overhead, but it cannot fix poor architecture or an overloaded dependency.

18. Production Incident Question

Scenario

Your Java API suddenly reaches 95% CPU in production. What do you do?

Strong investigation sequence

  1. Confirm scope and affected instances.
  2. Check traffic and request rate.
  3. Check recent deployments/configuration changes.
  4. Inspect CPU by process/thread.
  5. Take thread dumps.
  6. Check GC and heap behavior.
  7. Inspect database and downstream calls.
  8. Identify root cause.

Possible immediate mitigations

  • Scale out when appropriate.
  • Rollback a problematic deployment.
  • Rate-limit an abnormal traffic source.
  • Disable a problematic feature behind a feature flag.

Permanent correction

  • Code optimization
  • Query optimization
  • Concurrency correction
  • Capacity adjustment
  • Better test coverage
  • Improved monitoring and alerting

19. HashMap Interview Drill

When you execute:

map.put("CUSTOMER123", customer);
CUSTOMER123 ↓ hashCode() ↓ hash spreading ↓ bucket index ↓ existing entry? ↓ ┌────┴────┐ No Yes ↓ ↓ Insert Compare ↓ equals()

Average lookup is generally O(1) under a reasonable hash distribution. Collision-heavy buckets can change behavior; modern Java implementations can treeify sufficiently collision-heavy buckets under appropriate conditions.

20. equals() and hashCode()

If:

a.equals(b) == true

then:

a.hashCode() == b.hashCode()

must also hold. Violating this contract can break expected behavior in HashMap, HashSet and other hash-based collections.

Interview question: What happens if you override equals but not hashCode? Equal objects may produce different hash codes, causing lookups or duplicate detection to behave incorrectly.

21. String Immutability

String immutability supports security, thread safety, pooling and predictable hashing.

String s = "ABC";
s = s + "DEF";

A new String is created rather than modifying the original.

For repeated mutation, use StringBuilder in typical single-threaded code. StringBuffer is synchronized and is generally a legacy choice unless that synchronization behavior is specifically needed.

22. Exception Handling

Avoid swallowing failures:

try {
    process();
} catch (Exception e) {
    e.printStackTrace();
}

Enterprise applications should provide meaningful exception types, structured logging, correlation IDs, error codes, proper propagation and centralized handling.

In Spring, @RestControllerAdvice is useful for consistent API error handling.

Checked vs unchecked: Avoid dogmatic answers. Choose based on whether callers are expected to recover, the application error model and whether forcing every layer to catch an exception adds useful semantics or merely noise.

24. Strategy Pattern — Banking Example

Instead of a growing conditional block:

if (type == CARD) {
   ...
} else if (type == UPI) {
   ...
} else if (type == NEFT) {
   ...
}

Define a stable abstraction:

interface PaymentStrategy {

    PaymentResult process(
        PaymentRequest request
    );
}
PaymentService | ↓ PaymentStrategy | ┌────┼─────┬─────┐ ↓ ↓ ↓ ↓ Card UPI NEFT RTGS

This makes new payment strategies easier to add without continually modifying the core service.

25. Factory Pattern

class PaymentStrategyFactory {

    PaymentStrategy get(PaymentType type) {

        return switch (type) {
            case CARD -> cardStrategy;
            case UPI -> upiStrategy;
            case NEFT -> neftStrategy;
            case RTGS -> rtgsStrategy;
        };
    }
}

26. Builder Pattern

Useful for objects with many optional parameters:

Payment payment =
    Payment.builder()
        .customerId(customerId)
        .amount(amount)
        .currency("INR")
        .channel("UPI")
        .build();

This is generally clearer than a constructor with a long list of positional parameters.

Exercise 1 — Thread-Safe Rate Limiter

Requirement: a customer can make 100 requests per minute.

Request ↓ RateLimiter ↓ Redis ↓ Allowed? ┌─┴─┐ Yes No ↓ ↓ API Reject

Know the trade-offs among Fixed Window, Sliding Window, Token Bucket and Leaky Bucket. In a distributed deployment, explain why an in-memory counter is insufficient across multiple application instances.

Exercise 2 — LRU Cache

Requirements: capacity 1,000; GET O(1); PUT O(1); thread-safe.

HashMap | ↓ Node ↔ Node ↔ Node

Use a HashMap for lookup and a doubly linked list for recency ordering. Then discuss concurrency and eviction semantics.

Exercise 3 — Retry with Exponential Backoff

Attempt 1 → immediate Attempt 2 → 100 ms Attempt 3 → 200 ms Attempt 4 → 400 ms Attempt 5 → 800 ms

Production implementation should consider maximum retries, maximum delay, jitter, retryable/non-retryable errors, timeout, circuit breaker and idempotency.

Important: Retry storms.

1,000 requests × 3 retries can create 3,000 additional calls against an already unhealthy dependency. Use exponential backoff, jitter, circuit breakers, retry budgets, timeouts, bulkheads and rate limiting.

31.38 Production Incident — AKS API Latency Spike

Scenario

At 10:05 AM, p99 latency for a Spring Boot payment API jumps from 250 ms to 4 seconds. CPU is 80%, pods are healthy, and there has been no application deployment.

What do you investigate?

Strong investigation path

  1. Check traffic volume and request distribution.
  2. Compare p50, p95 and p99 to identify tail-only vs broad degradation.
  3. Inspect distributed traces for the slowest span.
  4. Check database latency, connection pool utilization and lock waits.
  5. Check downstream service latency.
  6. Check GC, CPU throttling and memory pressure.
  7. Check node health and network telemetry.
  8. Check cache hit ratio and hot keys.
  9. Check message/queue lag if asynchronous dependencies exist.
  10. Compare infrastructure and business metrics against the incident start time.
  11. Mitigate first if customer impact is severe; root-cause second.
Principal behavior: Separate mitigation from diagnosis. Scaling out may reduce impact, but it does not prove CPU was the root cause.

34.1 Java Core — Q&A

Q1. Explain the Java Memory Model and why it matters in concurrent systems.

60-second answer: The Java Memory Model defines how threads interact through memory, including visibility, ordering and atomicity guarantees. Without proper synchronization, one thread may not observe another thread's updates reliably. volatile provides visibility and ordering guarantees for a variable, while locks and atomic classes provide stronger coordination for compound operations.

Principal deep dive: I reason about shared state first, then choose the smallest synchronization mechanism that gives the required correctness. I avoid assuming that visibility implies atomicity. For example, count++ is not made atomic merely because count is volatile.

private final AtomicInteger counter = new AtomicInteger();

public int increment() {
    return counter.incrementAndGet();
}

Follow-up: Why not use synchronized everywhere? Because synchronization has a coordination cost and can reduce concurrency. The goal is correctness first, then measured optimization.

Q2. HashMap vs ConcurrentHashMap?

Answer: HashMap is not safe for concurrent structural modification. ConcurrentHashMap provides thread-safe concurrent access with significantly better concurrency than synchronizing the entire map. It is appropriate for shared mutable maps when compound operations can be expressed through atomic APIs such as computeIfAbsent.

ConcurrentHashMap<String, User> cache = new ConcurrentHashMap<>();

User user = cache.computeIfAbsent(
    userId,
    id -> loadUser(id)
);

Principal consideration: Thread-safe collection operations do not automatically make a multi-step business workflow atomic. The business transaction may still require explicit coordination.

Q3. Explain equals() and hashCode().

Answer: If two objects are equal according to equals(), they must return the same hashCode(). Violating this contract can make objects behave incorrectly in hash-based collections.

public record CustomerId(String value) {}

Map<CustomerId, Customer> customers = new HashMap<>();

For entities, be particularly careful when identifiers are assigned after persistence. Equality semantics should match the domain model.

Q4. Explain immutability and why Principal Engineers prefer it in concurrent systems.

Answer: Immutable objects cannot change after construction. They are easier to reason about, naturally safer to share between threads and reduce synchronization requirements.

public record Money(BigDecimal amount, Currency currency) {
    public Money {
        Objects.requireNonNull(amount);
        Objects.requireNonNull(currency);
    }
}

Q5. Explain JVM memory and garbage collection at a high level.

Answer: Java applications allocate objects primarily on the heap, while each thread has its own stack. Garbage collectors reclaim objects that are no longer reachable. In production I monitor allocation rate, heap occupancy, GC pause behavior, CPU and application latency rather than tuning blindly.

Principal answer: GC is an operational concern. A latency-sensitive service needs an explicit latency budget and evidence-based tuning. If the application creates excessive temporary objects, increasing the heap may only postpone the underlying problem.

34.2 Object-Oriented Design — Q&A

Q6. SOLID principles in a real enterprise system?

Answer: SOLID is useful when it reduces coupling and improves changeability, not when applied mechanically.

  • S: One reason to change.
  • O: Extend behavior without repeatedly modifying stable code.
  • L: Subtypes preserve expected behavior.
  • I: Prefer focused interfaces.
  • D: Depend on abstractions rather than concrete implementation details.
public interface PaymentGateway {
    PaymentResult charge(Money amount);
}

public final class PaymentService {
    private final PaymentGateway gateway;

    public PaymentService(PaymentGateway gateway) {
        this.gateway = gateway;
    }
}

Q7. Composition vs inheritance?

Answer: Prefer composition when behavior varies independently or when inheritance would create tight coupling. Inheritance is appropriate when there is a genuine substitutable type relationship and the base abstraction has stable semantics.

Q10. Explain @Transactional.

Answer: Spring typically uses a proxy around the transactional component. The proxy starts/joins a transaction before method execution and commits or rolls back according to transaction rules.

@Transactional
public PaymentResponse transfer(TransferRequest request) {
    debit(request.from());
    credit(request.to());
    return PaymentResponse.success();
}

Important: @Transactional does not automatically make external HTTP calls transactional. Database transactions and distributed operations must be designed separately.

Q11. Why can self-invocation break Spring proxy behavior?

Answer: A method calling another method on the same object may bypass the proxy, so proxy-based annotations such as @Transactional or certain aspects may not be applied to the internal call.

Solution: Move the transactional boundary to another bean or redesign the service boundary instead of depending on self-proxy tricks.

Q16. How do you make REST APIs idempotent?

Answer: Use an idempotency key or business identifier and persist the result associated with the request. Repeated requests return the original outcome instead of creating duplicate business effects.

@PostMapping("/payments")
public PaymentResponse create(
        @RequestHeader("Idempotency-Key") String key,
        @RequestBody PaymentRequest request) {
    return paymentService.processIdempotently(key, request);
}

Q17. Explain circuit breaker, timeout and retry.

Answer: A timeout prevents indefinite waiting. A retry handles transient failures. A circuit breaker prevents repeated calls to an unhealthy dependency. They work together, but retries must be bounded and carefully applied.

@CircuitBreaker(name = "fraudService", fallbackMethod = "fallback")
@Retry(name = "fraudService")
@TimeLimiter(name = "fraudService")
public CompletableFuture<FraudResult> check(FraudRequest request) {
    return client.check(request);
}

Warning: Blind retries can amplify an outage. Use exponential backoff, jitter and retry budgets.

34.5 Distributed Systems — Q&A

Q18. Explain CAP theorem.

Answer: When a network partition occurs, a distributed system must choose between stronger consistency and availability for the affected operation path. CAP is about partitioned distributed systems; it does not mean a system can simply “pick two” under all circumstances.

Q19. Explain eventual consistency.

Answer: Replicas may temporarily disagree but converge when updates propagate successfully. The design must define which operations require strong consistency and which can tolerate stale reads.

Example: A product catalog view may tolerate seconds of staleness; a payment authorization balance may require much stronger guarantees.

Q20. How do you design distributed transactions?

Answer: Prefer local transactions combined with explicit workflow patterns such as Saga and transactional outbox. Avoid distributed two-phase commit unless the business and infrastructure genuinely require it and the operational cost is understood.

Order DB Transaction ↓ Transactional Outbox ↓ Event Bus ↓ Payment ↓ Inventory ↓ Shipment

Q21. Explain the transactional outbox.

@Transactional
public void createOrder(Order order) {
    orderRepository.save(order);

    outboxRepository.save(
        OutboxEvent.of(
            "OrderCreated",
            order.id()
        )
    );
}

A separate publisher reads the outbox and publishes the event. This avoids the classic failure where the database commits but event publication fails.

Q22. How do you make event consumers idempotent?

@Transactional
public void consume(PaymentCompleted event) {

    if (processedEventRepository.existsById(event.id())) {
        return;
    }

    updateCustomerBalance(event);

    processedEventRepository.save(
        ProcessedEvent.of(event.id())
    );
}

Use a unique event ID or business idempotency key and enforce uniqueness at the database level.

Q23. How do you handle distributed caching?

Answer: Define cache ownership, TTL, invalidation, stale-data tolerance and failure behavior. Redis can be used for shared caching, but the database remains the source of truth unless the architecture explicitly says otherwise.

@Cacheable(cacheNames = "customers", key = "#id")
public Customer getCustomer(String id) {
    return repository.findById(id).orElseThrow();
}

Q24. How do you design rate limiting?

Answer: Token bucket is a useful model for controlling sustained rate while permitting limited bursts.

tokens = min(capacity,
             tokens + elapsedTime * refillRate)

if tokens >= cost:
    tokens -= cost
    allow()
else:
    reject()

For distributed APIs, store shared state in a suitable low-latency system such as Redis or use a gateway/provider capability.

Q25. How do you design for failure?

  • Timeout every remote call.
  • Bound retries.
  • Use circuit breakers where appropriate.
  • Use bulkheads to isolate resources.
  • Make operations idempotent.
  • Provide graceful degradation.
  • Use queues for buffering where appropriate.
  • Monitor saturation.
  • Define recovery procedures.

public final class ToolPolicy {

    public boolean allowed(
            String principal,
            String tool,
            Map<String, Object> args) {

        if ("production.deploy".equals(tool)) {
            return hasRole(principal, "RELEASE_APPROVER");
        }

        if ("repository.read".equals(tool)) {
            return true;
        }

        return false;
    }
}
public ToolResult execute(
        String principal,
        ToolRequest request) {

    if (!policy.allowed(
            principal,
            request.name(),
            request.arguments())) {
        throw new AccessDeniedException(
            "Tool not authorized"
        );
    }

    validateSchema(request);
    audit(request);

    return toolRegistry
        .get(request.name())
        .execute(request.arguments());
}

36.1 What Is Software?

Software is simply a set of instructions that tells a computer what to do.

Human Problem ↓ Rules / Instructions ↓ Program ↓ Computer ↓ Result

Example: A banking application receives “transfer ₹1,000 from A to B”. The software checks the user, checks the balance, records the transaction and returns the result.

36.2 What Is a Programming Language?

A programming language is a structured way for humans to write instructions that a computer can execute.

public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello!");
    }
}

Java is popular in large organizations because it has a mature ecosystem, strong tooling, good performance and a large enterprise community.

36.3 What Is Java?

Java lets us write application code once and run it on systems that have a compatible Java runtime.

Java Source Code ↓ Java Compiler ↓ Bytecode (.class) ↓ JVM ↓ Operating System / Hardware

37. SOLID + Design Patterns — Complete Zero-to-Hero Java Guide

Every principle and pattern in this module follows the same learning sequence: simple meaning → real-world analogy → bad design → improved design → Java implementation → when to use → when not to use → interview question → exercise.

Important: Design patterns are not rules that must be applied everywhere. A pattern is a reusable way of solving a recurring design problem. The best design is often the simplest design that meets the requirements.

37.1 SOLID Overview

37.2 S — Single Responsibility Principle

Simple meaning: A class should have one primary responsibility and therefore one main reason to change.

Analogy: In a restaurant, the chef cooks, the cashier handles payment and the delivery person delivers. One person doing everything becomes difficult to manage as the restaurant grows.

Bad Code

class Invoice {

    void calculateTotal() {
        // calculate price
    }

    void saveToDatabase() {
        // database code
    }

    void printInvoice() {
        // printing code
    }

    void sendEmail() {
        // email code
    }
}

This class has several unrelated responsibilities. Database technology, printing and email changes can all force changes to the same class.

Better Code

class InvoiceCalculator {
    BigDecimal calculate(Invoice invoice) {
        return invoice.items().stream()
            .map(Item::price)
            .reduce(BigDecimal.ZERO, BigDecimal::add);
    }
}

class InvoiceRepository {
    void save(Invoice invoice) {
        // database implementation
    }
}

class InvoicePrinter {
    void print(Invoice invoice) {
        // printing implementation
    }
}

class InvoiceMailer {
    void send(Invoice invoice) {
        // email implementation
    }
}

When to use

Use SRP when a class is accumulating unrelated business, infrastructure and presentation responsibilities or becomes difficult to test.

Do not misunderstand SRP

SRP does not mean “one method per class”. A class can contain several methods belonging to one cohesive responsibility.

Interview Question

Q: How do you identify an SRP violation?

A: Look for multiple unrelated reasons for change, mixed abstraction levels, excessive dependencies and tests that need to set up unrelated infrastructure.

Exercise

Refactor a UserService that validates users, writes SQL, sends email, generates PDF and logs audit events into cohesive components.

37.3 O — Open/Closed Principle

Simple meaning: Stable business logic should be open to new behavior through extension points but should not require repeated modification for every new variation.

Analogy: A power socket can support many compatible devices without rebuilding the house every time you buy a new appliance.

Bad Code

class PaymentService {

    void pay(String type, BigDecimal amount) {

        if (type.equals("CARD")) {
            // card payment
        } else if (type.equals("UPI")) {
            // UPI payment
        } else if (type.equals("BANK")) {
            // bank transfer
        }
    }
}

Better Code

interface PaymentMethod {
    void pay(BigDecimal amount);
}

class CardPayment implements PaymentMethod {
    public void pay(BigDecimal amount) {
        System.out.println("Card payment: " + amount);
    }
}

class UpiPayment implements PaymentMethod {
    public void pay(BigDecimal amount) {
        System.out.println("UPI payment: " + amount);
    }
}

class PaymentService {

    private final PaymentMethod method;

    PaymentService(PaymentMethod method) {
        this.method = method;
    }

    void pay(BigDecimal amount) {
        method.pay(amount);
    }
}

Production version

@Service
class PaymentService {

    private final Map<String, PaymentMethod> methods;

    PaymentService(List<PaymentMethod> implementations) {
        this.methods = implementations.stream()
            .collect(Collectors.toMap(
                PaymentMethod::type,
                Function.identity()
            ));
    }

    void pay(String type, BigDecimal amount) {
        PaymentMethod method = methods.get(type);

        if (method == null) {
            throw new IllegalArgumentException(
                "Unsupported payment type"
            );
        }

        method.pay(amount);
    }
}

Interview Question

Q: Is OCP the same as never modifying code?

A: No. The principle means designing stable areas so foreseeable variations can be added through appropriate abstractions instead of creating repeated conditional modifications.

37.4 L — Liskov Substitution Principle

Simple meaning: If code expects a parent abstraction, every valid subtype should behave in a way that does not violate the expectations of that abstraction.

Classic analogy: If a program expects a bird that can fly, making a penguin subtype of that specific “flying bird” abstraction creates a behavioral problem.

Bad Code

class Bird {
    void fly() {
        System.out.println("Flying");
    }
}

class Penguin extends Bird {
    @Override
    void fly() {
        throw new UnsupportedOperationException();
    }
}

Code using Bird reasonably expects fly() to work, but the subtype breaks that expectation.

Better Code

interface Bird {
    void move();
}

interface FlyingBird extends Bird {
    void fly();
}

class Eagle implements FlyingBird {
    public void move() {
        fly();
    }

    public void fly() {
        System.out.println("Flying");
    }
}

class Penguin implements Bird {
    public void move() {
        System.out.println("Walking/swimming");
    }
}

Enterprise Example

Do not create an abstraction such as DatabaseRepository that promises transactions, joins and relational semantics if one implementation is a document database that cannot preserve those guarantees.

Interview Question

Q: How do you detect an LSP violation?

A: Look for subtype methods throwing “not supported”, surprising state changes, stronger preconditions, weaker postconditions or callers needing explicit subtype checks.

37.5 I — Interface Segregation Principle

Simple meaning: Clients should not be forced to depend on methods they do not use.

Analogy: A driving licence should not require a taxi driver to learn unrelated aircraft controls.

Bad Code

interface Machine {
    void print();
    void scan();
    void fax();
}

class SimplePrinter implements Machine {

    public void print() {
        System.out.println("Printing");
    }

    public void scan() {
        throw new UnsupportedOperationException();
    }

    public void fax() {
        throw new UnsupportedOperationException();
    }
}

Better Code

interface Printer {
    void print();
}

interface Scanner {
    void scan();
}

interface Fax {
    void fax();
}

class SimplePrinter implements Printer {
    public void print() {
        System.out.println("Printing");
    }
}

class OfficeMachine
        implements Printer, Scanner, Fax {

    public void print() {}
    public void scan() {}
    public void fax() {}
}

Spring Boot example

interface CustomerReader {
    Customer findById(Long id);
}

interface CustomerWriter {
    Customer save(Customer customer);
}

A read-only service does not need to depend on write operations.

37.6 D — Dependency Inversion Principle

Simple meaning: Business logic should depend on abstractions. Infrastructure details should implement those abstractions.

Analogy: A phone charger follows a standard connector. The phone does not need to know the internal wiring of the electricity company.

Bad Code

class OrderService {

    private final MySqlOrderRepository repository =
        new MySqlOrderRepository();

    void create(Order order) {
        repository.save(order);
    }
}

Better Code

interface OrderRepository {
    void save(Order order);
}

class OrderService {

    private final OrderRepository repository;

    OrderService(OrderRepository repository) {
        this.repository = repository;
    }

    void create(Order order) {
        repository.save(order);
    }
}

class MySqlOrderRepository
        implements OrderRepository {

    public void save(Order order) {
        // MySQL implementation
    }
}

Why Spring loves DIP

Spring's dependency injection container can provide implementations of interfaces, allowing business code to remain independent of infrastructure details.

            PaymentGateway gateway,
            PaymentRepository repository,
            FraudChecker fraudChecker) {

        this.gateway = gateway;
        this.repository = repository;
        this.fraudChecker = fraudChecker;
    }

    PaymentResult pay(Payment payment) {

        FraudResult fraud =
            fraudChecker.check(payment);

        if (fraud.isRejected()) {
            return PaymentResult.rejected();
        }

        PaymentResult result =
            gateway.charge(payment.money());

        repository.save(payment);

        return result;
    }
}

This example demonstrates SRP, OCP, LSP, ISP and DIP together through focused abstractions.

Pattern 1 — Singleton

Pattern 2 — Factory Method

Problem: Create objects without forcing callers to know concrete implementation details.

    void send(String message);
}

    public void send(String message) {

            case "EMAIL" -> new EmailNotification();
            case "SMS" -> new SmsNotification();

}

37.11 Behavioral Patterns

Pattern 13 — Strategy

Problem: Select one of several algorithms or business rules.

interface PricingStrategy {
    BigDecimal price(Order order);
}

    public BigDecimal price(Order order) {
        return order.total();
    }
}

            .multiply(new BigDecimal("0.90"));

Use: Pricing, tax, fraud rules, routing, authentication providers.

Pattern 14 — Observer

Problem: Notify multiple interested components when something changes.

interface OrderListener {
    void orderCreated(Order order);
}

class EmailListener implements OrderListener {
    public void orderCreated(Order order) {
        System.out.println("Send email");

}

class OrderPublisher {

        listeners.add(listener);

In distributed systems, the event-bus version of this idea decouples services more strongly.

Pattern 15 — Command

Pattern 16 — Chain of Responsibility

Problem: Pass a request through a sequence of handlers until it is processed or rejected.

interface Handler {
    void handle(Request request);
}

class AuthenticationHandler implements Handler {

    private Handler next;

    public void handle(Request request) {

        if (!request.authenticated()) {
            throw new SecurityException();
        }

        if (next != null) {
            next.handle(request);
        }
    }

    void next(Handler next) {
        this.next = next;
    }
}

Spring example: Servlet filters and security filter chains use similar ideas.

Pattern 17 — State

Problem: An object's behavior changes according to its current state.

enum OrderState {
    CREATED,
    PAID,
    SHIPPED,
    CANCELLED
}

class Order {

    private OrderState state = OrderState.CREATED;

    void pay() {
        if (state != OrderState.CREATED) {
            throw new IllegalStateException();
        }
        state = OrderState.PAID;
    }

    void ship() {
        if (state != OrderState.PAID) {
            throw new IllegalStateException();
        }
        state = OrderState.SHIPPED;
    }
}

For complex workflows, explicit state-machine modeling can be clearer than scattered conditionals.

Pattern 20 — Mediator

Problem: Reduce direct dependencies between many interacting objects by centralizing coordination.

class ChatMediator {

37.16 Pattern Anti-Patterns

  • Inheritance for reuse: Using inheritance where composition is safer.

Interview: What is an LLM?

38.3 Token Optimization — How to Save LLM / Copilot Costs

Layman explanation: Tokens are like the number of words a taxi carries. If you send unnecessary passengers every time, every trip becomes expensive. Send only what the model needs.

Bad Design

Huge system prompt + Entire chat history + Entire source repository + All documents + All tool definitions ↓ LLM ↓ High token cost + latency

Optimized Design

Small stable instructions + Relevant context + Compressed history + Only required tools + Cached repeated context ↓ Model Router ├── Small model → simple work └── Large model → difficult work

Practical Token-Saving Techniques

  1. Prompt compression: remove repeated prose and unnecessary examples.
  2. Context selection: retrieve only relevant documents/code.
  3. Conversation summarization: replace old conversation with a compact state summary.
  4. Tool selection: expose only tools needed for the current task.
  5. Output limits: constrain maximum output when a short answer is enough.
  6. Caching: reuse stable instructions/results when the platform supports it.
  7. Model routing: use smaller/cheaper models for classification, extraction and simple transformations.
  8. Batch work: combine compatible operations when latency/business semantics allow.
  9. Structured output: request only required fields instead of verbose prose.
  10. RAG: retrieve relevant chunks instead of sending an entire knowledge base.

GitHub Copilot / AI Coding Cost Optimization

  • Keep repository instructions concise and hierarchical.
  • Give an agent the exact files relevant to the task.
  • Use repository search instead of dumping entire repositories into context.
  • Break large tasks into specifications and focused implementation steps.
  • Ask for targeted diffs rather than rewriting unrelated files.
  • Use smaller models for straightforward transformations where available.
  • Run tests locally/automatically and provide only failure context back to the agent.
  • Store stable architectural rules in reusable instructions rather than repeating them in every prompt.

RAG means Retrieval-Augmented Generation. Instead of asking the model to remember every bank policy, retrieve the relevant policy and give it to the model.

ACL-Aware RAG

A user must never retrieve a document merely because it is semantically relevant. Retrieval must also respect identity and authorization.

Hybrid Retrieval

Combine keyword search and semantic/vector search when both exact terms and conceptual meaning matter.

Retrieve a wider candidate set cheaply, then use a stronger reranker to select the most relevant passages before calling the expensive generation model.

  • Keep chunks focused.
  • Retrieve a small top-K and rerank.
  • Cache repeated questions/results where safe.
  • Use smaller embedding models when evaluation shows acceptable quality.
  • Compress retrieved context.
  • Use a smaller generation model for low-risk FAQ tasks.
  • Measure retrieval recall, answer quality, latency and cost together.

38.20 AI / Agentic Interview Q&A

Q. How would you reduce LLM cost by 50%?

Answer: First establish a baseline by measuring input tokens, output tokens, requests, model mix, latency and cost per successful task. Then reduce unnecessary context, compress history, cache stable context, retrieve only relevant RAG chunks, route simple tasks to smaller models, constrain outputs and eliminate redundant agent/tool calls. Finally, validate quality so cost savings do not simply reduce business value.

Q. How do you secure an AI agent that can transfer money?

Answer: The model never receives unrestricted financial authority. Put the agent behind an authorization layer, validate arguments against authenticated user identity, enforce account ownership and transaction limits, require idempotency, apply risk-based step-up authentication or human approval, audit every action and provide deterministic fallback behavior. The backend remains the final security boundary.

Q. What is MCP and why use it?

Answer: MCP standardizes how AI applications can interact with external capabilities and context providers. It can reduce bespoke integration work, but MCP does not replace authentication, authorization, validation or governance. Every exposed capability still needs enterprise security controls.

Q. RAG vs fine-tuning?

Answer: Use RAG when the model needs current/private/traceable information. Fine-tuning is more appropriate for changing model behavior or specialization rather than simply injecting frequently changing enterprise facts. They can also be combined.

Q. What is Spec-Driven Development?

Answer: It makes an explicit specification the contract between business intent, engineers and AI coding agents. The specification defines behavior, constraints, interfaces and acceptance criteria before implementation. This reduces ambiguity and makes AI-generated code easier to validate.

Q. What is the biggest mistake companies make with agents?

Answer: Giving an LLM too much authority before establishing deterministic authorization, observability, evaluation and failure controls. An agent should be treated as an untrusted decision-making component operating inside a trusted software control plane.

Q. Why Python for GenAI?

Answer: Python has a mature ecosystem for model APIs, embeddings, vector databases, data processing, evaluation and agent frameworks. I would still integrate the AI layer with enterprise Java services where the organization's core transaction platform requires Java.

Q. LangChain vs LangGraph?

Q. How would you measure an AI platform?

Answer: I would measure business success plus engineering metrics: task success rate, groundedness, safety violations, retrieval quality, tool-call accuracy, latency, token usage, cost per successful task, failure rate and human-escalation rate.

39.5 SOLID — Full Explanation

S — Single Responsibility Principle

Layman: One worker should not be responsible for cooking, collecting payment, cleaning the restaurant and delivering food if those responsibilities grow independently.

Bank: Do not make AccountService calculate interest, send emails, write audit logs, call fraud APIs and generate PDF statements all in one class.

Bad

class AccountService {

    void transfer() {}
    void sendEmail() {}
    void generateStatement() {}
    void saveAuditLog() {}
    void callFraudApi() {}
}

Good

class TransferService {}
class NotificationService {}
class StatementService {}
class AuditService {}
class FraudService {}

Interview: SRP is about one primary reason to change, not literally one method per class.

O — Open/Closed Principle

Layman: Add a new payment method without rewriting stable transfer logic.

Bad

if (method.equals("UPI")) {
    // UPI
} else if (method.equals("CARD")) {
    // Card
} else if (method.equals("WIRE")) {
    // Wire
}

Good

interface PaymentMethod {
    void pay(Money amount);
}

class UpiPayment implements PaymentMethod {
    public void pay(Money amount) {}
}

class CardPayment implements PaymentMethod {
    public void pay(Money amount) {}
}

Adding WalletPayment should not require rewriting the core payment algorithm.

L — Liskov Substitution Principle

Layman: If a rule says “all objects of this type can perform X”, a subtype must not unexpectedly break X.

Bank: If PaymentGateway promises refund(), do not create a subtype that always throws “refund not supported” unless the abstraction explicitly allows that behavior.

Bad

interface PaymentGateway {
    void pay();
    void refund();
}

class NoRefundGateway implements PaymentGateway {
    public void pay() {}
    public void refund() {
        throw new UnsupportedOperationException();
    }
}

Better

interface PaymentGateway {
    void pay();
}

interface RefundablePaymentGateway
        extends PaymentGateway {
    void refund();
}

Remember: LSP is about behavioral correctness, not merely method signatures.

I — Interface Segregation Principle

Layman: Do not give every employee a giant form containing fields they never use.

Bank: A read-only reporting service should not depend on account deletion, account creation and update methods.

Bad

interface AccountOperations {
    void create();
    void update();
    void delete();
    Account read();
}

Factory Pattern

Problem: We support UPI, card, wire transfer and wallet payments.

interface PaymentProcessor {
    void process(Money money);
}

class UpiProcessor implements PaymentProcessor {
    public void process(Money money) {}
}

class CardProcessor implements PaymentProcessor {
    public void process(Money money) {}
}

class PaymentProcessorFactory {

    static PaymentProcessor get(String type) {
        return switch (type) {
            case "UPI" -> new UpiProcessor();
            case "CARD" -> new CardProcessor();
            default -> throw new IllegalArgumentException();
        };
    }
}

Why: Callers do not need to know how each processor is constructed.

50.1 JavaScript + Node.js — Interview Answers

Q1. var vs let vs const?

Answer: var is function-scoped and can be redeclared. let and const are block-scoped. Use const by default, let when reassignment is required, and generally avoid var in modern applications.

const accountId = "ACC1001";
let balance = 50000;
balance = 48000;

Interview point: const prevents reassignment of the binding; it does not make an object immutable.

Q2. What is a closure?

Answer: A closure occurs when a function remembers variables from the scope in which it was created, even after that outer function has finished.

function createAuditLogger(customerId) {
  return function(message) {
    console.log(customerId, message);
  };
}

const log = createAuditLogger("C100");
log("Transfer completed");

This can be useful for encapsulation, callbacks and configuration, but excessive closures can make code difficult to understand.

Q3. What is the JavaScript event loop?

Answer: JavaScript executes synchronous work on the call stack. Asynchronous operations are handled by the runtime, and their callbacks/promises are scheduled for execution when the stack is available.

Call Stack ↓ Start API Request ↓ Browser / Node Runtime ↓ API Completes ↓ Task / Microtask Queue ↓ Event Loop ↓ Call Stack

Banking: Loading transactions should not freeze the dashboard while the API request is in progress.

Q4. Promise vs async/await?

Answer: A Promise represents a future result. async/await is syntax that makes Promise-based asynchronous code easier to read.

const account = await getAccount("ACC1001");

Both use the same underlying Promise model.

Q5. Why is Node.js good for I/O-heavy applications?

Answer: Node.js uses an event-driven, non-blocking model that can efficiently handle many concurrent I/O operations. It is less suitable for CPU-heavy work that blocks the event loop.

Banking: An API gateway or aggregation service calling several backend APIs can be a good Node.js workload. CPU-heavy fraud modelling may need another execution strategy.

Q6. What is middleware in Express?

Answer: Middleware is a function that participates in processing an HTTP request before the final route handler.

app.use(authMiddleware);
app.use(requestLoggingMiddleware);

app.get("/api/accounts", handler);

Typical middleware handles authentication, logging, validation, rate limiting and error handling.

Q7. How do you secure a Node.js API?

Answer: Enforce authentication and authorization server-side, validate inputs, use HTTPS, protect secrets, apply rate limits, secure headers, dependency scanning, structured logging and least privilege. Never trust the browser to enforce banking permissions.

Q8. How do you prevent duplicate transfers?

Answer: Use an idempotency key generated for the business operation. The backend stores the result associated with that key and returns the same logical result when the same request is retried.

POST /api/transfers
Idempotency-Key: 8e4d-transfer-001

The database/business layer—not JavaScript alone—must guarantee the behavior.

50.2 React — Interview Answers

Q1. Props vs state?

Answer: Props are inputs supplied by a parent. State is data owned and changed by a component or state-management layer.

<BalanceCard balance={50000} />

The balance above is a prop.

Q2. What does useEffect do?

Answer: It synchronizes a component with an external system such as an API, subscription, timer or browser API. It should not be used merely to calculate derived values that can be calculated during rendering.

useEffect(() => {
  loadTransactions();
}, [accountId]);

Q3. Why does React need keys?

Answer: Keys provide stable identity for items in a list so React can efficiently determine which items changed.

{transactions.map(tx =>
  <TransactionRow
    key={tx.id}
    transaction={tx}
  />
)}

Use a stable business identifier, not a random value generated during rendering.

Q4. Context vs Redux?

Answer: Context is useful for relatively shared values such as theme or authentication context. Redux Toolkit provides a more structured global state architecture with actions, reducers, middleware and predictable state transitions. Choose based on complexity rather than popularity.

Q5. Client state vs server state?

Answer: Client state is UI/application state such as whether a modal is open. Server state comes from backend systems and has freshness, caching, loading and synchronization concerns.

Banking: “Transfer modal open” is client state. “Current account balance” is server state.

Q6. How do you optimize a huge transaction table?

Answer: Do not load 100,000 records into the browser. Use server-side pagination/filtering, virtualization where appropriate, indexed backend queries, response compression, caching and selective fields.

GET /transactions?
    page=0&
    size=50&
    fromDate=2026-01-01&
    type=DEBIT

Q7. How do you secure React?

Answer: Treat the frontend as untrusted. Protect the backend with authorization, prevent XSS, use secure authentication/session patterns, validate data server-side, avoid exposing secrets, use CSP where appropriate and scan dependencies.

50.3 Angular — Interview Answers

Q1. What is dependency injection?

Answer: A class receives the services it depends on instead of constructing them itself. Angular's DI container manages those dependencies.

constructor(
  private accountService: AccountService
) {}

This improves testing, reuse and separation of concerns.

Q2. Observable vs Promise?

Answer: A Promise represents one eventual result. An Observable can represent a sequence of values over time and supports operators such as filtering, mapping and cancellation patterns.

Banking: A one-time account lookup can conceptually be Promise-like; a live notification stream is naturally stream-oriented.

Q3. What is an HTTP interceptor?

Answer: An interceptor centrally processes HTTP requests/responses. It is useful for authentication headers, correlation IDs, logging, standardized errors and retry policies where appropriate.

Q4. What is a route guard?

Answer: It decides whether navigation should be allowed based on application state. It is a UX/navigation control, not the final security boundary. The backend must still enforce authorization.

Q5. Reactive forms vs template-driven forms?

Answer: Reactive forms define form structure and validation programmatically and are often preferable for complex enterprise forms. Template-driven forms can be simpler for small forms.

Q6. How do you manage Angular state?

Answer: Start with local component state. Use services/signals/RxJS for shared state where appropriate. Use NgRx or another structured store when application complexity justifies centralized actions, selectors and predictable state transitions.

50.4 Vue — Interview Answers

Q1. What is Vue reactivity?

Answer: Vue tracks reactive dependencies and updates the relevant UI when reactive values change.

const balance = ref(50000);
balance.value = 48000;

Q2. ref vs reactive?

Answer: ref wraps a reactive value and uses .value in JavaScript. reactive creates a reactive proxy around an object. Use the approach that keeps the component easiest to reason about.

Q3. computed vs watch?

Answer: Use computed for derived values. Use watch when a change should trigger a side effect.

const totalDebit = computed(() =>
  transactions.value
    .filter(t => t.type === "DEBIT")
    .reduce((sum, t) => sum + t.amount, 0)
);

Q4. What is Pinia?

Answer: Pinia is Vue's modern state-management library. It provides stores containing state, getters and actions.

Q5. How do you secure Vue?

Answer: Use the same principle as React: the browser is not trusted. Validate on the backend, protect authentication, prevent XSS, avoid secrets in bundles, use secure headers/CSP and enforce authorization server-side.

50.5 CSS / Tailwind / Build Tools — Interview Answers

Q1. Explain the CSS box model.

Answer: Every element is conceptually composed of content, padding, border and margin. Understanding this is essential for predictable layouts.

Q2. Flexbox vs Grid?

Answer: Flexbox is primarily useful for one-dimensional layouts. Grid is designed for two-dimensional row/column layouts. They are complementary, not competitors.

Q3. What is responsive design?

Answer: The UI adapts to different screen sizes and interaction modes rather than assuming one fixed desktop width.

Q4. What is Tailwind?

Answer: Tailwind is a utility-first CSS framework. Instead of creating a class for every visual component, developers compose predefined utility classes and can build a controlled design system around them.

Q5. Webpack vs Vite?

Answer: Webpack is a mature configurable module bundler with a large ecosystem. Vite emphasizes very fast development feedback and modern browser/module workflows, while producing optimized production builds through its build pipeline. Choice depends on project requirements and ecosystem constraints.

Q6. What is tree shaking?

Answer: Tree shaking removes unused code from production bundles when the module/build pipeline can safely determine it is unused.

Q7. What is code splitting?

Answer: Instead of sending the entire application to the browser at first load, split it into chunks and load features when needed.

50.6 Cross-Framework Senior Interview Answers

Q. React vs Angular vs Vue — which would you choose?

Strong answer: “I would not choose solely from personal preference. I would evaluate team expertise, existing ecosystem, application size, governance, accessibility, performance requirements, hiring, long-term maintenance and organizational standards. Angular offers strong conventions for enterprise applications; React offers a flexible ecosystem; Vue offers progressive adoption and a relatively approachable model. For a regulated banking system, consistency, security, testing, observability and maintainability matter more than framework fashion.”

Q. Where should business rules live?

Answer: Critical business rules must be enforced by trusted backend services. The frontend can provide validation for usability, but it cannot be the authoritative security/business-rule boundary.

Q. How would you handle an API that takes 10 seconds?

Answer: First measure. Then consider timeout policy, loading states, cancellation, backend profiling, caching, pagination, parallel requests where safe, asynchronous workflows and UX alternatives. Never simply increase the timeout without understanding why the API is slow.

Q. How do you design frontend observability?

Answer: Capture route performance, API latency, failed requests, JavaScript errors, user-impact metrics and correlation IDs. Avoid logging sensitive banking data. Connect frontend telemetry with backend traces so a customer-visible error can be followed across the system.

51.9 Shared API Client

async function apiRequest(
  url,
  options = {}
) {

  const response = await fetch(
    url,
    {
      ...options,
      headers: {
        "Content-Type":
          "application/json",
        ...(options.headers || {})
      }
    }
  );

  if (!response.ok) {
    const message =
      await response.text();

    throw new Error(
      message || "API request failed"
    );
  }

  return response.json();
}

53. Principal Engineer Frontend Questions — Model Answers

Q. How would you architect a banking frontend for millions of users?

Answer: I would start with business capabilities and user journeys rather than choosing a framework first. I would use a CDN and optimized static delivery, route-level code splitting, a consistent design system, a clear client/server-state boundary, backend-for-frontend/API aggregation where useful, secure authentication, server-side authorization, pagination and caching, strong observability and automated quality gates. I would define performance and availability budgets and validate them with real measurements.

Q. How do you balance frontend performance and developer productivity?

Answer: Establish sensible defaults and reusable infrastructure rather than asking every developer to optimize manually. Use a design system, shared API client, route-level lazy loading, automated bundle budgets, linting, testing and CI checks. Optimize the highest-impact bottlenecks based on telemetry.

Q. How would you migrate an Angular banking portal to React?

Answer: I would avoid a big-bang rewrite. First define architecture and API contracts, identify bounded UI domains, build characterization tests around critical flows, introduce a strangler-style routing boundary, migrate low-risk features first, run both systems where necessary, measure, then progressively retire the old application.

Q. What would you standardize across React, Angular and Vue?

Answer: I would standardize business/API contracts, authentication architecture, security requirements, observability, accessibility, design tokens, testing expectations, error semantics, performance budgets and CI/CD controls. I would not force identical implementation details where framework conventions differ.

Q. What separates a senior frontend engineer from a Principal Engineer?

Answer: A senior engineer can build a high-quality feature. A Principal Engineer additionally establishes architectural direction, reduces organizational complexity, creates reusable engineering standards, anticipates scale and failure, drives modernization, makes trade-offs explicit, mentors engineers and connects technical decisions to customer and business outcomes.
