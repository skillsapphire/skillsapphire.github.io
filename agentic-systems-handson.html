Implementation companion — LangChain 0.3 / LangGraph

Every diagram in the handbook, wired up as a running graph.

The source document describes agent patterns and production architecture in the abstract. This page rebuilds each one as working LangGraph code, with every idea explained in plain language first — no assumed background needed.

Start here — what even is an "agent"?

Imagine a robot assistant. On its own, it can only think — it can't check the weather, send an email, or look anything up. Now give it a phone and internet access. Suddenly it can actually do things, not just think about them. That's the whole idea of an "AI agent": a thinking brain (the AI model) plus tools it's allowed to use (search, a calculator, a database).

LangChain is a toolbox of ready-made pieces for building this — things like "connect to an AI model" or "give it a search tool." LangGraph is a way to draw the agent's steps as a flowchart (a "graph") so you can control exactly what happens in what order, instead of just hoping the AI does the right thing.

This picture is called a "state graph." Each box is a step (a "node"). Each arrow is a path the agent can take next. Every pattern below is really just a different arrangement of boxes and arrows like this one.

Setup

Environment

Before writing any agent, we need to install the libraries we'll use and set up a couple of "keys" (like passwords) so our code is allowed to talk to the AI model.

What's a "package" and an "API key"?

A package is just a folder of code someone else already wrote, so you don't have to write it yourself — like downloading an app instead of building one from scratch. pip install is the command that downloads these packages onto your computer.

An API key is like a library card. It proves to the AI company's server "yes, this request is allowed, and please bill this account." You keep it secret, the same way you wouldn't hand your library card to a stranger.

Chapter 2 · Pattern 01

ReAct — Reason, act, observe, repeat

The handbook describes ReAct as alternating Thought → Action → Observation. In LangGraph this is a two-node cycle: an agent node that reasons and may request a tool call, and a tools node that executes it and feeds the observation back.

In plain English

Picture playing 20 Questions, but instead of guessing, you're allowed to actually check things. You think ("I should check the price"), you act (look it up), you observe the answer, and then you think again with that new information. ReAct just means the AI does this same loop: think → do a small task → look at the result → think again — instead of trying to answer everything in one guess.

A tool, in code, is just a regular function (a mini-program) that does one job, like "look up a stock price." We "give" this function to the AI so it can ask our program to run it whenever it needs to.

react_agent.pypython
# StateGraph = the "flowchart" builder. MessagesState = a built-in way to
# keep track of the conversation (the list of chat messages) as we go.
from langgraph.graph import StateGraph, MessagesState, START, END

# ToolNode = a ready-made box that knows how to run a tool for us.
# tools_condition = a ready-made "traffic light" that checks: did the AI
# just ask to use a tool? If yes, go to the tools box. If no, we're done.
from langgraph.prebuilt import ToolNode, tools_condition

# "tool" is a decorator (a label we put above a function) that turns a
# normal Python function into something the AI is allowed to call.
from langchain_core.tools import tool

@tool
def get_stock_price(ticker: str) -> float:
    """Return the current price for a ticker symbol."""
    # This is pretend data. In real life this might call a stock market API.
    prices = {"ACME": 182.40, "GLBX": 94.12}
    # .get(...) looks up the ticker in our dictionary; if it's missing, return 0.0
    return prices.get(ticker.upper(), 0.0)

@tool
def get_52_week_high(ticker: str) -> float:
    """Return the 52-week high for a ticker symbol."""
    highs = {"ACME": 201.10, "GLBX": 110.00}
    return highs.get(ticker.upper(), 0.0)

# We put both tools in a list so we can hand them to the AI together.
tools = [get_stock_price, get_52_week_high]

# .bind_tools(...) tells the AI model "here are the tools you're allowed
# to ask for." The model still can't run them itself — it can only say
# "please run get_stock_price with ticker=ACME" and wait for the answer.
llm_with_tools = frontier_model.bind_tools(tools)

# This function is our "agent" box (node) in the flowchart.
# "state" holds everything that's happened so far — mainly the chat messages.
def agent_node(state: MessagesState):
    # We hand the whole conversation to the model and get back its reply
    # (which might be plain text, OR a request to use a tool).
    return {"messages": [llm_with_tools.invoke(state["messages"])]}

# Now we actually build the flowchart.
graph = StateGraph(MessagesState)

# add_node gives a name to each box: "agent" runs our function above,
# "tools" runs the ready-made ToolNode, which knows how to execute
# whichever tool the agent asked for.
graph.add_node("agent", agent_node)
graph.add_node("tools", ToolNode(tools))

# add_edge draws a plain arrow: always go from START straight to "agent".
graph.add_edge(START, "agent")

# add_conditional_edges draws a "fork in the road" after "agent":
# tools_condition checks the agent's last message — if it asked for a
# tool, go to "tools"; otherwise, the conversation is finished, go to END.
graph.add_conditional_edges("agent", tools_condition)

# After the tool runs, we always loop BACK to "agent" so it can look at
# the tool's answer and decide what to do next. This loop is what makes
# it "ReAct" instead of a single one-shot tool call.
graph.add_edge("tools", "agent")

# .compile() turns our flowchart description into something we can run.
react_agent = graph.compile()

# .invoke(...) actually runs the graph, starting with one user message.
result = react_agent.invoke({
    "messages": [("user", "Is ACME close to its 52-week high?")]
})

# The final answer is the last message in the conversation.
print(result["messages"][-1].content)

The loop back from tools to agent is what makes this ReAct rather than a single tool call: the model sees each observation before deciding its next action.

Chapter 2 · Pattern 02

Reflection — the model as its own auditor

A generate node drafts, a critique node reviews against a rubric, and a conditional edge sends the draft back for another pass until the critique is clean or a retry ceiling is hit.

In plain English

This is like writing an essay, then swapping papers with a strict classmate who marks it up, then rewriting it based on their notes — maybe two or three times — until it's good enough. Here, the same AI plays both roles: once as the writer, once as the strict critic checking its own work.

A TypedDict is just a way of describing "this box of information will always have these labeled compartments" (like a form with named fields), so Python (and we) know exactly what's inside our state at every step.

reflection_loop.pypython
# TypedDict lets us describe the "shape" of our state: which fields
# exist and what type of data each one holds.
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class DraftState(TypedDict):
    task: str        # what the user asked for
    draft: str        # the current version of the written answer
    critique: str      # the critic's notes on the draft
    revisions: int      # how many times we've rewritten it so far

def generate(state: DraftState) -> DraftState:
    # Build the instruction we'll send to the AI.
    prompt = f"Write a one-paragraph reply to: {state['task']}"
    # If there's an earlier critique, tell the AI to fix those specific issues.
    if state.get("critique"):
        prompt += f"\n\nAddress this critique: {state['critique']}"
    # Ask the smart model to actually write the paragraph.
    draft = frontier_model.invoke(prompt).content
    # Return the new draft, and add 1 to our revision counter.
    return {"draft": draft, "revisions": state.get("revisions", 0) + 1}

def critique(state: DraftState) -> DraftState:
    # Ask the cheap model to act as a strict grader. We tell it exactly
    # what word to say ("APPROVED") if there's nothing wrong, so our code
    # can easily check for that word later.
    verdict = small_model.invoke(
        f"Critique this reply for tone and compliance. "
        f"Reply 'APPROVED' if it needs no changes, otherwise list fixes.\n\n{state['draft']}"
    ).content
    return {"critique": verdict}

def should_continue(state: DraftState) -> str:
    # This function decides which box to go to next.
    # If the critic said "APPROVED", or we've already tried 3 times,
    # stop here (go to END) so we don't loop forever.
    if "APPROVED" in state["critique"] or state["revisions"] >= 3:
        return END
    # Otherwise, go back and rewrite the draft again.
    return "generate"

graph = StateGraph(DraftState)
graph.add_node("generate", generate)
graph.add_node("critique", critique)
graph.add_edge(START, "generate")       # always start by writing a first draft
graph.add_edge("generate", "critique")   # then always get it critiqued
graph.add_conditional_edges("critique", should_continue)  # fork: retry or stop

reflection_agent = graph.compile()
Guardrail Cap revisions explicitly, like we did with revisions >= 3. Without that cap, a stubborn critic could send the draft back forever — the AI equivalent of never letting yourself turn in your homework.
Chapter 2 · Pattern 03

Plan and Execute — commit to a roadmap first

A planner node produces an ordered list of steps up front; an executor node works through them one at a time, and a replan node only fires if a step's result invalidates the rest of the plan.

In plain English

Instead of figuring things out one tiny step at a time (like ReAct), this is more like writing your whole packing list before a trip, then checking things off one by one. It's slower to start (you plan first), but each step is more predictable because you already know what's coming next.

A Pydantic model (the Plan class below) is a strict template that forces the AI's answer into an exact shape — here, "a list of text steps" — instead of letting it reply with any random sentence. This is what the handbook calls a "structured output."

plan_execute.pypython
from typing import TypedDict, List
from langgraph.graph import StateGraph, START, END
from pydantic import BaseModel

# This class says: "a Plan is always an object with one field called
# 'steps', and 'steps' is always a list of text strings." The AI's
# reply gets forced into this exact shape — no surprises.
class Plan(BaseModel):
    steps: List[str]

class PlanState(TypedDict):
    goal: str            # what the user wants overall
    plan: List[str]        # the steps left to do
    past_steps: List[str]    # steps we've already finished, with their results
    response: str          # the final answer we give back at the end

# .with_structured_output(Plan) means: "whatever this model returns,
# force it to match the Plan shape above" — a list of steps, guaranteed.
planner_llm = small_model.with_structured_output(Plan)

def plan_step(state: PlanState) -> PlanState:
    # Ask the AI to break the big goal into small, doable steps.
    plan = planner_llm.invoke(
        f"Break this goal into 3-6 sequential, concrete steps: {state['goal']}"
    )
    # plan.steps is a real Python list because of the Plan template above.
    return {"plan": plan.steps, "past_steps": []}

def execute_step(state: PlanState) -> PlanState:
    # Take the very first step off the list (index 0).
    step = state["plan"][0]
    # Ask the smart model to actually carry out that one step.
    result = frontier_model.invoke(f"Execute this step and report the outcome: {step}").content
    return {
        # state["plan"][1:] means "everything except the first item" —
        # so we remove the step we just finished.
        "plan": state["plan"][1:],
        # Keep a running history of what we did and what happened.
        "past_steps": state["past_steps"] + [f"{step} -> {result}"],
    }

def finalize(state: PlanState) -> PlanState:
    # Join all our past steps into one block of text, separated by new lines.
    summary = "\n".join(state["past_steps"])
    return {"response": frontier_model.invoke(f"Summarize the completed work:\n{summary}").content}

def has_remaining_steps(state: PlanState) -> str:
    # If the plan list still has items in it, keep executing.
    # An empty list in Python counts as "false", so this reads naturally:
    # "if there's a plan (any steps left), go execute; otherwise finalize."
    return "execute" if state["plan"] else "finalize"

graph = StateGraph(PlanState)
graph.add_node("plan", plan_step)
graph.add_node("execute", execute_step)
graph.add_node("finalize", finalize)
graph.add_edge(START, "plan")
# Both "plan" and "execute" check the same question afterward: is there
# still work left to do?
graph.add_conditional_edges("plan", has_remaining_steps, {"execute": "execute", "finalize": "finalize"})
graph.add_conditional_edges("execute", has_remaining_steps, {"execute": "execute", "finalize": "finalize"})
graph.add_edge("finalize", END)

plan_execute_agent = graph.compile()
Chapter 2 · Pattern 04

Multi-agent — a supervisor routing to specialists

The handbook's hospital analogy — surgeons, radiologists, pharmacists with clear contracts — maps to a supervisor graph: one router node reads intent and hands off to whichever specialist subgraph owns that domain.

In plain English

Think of calling a big company's customer service line. First you hear "press 1 for billing, press 2 for shipping" — that's the supervisor. Then you get connected to a specialist who only handles that one type of problem. Here, instead of a phone menu, a small cheap AI model reads your message and decides which specialist should answer.

Literal["billing", "shipping", "END"] just means "the answer must be exactly one of these three words — nothing else is allowed." That keeps our routing predictable.

supervisor.pypython
from typing import Literal
from langgraph.graph import StateGraph, MessagesState, START, END
from pydantic import BaseModel

# "next" can ONLY ever be one of these three exact words.
class Route(BaseModel):
    next: Literal["billing", "shipping", "END"]

# We use the cheap model here because "which department is this?" is an
# easy classification job — it doesn't need our most powerful (and
# expensive) model to get right.
router_llm = small_model.with_structured_output(Route)

def supervisor(state: MessagesState):
    # Ask the router which specialist should handle this conversation.
    route = router_llm.invoke(
        [("system", "Route to 'billing', 'shipping', or 'END' if the request is resolved.")]
        + state["messages"]
    )
    # We don't add a new chat message here (empty list) — we just record
    # which direction to go next, in the "next" field.
    return {"messages": [], "next": route.next}

def billing_agent(state: MessagesState):
    # This specialist ONLY ever sees a system prompt about billing —
    # it has no idea shipping questions even exist.
    reply = frontier_model.invoke(
        [("system", "You are the billing specialist. Only billing questions.")] + state["messages"]
    )
    return {"messages": [reply]}

def shipping_agent(state: MessagesState):
    reply = frontier_model.invoke(
        [("system", "You are the shipping specialist. Only shipping questions.")] + state["messages"]
    )
    return {"messages": [reply]}

graph = StateGraph(MessagesState)
graph.add_node("supervisor", supervisor)
graph.add_node("billing", billing_agent)
graph.add_node("shipping", shipping_agent)
graph.add_edge(START, "supervisor")

# lambda s: s["next"] is a tiny one-line function meaning "look at the
# state's 'next' field and use that to decide where to go" — matching it
# against the dictionary of possible destinations.
graph.add_conditional_edges("supervisor", lambda s: s["next"],
                             {"billing": "billing", "shipping": "shipping", "END": END})

# After a specialist answers, control goes BACK to the supervisor, in
# case the conversation needs to be routed somewhere else next.
graph.add_edge("billing", "supervisor")
graph.add_edge("shipping", "supervisor")

supervisor_agent = graph.compile()

Each specialist only ever sees its own system prompt — the input/output contract the handbook calls for stays enforced by graph structure, not by instruction alone.

Chapter 2 · Pattern 05

Swarm — decentralized hand-off, no coordinator

Where the supervisor pattern always returns control to a router, a swarm lets any agent hand off directly to any other. langgraph-swarm implements this as agents that can transfer the active thread among themselves.

In plain English

Imagine two friends working at neighboring desks who can just turn to each other and say "hey, this one's yours" — no manager needed to approve the hand-off. That's a swarm: agents pass the conversation directly to whichever agent should handle it next, without going through a supervisor first.

swarm.pypython
from langgraph_swarm import create_swarm, create_handoff_tool
from langgraph.prebuilt import create_react_agent

# A "handoff tool" is a special tool whose only job is "pass this
# conversation to a different named agent." It's not doing real work —
# it's just pointing to who should take over next.
transfer_to_booking = create_handoff_tool(agent_name="booking_agent")
transfer_to_support = create_handoff_tool(agent_name="support_agent")

# create_react_agent is a shortcut that builds a whole ReAct-style agent
# (like the one we built by hand earlier) in one line.
booking_agent = create_react_agent(
    frontier_model,
    tools=[transfer_to_support],   # this agent can hand off to "support"
    prompt="You handle new reservations. Hand off anything about existing bookings.",
    name="booking_agent",
)

support_agent = create_react_agent(
    frontier_model,
    tools=[transfer_to_booking],   # this agent can hand off to "booking"
    prompt="You handle existing-booking issues. Hand off anything about new reservations.",
    name="support_agent",
)

# create_swarm wires all the agents together and picks which one starts.
swarm = create_swarm(
    agents=[booking_agent, support_agent],
    default_active_agent="booking_agent",
).compile()

# .stream(...) is like .invoke(...) but it gives us updates piece by
# piece as they happen, instead of waiting for the whole thing to finish.
for chunk in swarm.stream({"messages": [("user", "Can I change my seat on booking #4471?")]}):
    print(chunk)
Design consideration Swarm trades the supervisor's predictability for reach — fine for the bee-colony case in the handbook, risky if any of those agents hold write tools. Pair it with the policy gate in Chapter 4 before letting it touch production data.
Chapter 2 · Pattern 06 (extension)

Agentic RAG — retrieval the AI controls, not a fixed step

The handbook doesn't name this one directly, but it falls straight out of Chapter 3's "Memory / RAG" row plus the ReAct pattern above. Plain RAG (Retrieval-Augmented Generation) always fetches documents first, no matter the question. Agentic RAG makes retrieval a tool the agent chooses to use, checks the quality of what it got back, and tries again with a better search if the results were bad.

In plain English

Think of an open-book test. A weak student flips open the book for every single question, even ones they already know ("what's 2+2?"). A smart student first decides "do I actually need to look this up?", finds a page, then asks themselves "wait, does this page actually answer the question, or did I search for the wrong thing?" — and if it's the wrong page, they try a better search term before answering. Agentic RAG is that smart-student behavior, built into the graph.

RAG stands for "Retrieval-Augmented Generation" — a fancy way of saying "look something up, then use what you found to write the answer," instead of the AI making things up purely from memory. A vector store is just a searchable filing cabinet of documents, where "search" means "find the documents whose meaning is closest to my question," not just matching exact keywords.

agentic_rag.pypython
# create_retriever_tool turns "search my documents" into a tool the
# agent can call, exactly like the stock-price tool back in Pattern 01.
from langchain.tools.retriever import create_retriever_tool

# InMemoryVectorStore is a simple "searchable filing cabinet" that lives
# only in memory (fine for learning; swap for Pinecone/pgvector/Weaviate
# in production, as the handbook's memory table suggests).
from langchain_community.vectorstores import InMemoryVectorStore

# Embeddings turn text into a list of numbers that capture its MEANING,
# so "how do refunds work?" can be matched to a document about refund
# policy even if it doesn't share a single exact word.
from langchain_openai import OpenAIEmbeddings
from langchain_core.documents import Document

from langgraph.graph import StateGraph, MessagesState, START, END
from langgraph.prebuilt import ToolNode, tools_condition
from pydantic import BaseModel
from typing import Literal

# --- 1. Build our tiny "filing cabinet" of company documents ---
docs = [
    Document(page_content="Our refund policy allows returns within 30 days of purchase."),
    Document(page_content="Shipping typically takes 3-5 business days within the country."),
]
# .from_documents(...) reads each document, turns it into an embedding
# (a list of numbers), and stores both the text and the numbers together.
vectorstore = InMemoryVectorStore.from_documents(docs, OpenAIEmbeddings())

# .as_retriever() gives us a simple "search this cabinet" function.
retriever = vectorstore.as_retriever()

# Wrap the retriever as a proper tool, with a name and description the
# agent will read to decide WHEN it's worth using.
retriever_tool = create_retriever_tool(
    retriever,
    "search_company_docs",
    "Search internal company policy documents for facts needed to answer the user.",
)

# Just like Pattern 01, the agent can only ASK for this tool — it can't
# run the search itself.
llm_with_retriever = frontier_model.bind_tools([retriever_tool])

def agent_node(state: MessagesState):
    # The agent decides: do I already know the answer, or should I
    # request a document search first?
    return {"messages": [llm_with_retriever.invoke(state["messages"])]}

# --- 2. A tiny grader that checks: was the search actually useful? ---
class Grade(BaseModel):
    relevant: Literal["yes", "no"]   # forces a clean yes/no, nothing else

grader_llm = small_model.with_structured_output(Grade)

def grade_documents(state: MessagesState) -> str:
    # The very first message is always the user's original question.
    question = state["messages"][0].content
    # The very last message is whatever the retriever tool just returned.
    retrieved = state["messages"][-1].content
    grade = grader_llm.invoke(
        f"Question: {question}\nRetrieved text: {retrieved}\n"
        f"Is the retrieved text relevant to answering the question? Answer yes or no."
    )
    # This return value tells the graph which box to go to next.
    return "generate" if grade.relevant == "yes" else "rewrite"

def rewrite(state: MessagesState):
    # If the search results were bad, ask the AI to write a CLEARER,
    # more specific search query — like trying different keywords on
    # a search engine when your first try comes up empty.
    question = state["messages"][0].content
    better_question = frontier_model.invoke(
        f"The previous search didn't find useful results. Rewrite this question "
        f"to be clearer and more specific for a document search: {question}"
    ).content
    # We feed the improved question back in as if the user asked it,
    # so the agent node gets another attempt at searching.
    return {"messages": [("user", better_question)]}

def generate(state: MessagesState):
    # Only reachable once we have documents the grader approved.
    context = state["messages"][-1].content
    question = state["messages"][0].content
    answer = frontier_model.invoke(
        f"Answer the question using ONLY this context. If the answer isn't "
        f"in the context, say you don't know.\n\nContext: {context}\n\nQuestion: {question}"
    ).content
    return {"messages": [("assistant", answer)]}

graph = StateGraph(MessagesState)
graph.add_node("agent", agent_node)
graph.add_node("retrieve", ToolNode([retriever_tool]))
graph.add_node("rewrite", rewrite)
graph.add_node("generate", generate)

graph.add_edge(START, "agent")
# Fork 1: did the agent ask to search, or does it already have an answer?
graph.add_conditional_edges("agent", tools_condition, {"tools": "retrieve", END: END})
# Fork 2: were the retrieved documents actually good enough to answer with?
graph.add_conditional_edges("retrieve", grade_documents, {"generate": "generate", "rewrite": "rewrite"})
# A bad search sends us back to the agent with a better question.
graph.add_edge("rewrite", "agent")
graph.add_edge("generate", END)

agentic_rag = graph.compile()

result = agentic_rag.invoke({"messages": [("user", "How long do I have to return something?")]})
print(result["messages"][-1].content)

The extra loop through rewrite is the whole point: plain RAG has no way to notice a bad search and try again, so it just answers confidently from irrelevant documents. This graph catches that and retries.

Where this connects to Chapter 3 InMemoryVectorStore here is a stand-in for the "Memory / RAG" row in the state-vs-memory table (Pinecone, pgvector, Weaviate) — this pattern is really just that storage layer wired into a decision loop instead of being fetched unconditionally on every turn.
Chapter 3

Model routing at the graph level

Rather than picking one model for the whole run, route per-node: classification and schema-filling nodes call small_model, reasoning nodes call frontier_model. Every pattern above already does this — router_llm and planner_llm both wrap small_model.

In plain English

It's like a hospital: you don't need the head surgeon to take your temperature. A nurse (cheap, fast model) handles the simple stuff; the surgeon (expensive, powerful model) only gets called in for the hard parts. This saves both time and money without losing quality where it matters.

One model, every step

Simple to write, but every intent check and schema fill pays frontier latency and cost.

Routed per node

Cheap model classifies and extracts; frontier model reasons. Same graph, lower bill.

Strict tool contracts

The handbook's rule — no open-ended natural language straight into a database — is enforced with Pydantic schemas on every tool, plus a risk tag that later powers the policy gate.

In plain English

Imagine a form with labeled boxes ("Name: ___", "Amount: ___") instead of a blank sheet of paper. The labeled form makes it much harder to accidentally write something dangerous or nonsensical, because each box only accepts one specific type of answer. A Pydantic model (like RefundArgs below) is exactly that: a form the AI must fill in correctly before our code will even look at it.

tool_contracts.pypython
from pydantic import BaseModel, Field
from langchain_core.tools import StructuredTool

# This is our strict "form." Every field has a name, a type, and a
# description so the AI knows exactly what to put in each box.
class RefundArgs(BaseModel):
    invoice_id: str = Field(description="Exact invoice identifier, e.g. INV-2291")
    # gt=0 means "must be greater than zero" — Pydantic will reject
    # a negative or zero refund amount automatically, before our code runs.
    amount_cents: int = Field(gt=0, description="Refund amount in integer cents")
    reason: str = Field(description="Short customer-facing reason")

def _issue_refund(invoice_id: str, amount_cents: int, reason: str) -> dict:
    # This is the REAL function that would talk to a payments system.
    # Notice it only ever receives clean, validated values — never raw
    # free-form text from the model.
    return {"status": "pending_approval", "invoice_id": invoice_id, "amount_cents": amount_cents}

# StructuredTool.from_function wraps our plain Python function and
# attaches the RefundArgs "form" to it, so LangChain automatically
# checks the AI's answer against that form before calling our function.
issue_refund = StructuredTool.from_function(
    func=_issue_refund,
    name="issue_refund",
    description="Propose a refund for an invoice. Requires human approval before executing.",
    args_schema=RefundArgs,
)

# We tag this tool as "high-write" risk. The policy gate in Chapter 4
# will check this tag before letting the tool actually run.
issue_refund.metadata = {"risk": "high-write"}

Decoupled state and memory

The handbook separates active-session state from durable memory. In LangGraph, a checkpointer owns the former; a separate store — vector or key-value — owns the latter, and a node reads from it explicitly rather than dumping everything into context.

In plain English

Think of state as your short-term memory during one conversation — like remembering what you said five minutes ago. Think of memory as your long-term memory — like remembering your friend's birthday even months later, across totally different conversations. We keep these in separate storage so a long chat doesn't get confused with facts learned in a completely different session.

state_and_memory.pypython
# A "checkpointer" saves progress for THIS conversation, step by step
# (like a video game auto-save), so we can pause and resume it later.
from langgraph.checkpoint.postgres import PostgresSaver

# A "store" saves information that should last FOREVER, across many
# different conversations — like a saved preference or a fact we
# learned about the user.
from langgraph.store.postgres import PostgresStore

checkpointer = PostgresSaver.from_conn_string("postgresql://localhost/agent_state")
long_term_store = PostgresStore.from_conn_string("postgresql://localhost/agent_memory")

def recall_preferences(state, *, store):
    # A "namespace" is like a labeled folder — here, one folder per user.
    namespace = ("user_prefs", state["user_id"])
    # .search(...) looks through that folder for things related to the
    # user's latest message, and returns the closest 3 matches.
    items = store.search(namespace, query=state["messages"][-1].content, limit=3)
    return {"retrieved_memory": [i.value for i in items]}

# When we .compile() the graph, we plug in BOTH storage systems:
# checkpointer for "what happened in this exact session,"
# store for "what do we permanently remember about this user."
app = graph.compile(checkpointer=checkpointer, store=long_term_store)

# thread_id identifies ONE specific conversation. Using the same
# thread_id later lets us pick that exact conversation back up.
app.invoke({"messages": [...], "user_id": "u_1029"},
           config={"configurable": {"thread_id": "session-88"}})

Raw trace logs and inactive sessions belong in cold storage (S3/GCS), not in checkpointer — keep it scoped to what a live run actually needs.

Trace-level evaluations

Every metric the handbook lists — intent accuracy, tool selection, retrieval hit rate, refusal compliance, cost — is a per-step judgment, so evaluation runs against the full LangSmith trace, not just the final message.

In plain English

Grading a math test only by the final answer would miss it if a student got the right answer through totally wrong steps (or got lucky). Trace-level evaluation is like a teacher checking every line of work, not just the answer at the bottom — did the agent pick the right tool? Did it use too many expensive steps? Each of those gets its own grade.

trace_eval.pypython
from langsmith import Client, traceable
from langsmith.evaluation import evaluate

client = Client()

# @traceable just means "record what this function does so we can look
# at it later in LangSmith's dashboard."
@traceable(name="tool_selection_correct")
def tool_selection_eval(run, example) -> dict:
    # "example" holds the CORRECT answer we expect for this test case.
    expected_tool = example.outputs["expected_tool"]
    # "run" holds what our agent actually did. We pull out the names of
    # every tool it called during this run.
    called_tools = [s.name for s in run.child_runs if s.run_type == "tool"]
    # The score is simply: did it call the tool we expected? (True/False)
    return {"key": "tool_selection", "score": expected_tool in called_tools}

@traceable(name="task_completion_cost")
def cost_eval(run, example) -> dict:
    # Add up every token used by every AI model call inside this run —
    # this tells us roughly how much the whole task cost.
    total_tokens = sum(r.total_tokens or 0 for r in run.child_runs if r.run_type == "llm")
    return {"key": "cost_tokens", "score": total_tokens}

# evaluate(...) runs our agent against a whole set of saved test cases
# (a "dataset"), and grades every single run using our two eval functions.
results = evaluate(
    lambda inputs: react_agent.invoke(inputs),
    data="agent-regression-set",       # a LangSmith dataset of {input, expected_tool} pairs
    evaluators=[tool_selection_eval, cost_eval],
    experiment_prefix="react-v1",
)

The policy gate — suggest, validate, approve, execute

LangGraph's interrupt maps directly onto the handbook's four-step pipeline. The graph pauses right before a high-risk tool executes, a human reviews the exact validated arguments, and only an explicit resume lets it proceed.

In plain English

This is the same idea as a bank teller who can suggest a large withdrawal, but a manager has to physically approve it before the money actually moves. The AI is only ever allowed to suggest a risky action like a refund — a person has to click "approve" before anything real happens. interrupt(...) literally pauses the program and waits for that click.

1 · LLM
Infers intent, proposes issue_refund(...)
2 · Code
Validates ownership & business rules, deterministically
3 · Human
Reviews the rendered proposal, clicks approve
4 · API
Executes the write, returns the result
policy_gate.pypython
from langgraph.types import interrupt, Command
from langgraph.checkpoint.memory import MemorySaver

def validate(state):
    # Step 2: this is plain, boring, predictable code — NOT the AI model.
    # It checks a real business rule: does this user actually own the
    # invoice they're asking to refund?
    call = state["proposed_call"]
    if call["invoice_id"] not in owned_invoices(state["user_id"]):
        return {"denied": True, "reason": "invoice not owned by user"}
    return {"validated": True}

def human_approval(state):
    if state.get("denied"):
        # If validation already failed, don't even bother asking a human.
        return {"executed": False}
    # interrupt(...) freezes the graph right here and shows this
    # information to a person in our app's UI. Nothing after this line
    # runs until a human responds.
    decision = interrupt({
        "action": "issue_refund",
        "args": state["proposed_call"],
    })
    return {"approved": decision == "approve"}

def execute(state):
    if not state.get("approved"):
        return {"executed": False}
    # Only NOW, after a real human clicked "approve", do we actually
    # call the function that moves real money.
    return {"executed": True, "result": _issue_refund(**state["proposed_call"])}

graph.add_node("validate", validate)
graph.add_node("human_approval", human_approval)
graph.add_node("execute", execute)
graph.add_edge("validate", "human_approval")
graph.add_edge("human_approval", "execute")

# MemorySaver lets the graph "remember" that it's paused here, so it can
# sit and wait (even for hours) until we resume it.
gated_app = graph.compile(checkpointer=MemorySaver())

# --- resuming after a human clicks "approve" in your UI ---
# Command(resume="approve") is how we "unfreeze" the exact paused graph
# and tell it what the human decided.
gated_app.invoke(Command(resume="approve"), config={"configurable": {"thread_id": "t-1"}})
Non-negotiable No model is ever the last step before a write. If validate or human_approval is skipped for latency, the gate no longer exists — it's decoration.

Isolating untrusted input

Retrieved documents and tool output are treated the same as user text: never interpolated into a shell, SQL string, or eval(). A thin sanitizing node sits between any retrieval step and the agent.

In plain English

Imagine finding a note stuck inside a library book that says "give the person holding this note $100." Obviously you wouldn't just follow it! But an AI reading a webpage or document might accidentally treat hidden instructions inside that document as real commands. This code looks for suspicious phrases (like "ignore all instructions") in anything we fetch from outside, and blanks it out before the AI ever reads it.

isolate_input.pypython
import re

# This is a "regular expression" — a pattern for matching suspicious text.
# re.I means "ignore uppercase vs lowercase" when matching.
INJECTION_MARKERS = re.compile(r"(ignore (all|previous) instructions|system prompt:)", re.I)

def sanitize_retrieved(state):
    cleaned = []
    # Go through every document we pulled in from search or a database.
    for doc in state["retrieved_docs"]:
        # .search(...) checks if any suspicious phrase appears in this document.
        if INJECTION_MARKERS.search(doc.page_content):
            # If we find one, replace the whole text with a safe warning
            # message instead of passing the sneaky instructions along.
            doc.page_content = "[content withheld: embedded instruction detected]"
        cleaned.append(doc)
    return {"retrieved_docs": cleaned}

graph.add_node("sanitize", sanitize_retrieved)
graph.add_edge("retrieve", "sanitize")
graph.add_edge("sanitize", "agent")   # the agent node only ever sees sanitized text

This is a pattern-matching floor, not a guarantee — pair it with least-privilege tool scopes so a successful injection still can't reach a high-risk tool without passing the policy gate above.

Neo4j & GraphRAG — following relationships, not just similar text

The vector store in the Agentic RAG section is great at "find text that means something similar to my question." It's much weaker at questions that need hopping between facts — "who approved the invoice that the finance manager flagged?" That's what a graph database like Neo4j is built for, and GraphRAG is the pattern of retrieving over that graph instead of (or alongside) a vector store.

In plain English

A vector store is like a filing cabinet: every document sits in its own folder, and you find folders that "sound similar" to what you're looking for. A graph database is more like a corkboard covered in sticky notes connected by pieces of string — each note is a fact ("Invoice #4471", "Priya", "Finance team"), and each string is a relationship ("APPROVED_BY", "MEMBER_OF"). To answer a question like "who's on the same team as whoever approved this invoice?", you don't just need one note — you need to follow the strings from note to note. That's exactly what a graph database is good at, and a filing cabinet isn't.

Cypher is Neo4j's query language — think of it as the graph-database version of SQL. Instead of writing Cypher ourselves, we'll let the AI translate a plain-English question into Cypher automatically.

    url="bolt://localhost:7687",
    username="neo4j",
    password="password",

# GraphCypherQAChain does three jobs in a row, automatically:
#   1. Turn the plain-English question into a Cypher query
#      (e.g. "who approved invoice 4471?" becomes a graph query
#      that follows the APPROVED_BY string from that note).
#   2. Actually run that query against the real database.
#   3. Turn the raw rows it gets back into a normal sentence.

    llm=frontier_model,
    graph=graph_db,
    verbose=True,
    # The chain writes its OWN Cypher, and Cypher can technically
    # create or delete data, not just read it. This flag is Neo4j's way

    # safer fix is a database USER that only has read permission at
    # all -- the same "least privilege" idea from Chapter 4.
    allow_dangerous_requests=True,
)

def graph_lookup_node(state):
    # Take the user's latest message as the question to look up.
    question = state["messages"][-1].content
    # .invoke(...) runs all three steps above and hands back the answer.
    answer = cypher_chain.invoke({"query": question})["result"]
    return {"messages": [("assistant", answer)]}
Combining both: route to whichever retrieval fits the question

Real systems usually need both kinds of lookup. We can reuse the same "let a cheap model decide" trick from the Multi-agent pattern: read the question, and decide whether it's a "find similar text" question (send it to the vector store) or a "follow the relationships" question (send it to the graph).

    route = router_llm.invoke(

Neither retrieval method is "better" in general — a vector store wins for "find the paragraph that explains X," a graph wins for "trace the chain of connections between X and Y." GraphRAG just means giving the agent both and letting it (or a router) pick.

MCP servers — one standard plug for every tool

Every tool we've built so far (get_stock_price, issue_refund, the retriever) was custom Python code written just for this agent. MCP (Model Context Protocol) is a standard way to package tools and data sources so any agent, in any framework, can connect to them without custom glue code for each one.

In plain English

Before USB-C existed, every phone brand had its own charger cable, and a charger for one phone usually didn't fit another. USB-C fixed that: one plug shape works everywhere. MCP is the USB-C of AI tools — instead of writing brand-new glue code every time you want to connect your agent to Slack, GitHub, a filesystem, or a database, an MCP server exposes those tools in one standard way, and any MCP-compatible agent can just plug in and use them immediately.

An MCP server is a small program that "hosts" a set of tools (or documents, called "resources") and answers requests for them in the standard MCP format. Your agent acts as an MCP client that connects to one or more of these servers and asks, "what tools do you have?" before using them.

The Agentic FDE — the person who makes the graph fit the customer

Everything above this section is a pattern that works in a tutorial. Getting one of these graphs to survive contact with a real customer's messy tools, real data, and real risk tolerance is a different job — usually done by a Forward Deployed Engineer (FDE). It's an engineering role, not a support or sales role: the FDE writes the actual graph code, wires the actual tools, and sets the actual policy gate for one specific deployment.

In plain English

Think of the difference between buying a cabinet from a furniture store and hiring a carpenter to build one into your actual kitchen. The store's cabinet is designed to fit an "average" kitchen reasonably well. The carpenter shows up, measures your actual walls, notices your outlet is in a weird spot, and builds something that fits your kitchen exactly — then teaches you how to open and close it.

A Forward Deployed Engineer is the carpenter. The five patterns and the Neo4j/MCP pieces on this page are the store-bought cabinet — solid, general-purpose building blocks. The FDE's job is to sit with one real customer, figure out which blocks actually fit their kitchen (their tools, their data, their comfort with risk), and bolt them together correctly.

What the role covers, roughly in order

01

Embed and discover

Sit with the people who will actually use the agent before writing any code. A support team's real workflow rarely matches the clean diagram in a slide deck — the FDE's first job is finding out where it doesn't.

02

Prototype against the real thing

Stand up a thin version of one of the patterns above — usually ReAct or the Multi-agent supervisor — pointed at sandboxed copies of the customer's actual tools, within days rather than months, so everyone can react to something real instead of a spec.

03

Wire the real integrations

Swap the mock get_stock_price-style tools for the customer's actual systems — an internal MCP server, their specific Neo4j schema, their ticketing API — and handle whatever those real systems do that the docs didn't mention.

04

Set the risk bar with the customer, not for them

Decide, together with the customer's own compliance or ops lead, which tools count as "high-write" and need the Chapter 4 policy gate. A hospital and a marketing team draw that line in very different places — the FDE doesn't get to assume the answer.

05

Instrument, then hand off

Wire up trace-level evals (Chapter 3) scoped to this specific deployment, document what was built and why, and transfer real ownership to the customer's own engineers or the platform's ongoing support team — an FDE who never leaves isn't forward-deployed, just deployed.

How it differs from a traditional FDE

Forward-deployed engineering existed long before LLMs — historically it meant embedding with a customer to integrate and customize existing software. An agentic FDE keeps all of that and adds a layer that's specific to agents.

Traditional FDE

Integrates existing software against a customer's APIs and data; writes deterministic glue code (ETL jobs, dashboards, custom reports) with predictable, testable outputs.

Agentic FDE

All of the above, plus: chooses which graph pattern fits the workflow, tunes prompts and structured-output schemas, decides what needs a human-approval gate, and keeps watching eval scores after launch because the same graph can quietly get worse as the customer's data drifts.

Why this role exists at all Nothing on this page is customer-specific by default — the patterns, the tool contracts, the policy gate are all generic. Someone has to decide, for one real deployment, which pattern to use, which tools are safe to automate, and where the human has to stay in the loop. That judgment call is the job; the code is just the output of it.

CI/CD for agents — why "it compiles" isn't enough

Normal CI/CD asks "does the code run without crashing, and do the tests pass?" That's necessary for an agent too, but it's not sufficient: an agent can run perfectly and still pick the wrong tool, write a rude reply, or quietly get worse after someone tweaks a prompt. Shipping agents safely means gating every change on the trace-level evals from Chapter 3, not just on unit tests.

In plain English

A calculator app is easy to test: 2 + 2 must always equal 4, every single time, forever. An AI agent is more like a new employee — even a great one won't phrase things identically every time, and "good enough" is a judgment call, not a single right answer. So instead of asking "did it produce the exact same output as before?", agent testing asks "did it still pass enough of our practice questions?" — the same regression suite you'd use to grade a student, run automatically on every change.

CI (Continuous Integration) means: every time someone proposes a code change, a robot automatically runs all our checks before a human even looks at it. CD (Continuous Deployment) means: once those checks pass, the change can go live automatically, without someone manually copying files onto a server.

Traditional CI/CD

Runs unit tests and linters. A change either passes (deterministic, same input always gives the same output) or fails. Pass → merge.

Agentic CI/CD

Runs the same unit tests on deterministic code (tool contracts, the policy gate), plus a LangSmith eval suite on the agent's behavior. Pass → merge, but "pass" means "score stayed at or above the last known-good baseline," not "identical output."

# "sys" lets us control the program's exit code -- 0 means "everything
# was fine," anything else means "something failed." GitHub Actions
# reads this exit code to decide whether to block the merge.
import sys
import argparse
from langsmith.evaluation import evaluate
from react_agent import react_agent          # the graph we built in Pattern 01
from evals import tool_selection_eval, cost_eval   # from Chapter 3

def main():
    # argparse lets us pass settings in from the command line, like
    # "--min-score 0.85", instead of hard-coding them in the file.
    parser = argparse.ArgumentParser()
    parser.add_argument("--dataset", required=True)
    parser.add_argument("--min-score", type=float, required=True)
    args = parser.parse_args()

    # Run the SAME evaluation harness from Chapter 3, but now as part of
    # an automatic check instead of something a person runs by hand.
    results = evaluate(
        lambda inputs: react_agent.invoke(inputs),
        data=args.dataset,
        evaluators=[tool_selection_eval, cost_eval],
        experiment_prefix="ci-check",
    )

    # .to_pandas() turns the results into a table we can easily average.
    scores = results.to_pandas()["feedback.tool_selection"]
    average_score = scores.mean()
    print(f"Average tool-selection score: {average_score:.2f} (need >= {args.min_score})")

    if average_score < args.min_score:
        print("REGRESSION DETECTED -- blocking this change.")
        # A non-zero exit code tells GitHub Actions "this step failed,"
        # which stops the pull request from being merged.
        sys.exit(1)

    print("Eval gate passed.")
    sys.exit(0)

if __name__ == "__main__":
    main()

--min-score 0.85 is a judgment call, not a magic number — set it from your own historical eval runs, the same way a teacher sets a passing grade based on how the class has actually performed before, not an arbitrary ideal.

AgentOps — watching, versioning, and rolling back a live agent

"DevOps" is the discipline of running normal software reliably in production. AgentOps is the same idea applied to agents, with three extra concerns a normal web app doesn't have: the agent's behavior can drift even when the code hasn't changed (because the underlying model provider updated something), every version needs to be traceable back to an exact prompt + graph + model combination, and rollback has to be instant because a misbehaving agent can take real actions, not just show a broken webpage.

In plain English

Running a website, if nothing about your code changes, the website keeps working the same way forever. Running an agent is more like managing a delivery driver who works for a company you don't control — one day their GPS app updates and suddenly they take a different route, even though you didn't change anything on your end. AgentOps is: keep watching the driver's routes even after everything "looks" unchanged, know exactly which map version they were using on any given day, and have a fast way to tell them "go back to the old route" if the new one starts causing problems.

1. Monitor: log every step, not just the final answer

The same idea as trace-level evals in Chapter 3, but running continuously in production instead of on a fixed test set.

agentops_callback.pypython
# A "callback handler" is a set of functions LangChain automatically
# calls at key moments -- "a tool just started," "a tool just
# finished," "the model just replied." We use these hooks to record
# what happened, without changing how the agent itself works.
from langchain_core.callbacks import BaseCallbackHandler
import time

class AgentOpsLogger(BaseCallbackHandler):
    def on_tool_start(self, serialized, input_str, **kwargs):
        # Remember when this tool call began, so we can measure how
        # long it took once it finishes.
        self._start_time = time.time()

    def on_tool_end(self, output, **kwargs):
        duration = time.time() - self._start_time
        # In a real system this would write to a monitoring database
        # (e.g. Datadog, Prometheus, or LangSmith itself) instead of
        # just printing -- the point is: every tool call gets recorded
        # with how long it took and whether it succeeded.
        print(f"[agentops] tool finished in {duration:.2f}s")

    def on_tool_error(self, error, **kwargs):
        # A spike in tool errors is often the FIRST sign something
        # upstream changed (an API updated its response format, for
        # example) -- long before anyone notices from user complaints.
        print(f"[agentops] TOOL ERROR: {error}")

# Attach the logger when we run the agent, exactly like plugging a
# recording device into a machine without opening it up.
react_agent.invoke(
    {"messages": [("user", "Is ACME close to its 52-week high?")]},
    config={"callbacks": [AgentOpsLogger()]},
)

A "version" of an agent isn't just the code — it's the code, the exact prompt text, the exact model name, and the exact graph shape, all together. Change any one of those and you have a new version that deserves its own tag.

3. Roll back fast: canaries and a kill switch

Ship a new agent version to a small slice of real traffic first (a "canary," like the caged canaries miners once used to detect bad air before it reached them), watch the eval scores on just that slice, and only widen the rollout once they hold up. And always keep an emergency off-switch that doesn't depend on redeploying code.

canary_and_killswitch.pypython
import random

# In a real system this flag would live somewhere you can flip instantly
# -- a feature-flag service or a small database row -- NOT a value
# baked into the code, because flipping code requires a new deployment,
# and the whole point of a kill switch is that it works even faster
# than that.
KILL_SWITCH_ENABLED = False
CANARY_TRAFFIC_PERCENT = 10   # only 10% of requests try the new version

def choose_agent_version():
    if KILL_SWITCH_ENABLED:
        # When the kill switch is on, skip the agent entirely and hand
        # back a safe, boring, pre-written message instead -- the
        # agent equivalent of "system temporarily under maintenance."
        return None
    # random.randint(1, 100) picks a random whole number from 1 to 100.
    # Roughly CANARY_TRAFFIC_PERCENT of the time, this sends the
    # request to the new version instead of the trusted old one.
    if random.randint(1, 100) <= CANARY_TRAFFIC_PERCENT:
        return "react_agent_v2"   # the new, less-proven version
    return "react_agent_v1"       # the old, trusted version

def handle_request(user_message: str) -> str:
    version = choose_agent_version()
    if version is None:
        return "We're temporarily unable to handle this automatically -- a person will follow up shortly."
    agent = react_agent_v2 if version == "react_agent_v2" else react_agent_v1
    result = agent.invoke({"messages": [("user", user_message)]},
                           config={"metadata": {"graph_version": version}})
    return result["messages"][-1].content

Because every request is tagged with graph_version (Monitor, above), you can compare the canary's eval scores against the trusted version's in near real time, and turn the canary off the moment it looks worse — without touching a single line of deployed code.

Observability — seeing inside the graph while it runs

AgentOps (Chapter 7) covers monitoring at the level of "is this deployment healthy overall." Observability is one level deeper: for any single request, can you reconstruct exactly what happened, in order, across every node, tool call, and model call — including the ones inside a nested subgraph? Without this, debugging a bad answer means guessing.

In plain English

Imagine a package that got lost in the mail. "Tracking" tells you it left the warehouse, passed through three sorting centers, and is now at the local depot — a timestamped trail of exactly where it went. Observability is that tracking number for a single agent request: a "trace" made of nested "spans," one per step, each with its own start time, end time, and details, so when something goes wrong you can see exactly which step it happened at instead of just "the final answer was wrong."

OpenTelemetry is an open, vendor-neutral standard for producing these traces, so the same instrumentation can be viewed in LangSmith, Grafana, Datadog, or any other tool that understands the format — you're not locked into one vendor's dashboard.

observability_setup.pypython
# pip install opentelemetry-sdk opentelemetry-exporter-otlp

from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter

# A TracerProvider is the factory that creates every trace in this
# program. BatchSpanProcessor collects finished spans and ships them
# in batches (rather than one at a time) to wherever we're storing
# them, which is much more efficient at real traffic volume.
provider = TracerProvider()
provider.add_span_processor(
    BatchSpanProcessor(OTLPSpanExporter(endpoint="http://otel-collector:4317"))
)
trace.set_tracer_provider(provider)

# "agent-service" here is just a label so that, later, in a dashboard
# with traces from many different services, you can filter to just ours.
tracer = trace.get_tracer("agent-service")

def traced_node(fn):
    """A decorator that wraps any LangGraph node function so every call
    to it automatically becomes one labeled span in the trace."""
    def wrapper(state):
        # start_as_current_span opens a new span named after the
        # function, and automatically closes it (recording how long it
        # took) when the "with" block ends -- even if an error happens.
        with tracer.start_as_current_span(fn.__name__) as span:
            # Attributes are extra labeled facts attached to this one
            # span -- here, which conversation this request belongs to.
            span.set_attribute("thread_id", state.get("thread_id", "unknown"))
            result = fn(state)
            span.set_attribute("output_keys", list(result.keys()))
            return result
    return wrapper

@traced_node
def agent_node(state):
    return {"messages": [frontier_model.invoke(state["messages"])]}

RAGAS — grading a RAG pipeline on more than "did it match"

The eval gate in Chapter 7 checked whether the agent called the right tool. For a RAG pipeline specifically (Agentic RAG, GraphRAG), you also need to know: did the retrieved documents actually contain the answer, and did the generated answer actually stick to what those documents said? RAGAS (Retrieval-Augmented Generation Assessment) is a library built specifically to score exactly that, without needing a human to read every answer.

In plain English

Imagine grading an open-book essay on four separate questions: Did the student actually use the book (not just make things up)? Did their answer actually address the question asked? Did they open the right pages of the book at all? And did they miss any pages they really needed? RAGAS turns those four questions into four numeric scores — faithfulness, answer relevancy, context precision, and context recall — computed automatically using another LLM as the "grader."

ragas_eval.pypython

        "How long do I have to return something?",
    ],

        ["Our refund policy allows returns within 30 days of purchase."],

Reranking — casting a wide net, then narrowing it precisely

The vector search in the Agentic RAG section returns documents ranked by embedding similarity, which is fast but approximate. A reranker takes a larger first batch of candidates and re-scores each one much more carefully by looking at the actual question and actual document together, then keeps only the best few.

In plain English

Think of hiring for a job. Step one, a recruiter skims a thousand resumes quickly and picks the 50 that seem roughly relevant — fast, but not super precise (that's the vector search: "cast a wide net"). Step two, a hiring manager reads those 50 much more carefully, side by side with the actual job description, and picks the best 5 to interview (that's the reranker: slower per-item, but far more accurate, and only worth doing once you've already narrowed the pool down).

A cross-encoder is the technical name for the reranker's approach: instead of comparing two separate number-lists (like a vector search does), it reads the question and one document together as a single input, which is much more accurate but too slow to run on thousands of documents — only practical once you're down to a few dozen candidates.

reranking.pypython
# pip install cohere
import cohere

co = cohere.Client(api_key="...")

def rerank_node(state):
    query = state["messages"][0].content
    # "candidates" is the WIDE first pass -- say, the top 20 documents
    # from the plain vector search in the Agentic RAG section.
    candidates = state["retrieved_docs"]

    # .rerank(...) sends the query and every candidate document to a
    # cross-encoder model, which scores each pair, then returns the
    # candidates re-sorted with the best matches first.
    reranked = co.rerank(
        query=query,
        documents=[d.page_content for d in candidates],
        top_n=4,                          # keep only the best 4 after reranking
        model="rerank-english-v3.0",
    )
    # reranked.results gives us back indices INTO our original list,
    # in the new, better order -- so we rebuild our document list using
    # those indices.
    ordered = [candidates[r.index] for r in reranked.results]
    return {"retrieved_docs": ordered}

# Slot this in between retrieval and generation in the Agentic RAG graph:
graph.add_edge("retrieve", "rerank")
graph.add_edge("rerank", "generate")
Why not just rerank everything, always? Cross-encoders are meaningfully slower per document than a vector search. The pattern is always "retrieve wide, rerank narrow" — e.g. fetch the top 20-50 candidates cheaply, then spend the expensive reranking step on just those, never on your whole document collection.

Redis semantic caching — skip the model call entirely when you can

A normal cache only helps if the exact same request comes in twice ("get user 42" → same key every time). Two people rarely type the exact same sentence, even when they're asking the exact same thing — "how do refunds work?" vs. "what's your return policy?" A semantic cache matches on meaning, using embeddings, so both questions can hit the same cached answer.

In plain English

A normal cache is like a filing cabinet where you can only find a folder if you know its exact label. A semantic cache is more like a librarian who remembers "someone asked something very similar to this last week" even if the wording was completely different, and just hands you the answer they gave last time instead of looking it up all over again. This saves both money (no new model call) and time (answers come back instantly).

redis_semantic_cache.pypython
# pip install langchain-redis redis
import langchain
from langchain_community.cache import RedisSemanticCache
from langchain_openai import OpenAIEmbeddings

# Every future model call in this program will first check this cache.
langchain.llm_cache = RedisSemanticCache(
    redis_url="redis://localhost:6379",
    embedding=OpenAIEmbeddings(),
    # score_threshold controls how "close" a new question has to be to
    # a cached one to count as a match. Lower = stricter (fewer, safer
    # cache hits); higher = looser (more hits, but more risk of
    # returning a stale answer to a subtly different question).
    score_threshold=0.2,
)

# From here on, this call automatically checks the cache first:
answer_1 = frontier_model.invoke("How do refunds work?")            # cache MISS -> calls the model, then saves the answer
answer_2 = frontier_model.invoke("What's your return policy?")      # close enough in meaning -> cache HIT, no model call at all
redis_tool_cache.pypython
# Semantic caching fits natural-language QUESTIONS. Tool calls have
# exact, structured arguments, so a plain (non-semantic) cache keyed on
# those exact arguments works well and is even simpler.
import redis, json, hashlib

r = redis.Redis(host="localhost", port=6379, decode_responses=True)

def cached_tool_call(tool_name: str, args: dict, fn, ttl_seconds=300):
    # Build one unique, deterministic key out of the tool name and its
    # exact arguments -- same tool + same args always produces the same key.
    raw_key = f"{tool_name}:{json.dumps(args, sort_keys=True)}"
    cache_key = hashlib.sha256(raw_key.encode()).hexdigest()

    cached = r.get(cache_key)
    if cached is not None:
        return json.loads(cached)   # cache hit -- skip calling the real tool

    result = fn(**args)
    # setex = "set with expiry" -- this entry disappears automatically
    # after ttl_seconds, so a stock price cached 5 minutes ago doesn't
    # get served forever as if it were still current.
    r.setex(cache_key, ttl_seconds, json.dumps(result))
    return result

# Usage: cached_tool_call("get_stock_price", {"ticker": "ACME"}, get_stock_price.func)

Pick a ttl_seconds that matches how quickly the underlying data actually changes — a stock price tool might cache for 30 seconds, a company policy lookup might safely cache for a day.

Token optimization — the same answer for a smaller bill

Every technique in this section reduces either how many tokens get sent to the model, how often the model gets called at all, or which model handles the call — without changing what the user experiences.

In plain English

You're billed by the model provider roughly the way a taxi bills you by distance traveled — the more text you send and receive, the more it costs. Token optimization is just "take a shorter route to the same destination": trim what doesn't need to be there, reuse work you've already paid for, and only hire the expensive expert when the cheap one genuinely can't do the job.

1. Trim conversation history instead of sending the whole transcript

trim_history.pypython
from langchain_core.messages import trim_messages

def trim_history_node(state):

    # it. trim_messages keeps the most recent messages that fit inside
    # a token budget, dropping older ones from the front.
    trimmed = trim_messages(
        state["messages"],

    )
    return {"messages": trimmed}

2. Summarize old turns instead of deleting them outright

3. Route to the cheapest model that can still do the job

Already covered in depth in Chapter 3 — worth repeating here because it's usually the single biggest token-cost lever available: classification, extraction, and routing steps rarely need the frontier model.

4. Cache aggressively — a cached answer costs zero new tokens

The Redis semantic cache above is a token-optimization technique as much as it's a latency one: a cache hit means the model is never called at all for that turn.

5. Truncate large tool outputs before they reach the model

truncate_tool_output.pypython
def truncate_tool_result(raw_result: str, max_chars: int = 2000) -> str:
    # A tool that returns a huge JSON blob or a full webpage can burn
    # thousands of tokens the model doesn't actually need. Truncating
    # (and, where possible, asking the tool itself to return only the
    # relevant fields) keeps the context small without losing the
    # information that actually matters.
    if len(raw_result) <= max_chars:
        return raw_result
    return raw_result[:max_chars] + "\n...[truncated]"

6. Reuse a stable system prompt so providers can cache it

Many model providers now support some form of prompt/context caching, where a long, unchanging prefix (like a big system prompt or a set of tool definitions) is billed at a reduced rate on repeat calls, as long as that exact prefix is reused rather than rebuilt slightly differently each time. Keep your system prompt identical across calls (build the varying, per-request part separately) to make this discount actually apply — check your specific provider's current documentation for the exact mechanism.

7. Ask for structured output instead of a free-form essay

A tool call or a Pydantic-typed response (Chapter 3) is naturally shorter than asking the model to "explain your reasoning in full sentences" — you're only paying for the fields you actually need, not for the model's narration around them.

Security beyond prompt injection

Chapter 4 covered the policy gate and basic input isolation. A production agent touches several more classic security concerns — most of them not new to AI at all, just newly relevant because an agent can now trigger them automatically instead of a human doing it by hand.

In plain English

Giving an agent tools is a lot like giving a new employee a company laptop, a badge, and a set of keys. You wouldn't hand a brand-new intern a master key to every door in the building "just in case" — you'd give them access to exactly the rooms their job requires, log when they use it, and make sure they can't accidentally (or be tricked into) wandering somewhere they shouldn't. Everything below is that same common-sense caution, applied to code.

1. Never hardcode secrets — and scope credentials per tool

secrets.pypython
import os

2. Block SSRF — don't let a tool fetch whatever URL it's handed

ssrf_safe_fetch.pypython
import ipaddress, socket
from urllib.parse import urlparse

# SSRF (Server-Side Request Forgery) is when a tool that fetches URLs
# gets tricked into fetching something internal instead -- like your
# cloud provider's metadata service, which can leak credentials, or an
# internal admin panel that was never meant to be reachable from here.
ALLOWED_DOMAINS = {"api.company.com", "docs.company.com"}

def safe_fetch(url: str) -> str:
    parsed = urlparse(url)
    if parsed.scheme not in ("http", "https"):
        raise ValueError("blocked: unsupported scheme")
    if parsed.hostname not in ALLOWED_DOMAINS:
        raise ValueError("blocked: domain not on allowlist")

    # Even an allowed-looking hostname could resolve to an internal IP
    # address (this is a common bypass trick), so check the ACTUAL
    # resolved address too, not just the domain name that was typed.
    resolved_ip = socket.gethostbyname(parsed.hostname)
    ip = ipaddress.ip_address(resolved_ip)
    if ip.is_private or ip.is_loopback or ip.is_link_local:
        raise ValueError("blocked: resolves to an internal network address")

    import requests
    return requests.get(url, timeout=5).text

3. Rate-limit per user, not just per API key

rate_limit.pypython
import time

# A simple "token bucket": each user starts with a small budget of
# requests and it slowly refills over time -- so one user spamming
# requests can't drown out everyone else or run up an enormous bill.
request_log = {}   # user_id -> list of recent request timestamps

def is_rate_limited(user_id: str, max_requests=20, window_seconds=60) -> bool:
    now = time.time()
    recent = [t for t in request_log.get(user_id, []) if now - t < window_seconds]
    request_log[user_id] = recent
    if len(recent) >= max_requests:
        return True   # too many requests in this window -- block it
    recent.append(now)
    return False
Non-negotiable Least privilege, secrets management, and SSRF protection aren't "extra hardening" for later — a single tool with a broad credential and no URL allowlist is enough to turn a successful prompt injection (Chapter 4) into a real data breach instead of a harmless refused request.

    )
    return result.stdout or result.stderr
This example is a start, not a finish line A bare subprocess call still shares the same filesystem, network, and kernel as your main application. Production code-execution tools should run inside something with a real security boundary — a container with no network access and a read-only filesystem, or a microVM (like Firecracker or gVisor) — precisely because "untrusted code an AI wrote" deserves the same isolation as "untrusted code a stranger on the internet submitted."

Authentication & authorization in a multi-agent MCP RAG system

Put together everything on this page — the supervisor pattern (Ch.2), Agentic RAG (Ch.2), Neo4j/MCP (Ch.5) — and you get a real architecture: a supervisor routing to specialist agents, each of which retrieves from documents and calls tools, some of them over MCP. None of that is safe to expose to real users until you can answer two separate questions correctly, every single time: who is making this request, and what are they specifically allowed to see or do.

In plain English

Authentication (AuthN) is the ID check at the front door of a building — proving you are who you say you are. Authorization (AuthZ) is what happens after you're inside — your keycard opens the lobby and your own office, but not the server room or someone else's desk. A system can authenticate someone perfectly and still be completely broken if it then lets them (or an agent acting for them) open every door in the building.

In a multi-agent system, this gets harder because the "person walking through the building" is now several agents handing a request to each other. If the supervisor checks ID once at the door and then every specialist agent and every MCP server just trusts "the supervisor already checked," one compromised or confused agent can now impersonate the user everywhere. The fix, covered below, is to keep checking at every door — plus never handing any one agent more keys than its own job requires.

1. Authenticate the user once, at the edge

Before any node in the graph runs, verify the caller's identity token (typically a JWT from an OAuth2/OIDC provider like Auth0, Okta, or Keycloak) and turn it into structured claims the rest of the graph can trust.

authn_node.pypython
# pip install pyjwt cryptography
import jwt
from jwt import PyJWKClient
from langgraph.graph import StateGraph, MessagesState, START, END

ISSUER = "https://your-tenant.auth0.com/"
AUDIENCE = "https://api.yourcompany.com/agents"

# PyJWKClient fetches (and caches) the identity provider's public keys,
# so we can verify a token's signature without storing any secret
# ourselves -- the provider signed it, we just check the signature.
jwks_client = PyJWKClient(f"{ISSUER}.well-known/jwks.json")

def verify_user_token(bearer_token: str) -> dict:
    signing_key = jwks_client.get_signing_key_from_jwt(bearer_token)
    # jwt.decode both verifies the signature AND checks that this token
    # was issued for OUR audience by OUR trusted issuer -- a valid
    # token for a different app must be rejected here, not accepted.
    claims = jwt.decode(
        bearer_token,
        signing_key.key,
        algorithms=["RS256"],
        audience=AUDIENCE,
        issuer=ISSUER,
    )
    return claims   # e.g. {"sub": "user_492", "roles": ["support_agent"], "tenant_id": "acme_corp"}

class AuthedState(MessagesState):
    user_id: str
    roles: list
    tenant_id: str
    user_token: str   # kept around so we can delegate/exchange it later, see section 3

def authn_node(state: AuthedState) -> AuthedState:
    # This node is the ONLY place a raw bearer token gets decoded. Every
    # node after this one works with clean, already-verified claims --
    # never re-parses a token itself.
    claims = verify_user_token(state["bearer_token"])
    return {
        "user_id": claims["sub"],
        "roles": claims.get("roles", []),
        "tenant_id": claims.get("tenant_id"),
    }

graph = StateGraph(AuthedState)
graph.add_node("authn", authn_node)
graph.add_edge(START, "authn")
graph.add_edge("authn", "supervisor")   # the Ch.2 supervisor node, unchanged otherwise
An expired or invalid token should never quietly become "no user" jwt.decode raises an exception on a bad signature, wrong audience, or expired token. Let that exception propagate and stop the graph — never fall back to a default/anonymous identity just to keep things moving, or you've turned an authentication check into a suggestion.

2. Zero trust between agents — every hop re-checks, none of them just assume

Because authn_node ran once at the top of the graph doesn't mean every downstream node should blindly trust state["roles"] forever. Each node that's about to do something sensitive should re-check the specific permission it needs, not assume an earlier node already handled it.

zero_trust_check.pypython
from functools import wraps

def requires_role(required_role: str):
    """A small guard any node or tool can wrap itself in. It doesn't
    matter how many nodes ran before this one -- this check happens
    again, right here, right before the sensitive action."""
    def decorator(fn):
        @wraps(fn)
        def wrapper(state, *args, **kwargs):
            if required_role not in state.get("roles", []):
                # Fail loudly and specifically -- this becomes an audit
                # log entry (Ch.13), not a silently skipped step.
                raise PermissionError(
                    f"user {state.get('user_id')} lacks required role '{required_role}'"
                )
            return fn(state, *args, **kwargs)
        return wrapper
    return decorator

@requires_role("billing:read")
def billing_agent(state):
    reply = frontier_model.invoke(
        [("system", "You are the billing specialist.")] + state["messages"]
    )
    return {"messages": [reply]}

This looks redundant with the supervisor's routing decision — that's the point. Zero trust means redundant checks are a feature: if the supervisor's routing logic ever has a bug that sends a non-billing user to billing_agent anyway, this second check is what actually stops it.

3. Delegate scoped-down tokens instead of the user's full token

When the supervisor hands off to a specialist, don't hand over the user's original, broad token. Exchange it for a narrower one, scoped to exactly what that one specialist needs — the OAuth 2.0 pattern for this is called Token Exchange (RFC 8693).

token_exchange.pypython
import requests

def exchange_token(user_token: str, target_scope: str, client_id: str) -> str:
    # We trade the user's original token for a NEW, narrower one --
    # same user, same identity provider, but permission is capped to
    # exactly "target_scope" instead of everything the user can do.
    resp = requests.post(
        "https://your-tenant.auth0.com/oauth/token",
        data={
            "grant_type": "urn:ietf:params:oauth:grant-type:token-exchange",
            "subject_token": user_token,
            "subject_token_type": "urn:ietf:params:oauth:token-type:access_token",
            "requested_token_type": "urn:ietf:params:oauth:token-type:access_token",
            "scope": target_scope,     # e.g. "billing:read" -- NOT the user's full scope list
            "client_id": client_id,     # identifies WHICH sub-agent is asking
        },
    )
    resp.raise_for_status()
    return resp.json()["access_token"]

def supervisor(state):
    route = router_llm.invoke(
        [("system", "Route to 'billing' or 'shipping'.")] + state["messages"]
    )
    if route.next == "billing":
        # The billing agent never sees the user's original token at
        # all -- only this scoped-down one, good for billing:read only.
        scoped_token = exchange_token(state["user_token"], "billing:read", client_id="billing-subagent")
        return {"next": "billing", "delegated_token": scoped_token}
    # ...same pattern for "shipping"
Why this matters more for agents than for normal microservices A traditional microservice calls a fixed, reviewed set of downstream endpoints. An LLM-driven agent decides at runtime which tool to call based on a model's output — which can be wrong, or manipulated by a prompt injection (Ch.4). A scoped-down delegated token means that even in the worst case, a misdirected or hijacked tool call is capped by what that narrow token can do, not by everything the original user was allowed to do.

Authorized retrieval, tool-level RBAC, and MCP server auth

Authentication tells you who's asking. The next three pieces are all about authorization — making sure that identity actually constrains what comes back from retrieval, what tools can run, and what a connected MCP server will allow.

1. Enforce document-level permissions inside the retriever, not after it

The most common RAG security mistake is retrieving broadly and then trying to filter out documents the user isn't allowed to see afterward. By then, the disallowed text has already sat inside the LLM's context — filtering after the fact doesn't undo that. Authorization has to be a filter on the retrieval query itself.

authorized_retrieval.pypython
# At ingestion time, every document should already be tagged with who's
# allowed to see it -- e.g. when the Agentic RAG section's documents
# were added to the vector store:
#
#   Document(
#       page_content="Our refund policy allows returns within 30 days.",
#       metadata={"tenant_id": "acme_corp", "allowed_roles": ["support_agent", "billing_agent"]},
#   )

def authorized_retrieve_node(state):
    query = state["messages"][-1].content

    # The filter is applied AS PART OF the search itself -- the vector
    # store never even considers documents outside the user's tenant or
    # role, so there's no window where disallowed text could leak into
    # context, even for one step.
    docs = retriever.invoke(
        query,
        filter={
            "tenant_id": state["tenant_id"],
            "allowed_roles": {"$in": state["roles"]},
        },
    )
    return {"retrieved_docs": docs}

This is the same idea as row-level security in a normal database, applied to a vector store: the permission check is baked into the query, not bolted on as a second pass over the results.

2. Gate high-risk tools with role checks, on top of the Ch.4 policy gate

The policy gate from Chapter 4 asks "does a human need to approve this?" Role-based access control asks an earlier, separate question: "is this user even allowed to request this kind of action at all?" Both checks matter, and neither replaces the other.

rbac_tool_gate.pypython
from pydantic import BaseModel, Field
from langchain_core.tools import StructuredTool

class RefundArgs(BaseModel):
    invoice_id: str = Field(description="Exact invoice identifier")
    amount_cents: int = Field(gt=0)
    reason: str

def _issue_refund(invoice_id, amount_cents, reason, *, state):
    # RBAC check FIRST: does this user's role even permit refunds?
    if "refunds:write" not in state["roles"]:
        raise PermissionError("user role does not permit issuing refunds")
    # ...then the Ch.4 policy gate still runs afterward: validate
    # ownership, get human approval, THEN actually execute.
    return {"status": "pending_approval", "invoice_id": invoice_id, "amount_cents": amount_cents}

issue_refund = StructuredTool.from_function(
    func=_issue_refund,
    name="issue_refund",
    description="Propose a refund. Requires refunds:write role AND human approval.",
    args_schema=RefundArgs,
)
issue_refund.metadata = {"risk": "high-write", "required_role": "refunds:write"}

3. Authenticate to MCP servers with delegated tokens, not one shared static key

MCP's authorization spec is built on OAuth 2.1 for remote (HTTP) servers: your agent presents a bearer token when it calls a tool, and the MCP server is responsible for validating that token — checking its audience and scope — before running anything, exactly like any other protected API. A local (stdio) MCP server instead relies on the operating system's own process boundary as its trust boundary, since it's launched directly by your own code rather than reached over a network.

mcp_delegated_auth.pypython
from langchain_mcp_adapters.client import MultiServerMCPClient

def build_mcp_client(delegated_token: str) -> MultiServerMCPClient:
    return MultiServerMCPClient({
        "support_desk": {
            "url": "https://mcp.example.com/support",
            "transport": "streamable_http",
            # This is the delegated, scoped-down token from Section 1's
            # token exchange -- NOT the user's original broad token,
            # and NOT one static key shared by every agent forever.
            "headers": {"Authorization": f"Bearer {delegated_token}"},
        },
    })

# A fresh, correctly scoped client is built per-request, using whichever
# delegated token this specific specialist agent was handed.
async def run_support_agent(state):
    mcp_client = build_mcp_client(state["delegated_token"])
    mcp_tools = await mcp_client.get_tools()
    llm_with_mcp_tools = frontier_model.bind_tools(mcp_tools)
    return {"messages": [llm_with_mcp_tools.invoke(state["messages"])]}
The server must enforce this too — never trust the client alone Everything above assumes the MCP server itself checks the incoming token's audience, scope, and expiry on every tool call, the same way authn_node does for your own graph. A client that "politely" only sends scoped tokens doesn't protect you from a differently-behaved client (or a bug, or an attacker skipping your code entirely and calling the server directly) — the server enforcing authorization on its own tools is what actually closes the gap.

Interview questions & answers

A run-through of everything on this page, phrased the way an interviewer might actually ask it. Click a question to reveal the answer — try answering in your own words first.

How to use this section

Don't just read the answers top to bottom. Cover the answer, say your own version out loud, then click to check. If your answer used a different analogy but the same underlying idea, that's a pass — interviewers care about understanding, not matching a script.

Foundations & the autonomy spectrum
What's the actual difference between a standalone LLM and an AI agent?

A standalone LLM can only reason over text — give it a question, it gives you an answer, and that's the end of its involvement with the world. An agent is that same LLM connected to tools (search, a calculator, an API) so it can perceive information and take real actions, not just describe what it would do. The "brain" doesn't change; what changes is whether it has hands.

Name the four pillars of an agentic system and what each one is responsible for.

The Brain (the LLM) decides what to do next. Tools are the functions it can call to affect the outside world. Memory holds short-term conversation context and long-term persisted facts. Planning is the ability to break a big, vague goal into smaller, ordered steps. Miss any one of these and you don't really have an agent — you have a chatbot, a script, or a database with no way to decide anything.

Why does increasing an agent's autonomy increase risk faster than you'd expect?

Because errors compound across steps. If an agent is 95% reliable per step, that sounds fine — until it's chained across ten autonomous steps, where the odds of at least one step going wrong drop to roughly 60%. The fix isn't "make it more autonomous and hope," it's matching autonomy to the actual risk of the task and putting a human check at the steps that matter most.

Execution patterns (Ch.2)
When would you pick ReAct over Plan-and-Execute?

ReAct fits tasks where each step's result changes what you should do next — you can't write the whole plan up front because you don't yet know what you'll find. Plan-and-Execute fits longer, more predictable workflows where the steps are largely known in advance and you want the structure and auditability of committing to a roadmap before running anything. In short: reach for ReAct when you need to react, and Plan-and-Execute when you can actually plan.

What's the practical difference between a supervisor multi-agent setup and a swarm?

A supervisor always routes control back through one central router, so every hand-off is predictable and auditable — like a phone menu. A swarm lets any agent hand off directly to any other agent with no central check-in, which is faster and more flexible but harder to reason about and audit. Use a supervisor when you need predictability (e.g. anything touching money or compliance); consider a swarm only when the domain is unstructured enough that a fixed router would constantly be wrong.

Why must a Reflection loop have a hard cap on revisions?

Without a cap, a critique that never says "approved" sends the draft back forever — an infinite loop that burns tokens and never returns an answer to the user. Capping revisions (e.g. stop after 3 tries regardless of the critique) guarantees the loop always terminates, even in the worst case where the critic and writer never agree.

In the ReAct graph, what's the actual role of tools_condition?

It's the conditional edge that inspects the agent's last message: if the model asked to call a tool, route to the tools node; if it produced a normal answer instead, route to END. It's what turns a single request/response into a loop — without it, the graph would have no way to decide whether the conversation is actually finished.

Production architecture (Ch.3)
Why bother with model routing instead of just using your best model everywhere?

Cost and latency. Simple jobs — classifying intent, extracting a field, deciding which of two words applies — don't need a frontier model's reasoning ability, and paying frontier prices for them on every single step of every single run adds up fast at production volume. Routing keeps the expensive model for the steps that actually need deep reasoning, and hands routine judgment calls to a small, cheap model.

Explain the difference between "state" and "memory" in an agent system.

State is the active, in-progress context of one specific session — the messages so far, which tools have been called, what's still pending. Memory is durable information that outlives any one session — user preferences, past summaries, semantic documents. LangGraph keeps these in separate systems on purpose (a checkpointer for state, a store for memory) so a long conversation doesn't get confused with, or bloated by, facts learned in a totally different session.

Why are trace-level evals necessary — isn't checking the final answer enough?

An agent can produce a correct-looking final answer while doing everything wrong along the way — calling the wrong tool, retrieving an irrelevant document, or burning ten times the expected token budget to get there by luck. Trace-level evals grade each step of the trajectory (tool selection, retrieval relevancy, cost, refusal compliance), which catches regressions that a final-answer-only check would completely miss.

Why force tool arguments through a Pydantic schema instead of letting the model write free-form text?

Free-form text handed straight to a database query or an API is an injection risk and a correctness risk — there's no guarantee the model's phrasing means what you think it means. A strict schema (named fields, types, validation rules like "amount must be greater than zero") forces the model's intent into an unambiguous, checkable shape before any code acts on it, and lets you reject bad input automatically instead of hoping the model got it right.

Governance & security (Ch.4)
Walk through the "suggest, validate, approve, execute" pipeline and why each step exists.

The LLM suggests a tool call based on inferred intent — it's allowed to be wrong here, because nothing has happened yet. Deterministic code then validates it against real business rules (ownership, permissions) — this step exists because the model can't be trusted to enforce rules perfectly and consistently. A human then explicitly approves the validated proposal — this is the actual safety backstop for anything high-risk. Only then does the application execute the write. Skip validation and a plausible-sounding but wrong request could slip through; skip human approval and there's no backstop against a validated-but-still-bad decision.

What is prompt injection, and why is "detect suspicious phrases" not a complete defense?

Prompt injection is when untrusted text — a retrieved document, a tool's output, even a user's message — contains instructions that try to hijack the model's behavior, the same way a hidden note could try to manipulate a person reading it. Keyword/pattern matching catches the obvious cases but can always be rephrased around, so it's a floor, not a ceiling. The real defense is layered: sanitize what you can detect, but also give tools the minimum permissions needed (least privilege) and require human approval before anything high-risk executes, so a successful injection still can't cause real damage on its own.

Why should the model never be the last step before a high-risk write operation?

Because the model's job is inferring intent from language, which is inherently probabilistic — it can be manipulated, confidently wrong, or simply misread an ambiguous request. Deterministic validation and a human approval step are what turn "the model thinks this is right" into "we've confirmed this is right." Removing that gate for speed doesn't remove the risk — it just removes the safety net.

Knowledge graphs & MCP (Ch.5)
When would you reach for a graph database like Neo4j instead of a vector store?

Vector stores answer "find me text that means something similar to this question" well, but they're weak at multi-hop questions that require following explicit relationships — "who approved the invoice that the finance manager flagged?" A graph database stores those relationships directly as edges between nodes, so traversing "invoice → approved_by → person → member_of → team" is a natural query instead of something you'd have to hope a similarity search stumbles into.

What specific problem does MCP solve that a custom tool integration doesn't?

Without MCP, every new tool or data source needs its own custom glue code, written again for every agent framework that wants to use it. MCP standardizes how a server exposes its tools and how a client discovers and calls them, so one MCP server can be plugged into many different agents without rewriting integration code each time — the same benefit USB-C got over proprietary charging cables.

If an MCP server is written by a third party, does it need the same guardrails as a hand-written tool?

Yes, if anything — arguably more. An MCP server you didn't write is still just a tool provider, and any tool it offers should get the same risk tag and, if it writes data, the same human-in-the-loop policy gate as a tool you built yourself. Standardized plumbing doesn't imply trusted plumbing.

The Agentic FDE (Ch.6)
What does a Forward Deployed Engineer do that a platform/product engineer typically doesn't?

A platform engineer builds general-purpose components meant to work reasonably well for many customers. An FDE embeds with one specific customer, learns their actual (often messy) workflow, and decides which general components fit, wires them to that customer's real systems, and sets the risk tolerance for that specific deployment. The code might look similar; the job is making generic building blocks fit one particular, real situation.

Why might two customers using the "same" agent need completely different policy-gate settings?

Because "high-risk" isn't a property of the tool alone — it depends on the customer's own risk tolerance, regulatory environment, and blast radius if something goes wrong. A marketing team auto-sending draft social posts and a hospital auto-updating patient records both use a "send/write" tool, but only one of them can reasonably tolerate that happening without a human checking first. The FDE's job includes setting that bar with the customer, not assuming a default.

CI/CD & AgentOps (Ch.7)
Why can't ordinary unit tests fully gate an agent's deployment?

Unit tests assume determinism — the same input should always produce the same output, and a mismatch means failure. An agent's phrasing and exact tool-call sequence can vary between runs even when it's behaving correctly, so exact-match testing produces constant false alarms. The fix is an eval suite that scores behavior against a threshold ("did tool selection stay above 85% on our regression set?") rather than checking for byte-identical output.

What is a canary deployment, and why does it matter more for agents than for typical web apps?

A canary deployment routes a small percentage of real traffic to a new version while most traffic stays on the trusted version, so you can compare their results before fully committing. It matters even more for agents because a regression isn't just a rendering bug — it can mean the new version takes wrong real-world actions (bad refunds, bad routing) at scale before anyone notices, so catching it on 10% of traffic instead of 100% meaningfully limits the damage.

Why pin an exact, dated model snapshot instead of just referencing "gpt-4o"?

Model providers periodically update what a generic model name points to, and those updates can silently change your agent's behavior even though you changed nothing on your end. Pinning a dated snapshot means your agent's behavior only changes when you deliberately decide to upgrade and re-run your eval gate against it — not whenever the provider feels like shipping an update.

Why should a kill switch be a flag you can flip instantly, rather than something requiring a new deployment?

The entire purpose of a kill switch is to stop a misbehaving agent faster than a redeploy would allow — if turning it off requires the same code-review-and-deploy pipeline as a normal release, it's not actually an emergency control. Storing it as a feature flag or a database value means an on-call engineer can disable the agent in seconds, independent of the deployment pipeline's normal speed.

Observability (Ch.8)
What's the difference between a "trace" and a "span" in observability terms?

A span is one measured step — one node running, one tool call, one model invocation — with its own start time, end time, and attached details. A trace is the whole tree of spans for a single request, showing how they nested and connected. "The agent took 4 seconds" is barely useful; "the agent took 4 seconds because the reranker span alone took 3.2 of them" is what actually lets you fix something.

Why use OpenTelemetry instead of just logging to LangSmith directly?

OpenTelemetry is a vendor-neutral standard, so the same instrumented code can export traces to LangSmith, Grafana, Datadog, or whatever you use next year, without rewriting your instrumentation. Coupling your code directly to one vendor's SDK means switching tools later requires touching every instrumented function; standardizing on OpenTelemetry means you only ever change the exporter configuration.

Why prefer structured (JSON) logs over plain text log lines?

Plain text log lines are built for a human reading them one at a time. Structured logs are built for a machine searching across millions of them — "show me every failed tool_call for thread_id=session-88" is a simple filter against structured fields, but would require fragile text parsing against unstructured sentences.

RAGAS & LangSmith deep-dive (Ch.9)
What's the difference between RAGAS's "faithfulness" and "answer relevancy" metrics?

Faithfulness checks whether the generated answer only states things actually supported by the retrieved context — it catches hallucination even when the answer sounds confident. Answer relevancy checks whether the answer actually addresses the question that was asked — an answer can be perfectly faithful to the context and still dodge the actual question. You need both: a faithful-but-irrelevant answer and a relevant-but-hallucinated answer are both failures, just different ones.

What's the difference between context precision and context recall?

Context precision asks: of the documents we actually retrieved, how many were genuinely useful (versus noise that could confuse the model)? Context recall asks the opposite direction: of the documents that would have actually helped answer the question, how many did we manage to retrieve at all? A retriever can have great precision but poor recall if it returns 2 highly relevant documents while missing 3 others that were also needed.

Why keep growing a LangSmith regression dataset from production feedback instead of writing it once?

A dataset written once only covers the failure modes the team thought of in advance. Real users ask questions nobody anticipated, and a thumbs-down on a real trace is direct evidence of an actual gap. Promoting those real cases into the regression set means the test suite keeps getting harder and more representative over time, instead of staying frozen at day-one coverage.

Retrieval quality & reranking (Ch.10)
Why not just use a cross-encoder for the initial retrieval instead of a vector search?

A cross-encoder scores a query against one document at a time by processing both together, which is far more accurate but far too slow to run against an entire document collection of thousands or millions of items. Vector search is fast at narrowing a huge collection down to a manageable shortlist; the cross-encoder then spends its accuracy budget only on that shortlist. Using it for everything would make retrieval too slow to be usable.

How many candidates should you retrieve before reranking, and how many should survive?

There's no universal number — it's a trade-off between recall (wide enough to not miss the right document) and latency/cost (narrow enough that reranking stays fast). A common starting point is retrieving 20-50 candidates and reranking down to the top 3-5 that actually get passed to the generation step, then tuning both numbers against your own eval scores.

Redis semantic caching (Ch.11)
Why doesn't a normal (exact-match) cache work well for LLM responses?

Two users asking the same underlying question rarely type it identically — "how do refunds work?" and "what's your return policy?" would be two different cache keys under exact matching, so neither would ever hit the other's cached answer. A semantic cache matches on embedding similarity instead of exact text, so differently worded but equivalent questions can share a cached answer.

What's the risk of setting the semantic cache's similarity threshold too loose?

A too-loose threshold will match questions that are related but not actually the same, and serve a wrong (but confident-sounding) cached answer to a genuinely different question — a false cache hit is worse than a cache miss, because a miss just costs a bit more money and time, while a false hit gives the user an actively incorrect answer. Tune the threshold conservatively and validate it against real near-duplicate and real distinct question pairs.

Why cache tool calls with an exact-match key instead of semantic matching?

Tool arguments are already structured and exact (a ticker symbol, an invoice ID) rather than free-form natural language, so there's no ambiguity to resolve with embeddings — two identical argument sets mean the identical request, full stop. A plain hash-based cache key is simpler, faster, and has none of the "close enough" risk that a semantic cache carries.

Token optimization (Ch.12)
What's the single biggest lever for cutting an agent's token cost?

Usually model routing — sending routine classification, extraction, and routing steps to a cheap small model instead of a frontier model. Because those steps typically fire on nearly every turn of every conversation, even a small per-call saving compounds enormously at real traffic volume, more than most individual prompt-trimming tricks do.

Why summarize old conversation turns instead of just deleting them once the history gets long?

Deleting old turns outright can lose facts the conversation still depends on (a preference the user stated ten messages ago, a decision already made). Summarizing compresses that history into a much shorter form while keeping the facts that matter, so later turns still have the context they need without paying to resend the full original transcript every time.

Why does asking for structured output (a tool call or a Pydantic object) tend to save tokens versus asking for a written explanation?

A structured response only contains the specific fields you actually need — an amount, a ticker, a yes/no — with no narration around them. Asking the model to "explain your reasoning" or write full sentences naturally produces more tokens to convey the same underlying decision, even though only the decision itself is what your code will actually use.

Security (Ch.13)
What is SSRF, and why is it a specific risk for agent tools that fetch URLs?

SSRF (Server-Side Request Forgery) is when a tool that's supposed to fetch an external URL gets tricked — by a malicious link, or by a compromised/injected instruction — into fetching an internal address instead, like a cloud metadata endpoint that can leak credentials, or an internal admin service never meant to be reachable from outside. It's a specific risk for agents because the "decide which URL to fetch" step is now driven by model output, which can be manipulated, rather than by a human typing a URL they chose themselves.

Why give each tool its own scoped credential instead of one shared API key for the whole agent?

If every tool shares one broad credential, a bug or successful attack against any single tool exposes everything that credential can do. Scoping credentials per tool — the refund tool can only call the refunds API, the shipping tool can only call the shipping API — means a compromise stays contained to what that one tool was ever allowed to touch, which is the same least-privilege idea behind the handbook's Cryptographic Agent Identities.

Why is a bare subprocess call not considered a real sandbox for executing untrusted code?

A subprocess still shares the same filesystem, network access, and underlying kernel as the parent application — code running inside it can potentially read other files, reach internal services, or exploit a kernel-level vulnerability that a container or microVM boundary would block. A real sandbox needs an actual isolation boundary (a container with no network and a read-only filesystem, or a microVM), not just a separate process ID.

Why does an audit log need to be append-only rather than a normal editable database table?

The entire point of an audit log is answering "what actually happened, and who approved it" with certainty, including in a dispute or an incident investigation. If the log lives in a normal table someone (or some bug, or an attacker) could edit after the fact, it can no longer be trusted as evidence of what really occurred — append-only, tamper-evident storage is what makes the log actually useful as an audit trail rather than just another log file.

AuthN/AuthZ in multi-agent MCP RAG (Ch.14)
In one sentence, what's the difference between authentication and authorization?

Authentication proves who is making the request; authorization decides what that specific identity is allowed to see or do. A system can authenticate a user perfectly and still be badly broken if authorization then lets them (or an agent acting for them) reach data or actions their role was never meant to touch.

Why shouldn't every downstream agent just trust that the supervisor already checked the user's permissions?

Because that turns one routing bug, one compromised node, or one successful prompt injection into a total bypass — if nothing downstream re-checks, nothing downstream can catch a mistake upstream. Zero trust between agents means each sensitive action re-verifies the specific permission it needs, right before it acts, so a failure in one layer doesn't automatically become a failure of the whole system.

What problem does OAuth Token Exchange solve that just passing the user's original token to every sub-agent doesn't?

Passing the user's full token everywhere means every sub-agent and every tool call carries the user's ENTIRE permission set, even for a narrow, single-purpose task. Token exchange trades that broad token for a new one scoped to exactly what the receiving agent needs — so a billing sub-agent gets a token that can only do billing:read, for example, and a bug or hijack in that one sub-agent is capped by that narrow scope instead of by everything the user could do.

Why is filtering retrieved documents by permission AFTER the vector search not good enough?

By the time you filter afterward, the disallowed document has already been retrieved and has already sat in the pipeline — in a more complex system it could be logged, cached, or briefly included in the model's context before being stripped out. Applying the permission filter as part of the search query itself (matching on tenant and role at query time) means the disallowed documents are never fetched in the first place, not fetched-then-hidden.

Who is responsible for enforcing an MCP tool's authorization — the calling agent, or the MCP server?

Both, but the server's check is the one that actually matters for security. A well-behaved client sending only scoped, delegated tokens is good practice, but it doesn't protect the system from a different client, a bug, or an attacker calling the MCP server directly and skipping the client's logic entirely. The MCP server must independently validate every incoming token's audience, scope, and expiry on every tool call — the same principle as never trusting client-side validation alone in any other API.
