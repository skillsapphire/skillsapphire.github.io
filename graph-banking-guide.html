01 · Foundations

What is a graph, really?

Before Neo4j, before AI — start with the shape underneath everything: dots and lines.

🧒 Explain it like I'm 8

Picture your class standing on the playground, holding hands with their best friends. Each kid is a dot (we call it a node). Each held hand is a line connecting two kids (we call it an edge). If you want to know "who is Sam's friend's friend?", you just follow the hands: Sam → Priya → Priya's other hand → done! That whole holding-hands picture is a graph.

Now give every kid a name tag (their label, like "Student") and write on each held hand what kind of friendship it is ("best friend since 2022"). Congratulations — you just built a tiny knowledge graph.

⚙ The technical version

Formally, a graph G = (V, E) is a set of vertices (nodes) and edges (relationships) connecting pairs of vertices. Graphs can be directed (edges point one way, like OWES_MONEY_TO) or undirected, and weighted (an edge carries a number, like transaction amount). Neo4j uses the Labeled Property Graph (LPG) model: nodes carry one or more labels (:Customer, :Account) plus key–value properties, and relationships carry a single type (:TRANSFERRED_TO), a direction, and their own properties (amount, timestamp, currency).

●Node

A "thing" — a customer, an account, a merchant, a device, a document chunk.

→Relationship

A typed, directed connection between two nodes — OWNS, PAID, REFERRED.

{ }Property

A fact attached to a node or edge — balance, risk score, date opened.

02 · Foundations

Graph database vs. relational database

Same data, two very different ways of finding your way around it.

🧒 Explain it like I'm 8

A relational database is like a school with every student's info in a different filing cabinet drawer — one drawer for "Students," another for "Clubs," another for "Who's in Which Club." To answer "which club is my friend's friend in?", you have to run between drawers matching ID numbers over and over. Slow, and it gets slower the more friends you ask about.

A graph database is like a giant wall poster where every kid is already drawn as a dot with strings to their friends and clubs. To answer the same question, you just look and follow the string. No running between drawers — the connections are already right there.

Relating dataForeign keys + JOIN at query timeRelationships stored physically as pointers — "index-free adjacency"
Multi-hop queriesCost grows fast — every hop is another JOINCost stays roughly flat per hop — you just walk the pointer

03 · Foundations

Neo4j and Cypher

The most widely used graph database, and the query language built to "speak" in graph patterns.

🧒 Explain it like I'm 8

Neo4j is a computer program that is really, really good at storing the dots-and-lines picture and instantly following any string you point at. Instead of asking it a question in complicated computer-speak, you basically draw your question using little pictures made of text, like (sam)-[:FRIEND]->(priya). That drawing language is called Cypher, and Neo4j reads it and shows you the matching part of the picture.

⚙ The technical version

Neo4j is an ACID-transactional, native graph database. Cypher is its declarative query language (now standardized industry-wide as the basis for GQL, ISO/IEC 39075) — you describe the pattern you want matched, not the steps to find it. Production deployments run as a causal cluster for high availability, or on Neo4j Aura (managed cloud). The Graph Data Science (GDS) library adds 65+ graph algorithms, and APOC adds hundreds of utility procedures (data import, refactoring, virtual graphs).

Cypher — model a customer, account, and a transfer

MERGE (c:Customer {id: 'CUST-1042', name: 'A. Rao', kycTier: 'gold'})
MERGE (a:Account {iban: 'IN29-XXXX-0042', type: 'savings'})
MERGE (c)-[:OWNS]->(a)
MERGE (b:Account {iban: 'GB33-YYYY-0091'})
MERGE (a)-[t:TRANSFERRED {amount: 48500, currency: 'INR', ts: datetime()}]->(b)

Cypher — a query no SQL JOIN chain wants to write: "second-degree money movement"

MATCH (start:Account {iban: 'IN29-XXXX-0042'})-[:TRANSFERRED*1..3]->(reached:Account)
RETURN DISTINCT reached.iban AS downstream_account
// finds every account money could have reached within 3 hops — instantly
04 · Foundations

Knowledge graphs

A graph that doesn't just connect things — it understands what they mean.

🧒 Explain it like I'm 8

Remember the detective's corkboard in movies, covered with photos and red string connecting suspects? That's a knowledge graph. Every photo (node) has a label saying what it is ("Person," "Company," "Bank Account"), and every red string (edge) says exactly how they're linked ("works for," "owns," "sent money to"). It's a web of facts, not just doodles — so a computer can look at the board and actually understand the story, not just see lines.

⚙ The technical version

A knowledge graph (KG) is a graph where nodes represent real-world entities and edges represent typed, semantic relationships, usually governed by a schema or ontology. Public examples include the Google Knowledge Graph and Wikidata. In the enterprise, KGs unify data scattered across silos — CRM, core banking, document stores — into one queryable "single source of truth," and are foundational to entity resolution (deciding that "A. Rao," "Anita Rao," and "ANITA R." are the same customer).

05 · AI & Retrieval

GraphRAG

Retrieval-Augmented Generation, upgraded from "search loose pages" to "follow the evidence trail."

🧒 Explain it like I'm 8

Plain RAG is like giving an AI a big messy pile of loose pages and saying "find the pages that sound similar to my question." It grabs a handful and guesses. That works fine for simple questions, but if the answer needs pages 4, 19, and 55 together, and none of them look alike on their own, plain RAG can miss it.

GraphRAG gives the AI that detective corkboard instead of loose pages. Now it can start at one fact and walk the strings to related facts, even ones that don't "sound similar" at all, and it can explain its answer by showing you the exact path of string it followed.

⚙ The technical version

Standard RAG: chunk documents → embed chunks → retrieve top-k chunks by vector similarity → stuff into the LLM's context. It struggles with multi-hop reasoning and "global" questions ("summarize the themes across all 400 reports") because similarity search only sees one chunk at a time.

GraphRAG extracts entities and relationships from source data into a knowledge graph, often with community detection to pre-summarize clusters of related entities. Retrieval then combines: (a) vector search for semantically relevant nodes/chunks, (b) graph traversal for structurally connected facts, and (c) community summaries for high-level, aggregate questions. Microsoft Research's GraphRAG popularized the community-summary "map-reduce" pattern for exactly this class of global questions.

06 · AI & Retrieval

Graphiti — temporal memory for agents

Built by Zep AI, running on Neo4j: a knowledge graph that remembers not just what is true, but when it was true.

🧒 Explain it like I'm 8

Imagine your friend tells you their favorite color is blue. Later, they tell you it's actually green now. A normal notebook would just cross out "blue" and write "green" — you'd lose the fact that blue was ever true. Graphiti is like a smarter notebook: it keeps "blue" but writes next to it "true until March," and adds "green — true from March onward." So your AI assistant can always answer both "what's their favorite color now?" and "what was it back in January?" correctly, without getting confused.

⚙ The technical version

Graphiti builds a real-time, incrementally-updated knowledge graph for agent memory, with a bi-temporal model: every edge tracks both when an event actually happened and when the system learned about it, via explicit validity intervals. When new information contradicts an existing fact, Graphiti closes that fact's validity window rather than deleting it — history stays fully queryable and auditable, while the agent still reasons over current state.

It organizes memory into three subgraphs: an episode subgraph (raw ingested messages/documents), a semantic entity subgraph (extracted entities and facts), and a community subgraph (cluster-level summaries). In the underlying research (the Zep paper), this architecture outperformed MemGPT on the Deep Memory Retrieval benchmark and showed notable accuracy gains with much lower latency on the more enterprise-realistic LongMemEval benchmark.

Why it matters for banking agents

A relationship manager's AI assistant needs to remember a client's evolving risk appetite, past complaints, and product changes — not just today's snapshot — and be able to justify an answer with "as of what date," which regulators expect.

Where it fits

Graphiti typically sits alongside — not instead of — your GraphRAG document knowledge graph: one graph for durable, evolving "facts about the world," one memory layer for the agent's conversational and behavioral context.

07 · AI & Retrieval

Vector + graph hybrid search

Two very different questions — "what does this mean?" and "what is this connected to?" — answered together.

🧒 Explain it like I'm 8

Vector search is like finding kids on the playground who are dressed similarly to you — it's about "feeling alike." Graph search is like finding kids who are actually holding your hand or your friend's hand — it's about "really being connected." Sometimes you want both: find kids who look like you and are actually in your friend group.

⚙ The technical version

Neo4j supports native vector indexes alongside its graph store, so a single query can perform approximate-nearest-neighbor search over embeddings and then expand outward through graph relationships (e.g., "find the 20 most semantically similar clauses, then pull in every regulation node they reference"). This hybrid pattern is the technical backbone of GraphRAG retrieval, and it lets you rank by relevance while filtering or boosting by real relationships — e.g., only within documents the current customer is actually entitled to see.

08 · AI & Retrieval

Graph algorithms (Graph Data Science)

Once your data is a graph, a whole toolbox of algorithms becomes available that tabular data can't easily offer.

PageRank — importance

Like a popularity contest where being picked by popular kids makes you more popular too. A node connected to many well-connected nodes scores higher.

Used to rank the most "central" accounts or entities in a transaction network — often surfacing money mules or hub accounts.

Louvain — community detection

Like automatically sorting a tangled friend-web into actual friend groups, without anyone telling the computer the groups in advance.

Used to find fraud rings — tight clusters of accounts that transact mostly with each other and stand apart from the main legitimate network.

FastRP / Node2Vec — node embeddings

Turning each dot's "neighborhood shape" into a list of numbers — a fingerprint a machine-learning model can read.

These graph-derived features, blended with traditional tabular features, measurably improve fraud classifiers (e.g., XGBoost) over tabular data alone.

Shortest Path / Betweenness — reach & bridges

Finds the shortest hand-holding chain between two kids, or the one kid who bridges two separate friend groups.

Used for ownership-chain analysis (who ultimately controls a shell company) and for spotting choke-point accounts in layering schemes.

09 · Build

Python + Neo4j

The official driver, plus the LangChain layer most production GraphRAG stacks are built on.

Install

pip install neo4j langchain-neo4j

Native driver — run a Cypher query

from neo4j import GraphDatabase

driver = GraphDatabase.driver("neo4j+s://<your-aura-id>.databases.neo4j.io",
                              auth=("neo4j", "<password>"))

def accounts_within_hops(tx, iban, hops=3):
    query = """
    MATCH (a:Account {iban: $iban})-[:TRANSFERRED*1..%d]->(reached)
    RETURN DISTINCT reached.iban AS acct
    """ % hops
    return [r["acct"] for r in tx.run(query, iban=iban)]

with driver.session() as session:
    result = session.execute_read(accounts_within_hops, "IN29-XXXX-0042")
    print(result)

LangChain — GraphRAG QA chain over Neo4j

from langchain_neo4j import Neo4jGraph, GraphCypherQAChain
from langchain_anthropic import ChatAnthropic

graph = Neo4jGraph(url="neo4j+s://...", username="neo4j", password="...")
llm = ChatAnthropic(model="claude-sonnet-4-6")

chain = GraphCypherQAChain.from_llm(llm=llm, graph=graph, verbose=True)
answer = chain.invoke({"query": "Which accounts received funds from CUST-1042 within 3 hops?"})

10 · Banking in Production

Real-world production use cases

Documented, real deployments — not hypotheticals. Names, patterns, and results reported by the institutions and by Neo4j's published case material.

UBS
Data Lineage & Governance

UBS uses a Neo4j-based graph to trace data lineage — how data flows and transforms across systems — to satisfy regulatory data-governance requirements. Engineers there found Cypher's pattern-matching far more natural for lineage tracing than chaining SQL JOINs across many tables in a relational model.

Source: Neo4j customer case study, "UBS."

Citi Private Banking
Client & Portfolio Data

Citi's Private Banking data, reporting & analytics group re-engineered front-to-back data flows on a graph structure to support global client operations — modeling security entitlements and complex party-related data that don't fit neatly into flat tables.

Source: Neo4j financial services use-case material.

Standard Chartered
Threat Intelligence

Standard Chartered has presented on applying knowledge-graph techniques to threat intelligence — connecting indicators, actors, and infrastructure so analysts can pivot across a fraud or cyber investigation the way they'd follow a lead, not run isolated lookups.

Source: Standard Chartered / Neo4j published presentation.

Retail & commercial banks
Fraud Ring Detection

A recurring, widely deployed pattern: "bust-out" fraud, where a group of people pool stolen or synthetic identities, share contact details across multiple new accounts, build up credit responsibly for months, then simultaneously max out every line and disappear. This is invisible account-by-account — it only appears as a shape in the graph, where several "different" people share the same phone number, address, or device fingerprint. A single Cypher pattern query can surface these rings in real time, something that's extremely costly to express as recursive SQL.

Source: Neo4j developer blog & industry fraud-ring GraphGists.

UK retail banks
APP Scam / Transaction Monitoring

Authorised Push Payment (APP) fraud — where a victim is tricked into approving a transfer — cost UK consumers over £249 million in just the first half of 2022, up roughly 30% year over year, driving regulatory pressure (the Contingent Reimbursement Model) for banks to detect fraud rings, including ones that shave off a "cut" (often up to ~20%) at each hop as stolen funds are layered through multiple accounts.

Source: Neo4j "Transaction Fraud Ring" industry use case, citing UK payment-fraud reporting.

Graph-enhanced ML models
Fraud Scoring Uplift

In benchmark work on real transaction data, combining graph-derived features (Louvain communities, FastRP embeddings capturing structural role) with traditional tabular features (amount, time) and feeding both into a classifier such as XGBoost meaningfully outperformed a tabular-only baseline on precision-recall — because fraud rings show up as a distinct network shape that pure transaction attributes can't see.

Source: Neo4j "A Graph-Based Approach to Financial Fraud Detection" (IEEE-CIS dataset).

ICIJ — Panama & Pandora Papers
UBO / Ownership Analysis

Investigative journalists used graph technology to map beneficial ownership across shell companies and offshore accounts spanning millions of leaked records — the same "who ultimately controls this entity" pattern banks now run internally for Know-Your-Customer and Ultimate Beneficial Owner (UBO) compliance, since ownership chains are naturally graphs, not tables.

Source: Neo4j-supported ICIJ investigations, referenced in Neo4j customer materials.

Other production banking patterns

Real-time credit line / counterparty exposure aggregation across legal entities · cross-sell & next-best-offer recommendations from a 360° customer graph · customer churn prediction from relationship & interaction graphs · sanctions & adverse-media entity screening.

Why banks specifically reach for graphs

Money movement, ownership, and identity are inherently relational. Regulators increasingly demand explainable decisions (model-risk frameworks, GDPR-style rights to explanation) — a graph traversal is a literal, auditable evidence trail; a black-box tabular score is not.

11 · Architecture

Agentic solution design for banking

An AI agent that can safely answer, reason, and act on behalf of a bank — grounded in a graph, remembering over time, and never skipping compliance.

Every model call passes through the policy filter before any action executes, and every answer is logged with the evidence path it was grounded on.

Design principle: ground before you generate

The agent never answers a factual or numeric question from parametric memory alone — it retrieves from the knowledge graph or calls a core-banking tool first, then generates, so every claim is traceable.

Design principle: separate "what's true" from "what happened"

The Neo4j knowledge graph holds durable facts (products, policies, entities); Graphiti holds the evolving, timestamped memory of this customer and conversation. Mixing the two erodes both auditability and freshness.

Design principle: guardrails are not optional middleware

PII redaction, entitlement checks (row-/label-level access control in Neo4j), and human-in-the-loop approval for irreversible actions (payments, limit changes) sit in the critical path, not as an afterthought.

Design principle: log the reasoning, not just the answer

Regulators expect explainability. Storing the actual graph traversal or retrieved subgraph behind an answer turns "the AI said so" into an inspectable evidence trail.

12 · Architecture

Production RAG system design

From raw documents and transaction data to a grounded, cited answer — the full ingestion-to-generation pipeline.

Entitlement filtering happens before reranking, not after — so an unauthorized fact never reaches the LLM's context in the first place.

Chunking strategy

For banking policy and product documents, chunk by semantic section (clause, product tier) rather than fixed token windows, and preserve parent-document links in the graph so retrieval can walk back to full context.

Streaming freshness

Transaction and account-state data is ingested continuously (e.g., via Kafka into Neo4j) rather than batch-reloaded, so fraud and risk graphs reflect near-real-time state.

Entitlements before relevance

In a multi-tenant or multi-customer system, filtering by what the requester is authorized to see must happen before ranking — never rely on the LLM to "choose not to mention" something it shouldn't have seen at all.

Groundedness gate

A lightweight check (rule-based or a second LLM pass) verifies each claim in the draft answer traces to retrieved evidence before it's returned — critical where a wrong answer has regulatory or financial consequences.

13 · Reference

More concepts worth knowing

Rounding out the picture — things production teams run into that are easy to miss on a first pass.

Entity Resolution / Identity Resolution
Deciding that several records ("A. Rao," "Anita Rao," a phone number, a device ID) refer to the same real-world person or company — foundational to KYC, fraud rings, and clean knowledge graphs.
GQL (ISO/IEC 39075)
The new international standard graph query language, with Cypher as its principal input — meaning graph query skills are becoming portable across vendors, much as SQL is.
APOC
"Awesome Procedures On Cypher" — Neo4j's standard library of utility procedures for data import/export, refactoring, and virtual graph construction.
Graph data modeling
Designing labels, relationship types, and property placement up front matters as much as schema design does in SQL — a poorly modeled graph can be just as slow as a poorly indexed table.
Causal clustering & Fabric (sharding)
Neo4j scales horizontally for read throughput via causal clusters, and for very large graphs, via Fabric, which federates queries across sharded graph databases.
Neo4j Bloom / NeoDash
No-code graph visualization and dashboarding tools — useful for fraud analysts exploring a ring interactively rather than writing Cypher by hand.
Model risk management & explainability
Banking regulators (e.g., under frameworks like SR 11-7 in the US) expect model decisions to be explainable — a graph traversal that produced a decision is inherently more auditable than an opaque score.
RAGAS-style evaluation
Automated evaluation frameworks scoring RAG output on faithfulness (is it grounded?), answer relevance, and context precision/recall — essential before promoting any RAG change to production.
Row-/label-level security
Neo4j supports fine-grained access control down to node labels and properties, which matters enormously when one graph serves many customers or business units with different visibility rules.
Streaming ingestion (Kafka → Neo4j)
Production fraud and risk graphs are typically kept fresh via a "hot path" streaming pipeline, separate from the "cold path" used for historical model training.
