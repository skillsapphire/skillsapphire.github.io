BeginnerFoundations

What MLOps actually is

🎈 In plain words

Imagine a robot that guesses whether it'll rain tomorrow. MLOps is the toolbox and rulebook that keeps that robot working well over time — even as weather patterns change — and makes sure that if it starts guessing wrong, someone finds out fast and fixes it.

MLOps is DevOps plus two things DevOps never had to deal with: data that changes shape and distribution over time, and models whose "correctness" degrades silently even when the code hasn't changed. A model that scored 94% accuracy on Tuesday can be quietly wrong by Friday because user behavior shifted — no exception is thrown, no build breaks. MLOps is the discipline (and tooling) that makes that visible and reversible.

Reproducibility

Given a model version, you can rebuild the exact data, code, and environment that produced it — six months later, on a different cluster.

Automation (CI/CD/CT)

Continuous Integration and Delivery, plus Continuous Training: pipelines that retrain and redeploy automatically when data drifts or a schedule fires.

Observability

Not just uptime — prediction quality, input drift, feature skew, and business KPIs tied back to a specific model version.

Mental model

Traditional software has one artifact that changes: code. ML systems have three that change independently and interact: code, data, and the model/config. Every MLOps pattern in this guide exists to version, test, and roll back some combination of those three.

Why 8-year engineers still get burned by this

Experienced backend and data engineers often under-invest in MLOps because their instinct — "version the code, ship the container" — is necessary but not sufficient. Three failure modes repeat across almost every org:

  • Training/serving skew. Feature computed one way in a notebook, a slightly different way in the serving pipeline (e.g. a `fillna(0)` vs `fillna(mean)` mismatch). Model looks fine offline, degrades in production.
  • Silent drift. No error, no alert — the input distribution moved, and nobody is watching the right metric (they're watching latency/uptime, not prediction distribution).
  • Untraceable models. "Which data, code commit, and hyperparameters produced the model currently serving traffic?" is unanswerable six months in without a registry and lineage.

The end-to-end ML lifecycle

🎈 In plain words

Think of building a model like running a never-ending bake sale: gather ingredients (data), mix and shape them (features), bake (train), taste-test (evaluate), put a sticker on the best batch (register), sell it (deploy), and keep tasting new batches to make sure people still like it (monitor) — then do it all again.

Every cloud platform in this guide is really just tooling wrapped around the same eight stages. Learn this loop first — everything else is "how does Azure/AWS implement stage N."

The loop closes at Monitor, which is the stage most teams under-build. Data and Features are usually owned by data engineering; Train/Evaluate/Register by ML engineers; Deploy/Monitor by platform or MLOps engineers — which is exactly why hand-offs between these stages are where most production incidents originate.

IntermediateFoundations

MLOps maturity model (L0 → L3)

🎈 In plain words

This grades how organized a science-fair project is. Level 0 is one messy poster made the night before. Level 3 is a fully automated science fair where robots build, test, and swap in a better poster all by themselves whenever a better idea comes along — no human has to remember to do it.

Use this to honestly place your org — and to justify investment. Almost every team overestimates its own level.

LEVEL 0

Manual, notebook-driven

Data scientist trains locally, hands a pickle/serialized model to an engineer over Slack. No pipeline, no registry. Deployment is a manual, infrequent event.

LEVEL 1

ML pipeline automation

Training is a reproducible pipeline (steps, parameters, data versioned). Still manually triggered. Deployment still separate/manual, but the model artifact itself is trustworthy.

LEVEL 2

CI/CD for the pipeline

Source-controlled pipeline code goes through automated build, test, and deploy. New pipeline versions promote automatically through dev → staging → prod. Training still needs a human trigger.

LEVEL 3

Full CI/CD/CT

A live trigger service (drift detector, schedule, new label volume) automatically retrains, evaluates against gates, and — if it passes — promotes the model with no human in the loop, under monitoring and automatic rollback.

War story

A mid-size fintech believed it was "Level 3" because retraining ran on a weekly cron. It wasn't — the cron retrained but a human still manually eyeballed a dashboard and clicked "promote" in the registry UI. That's Level 2 with a scheduling trigger, not Level 3. The distinction mattered: when the on-call engineer was out for a week, four stale model versions queued up unreviewed, and the production model silently drifted for 9 days before anyone promoted the fix.

Roles & team topology

🎈 In plain words

It's like a school group project: one person collects the information (data engineer), one person writes the report using it (ML scientist), one person makes sure the printer and delivery all work (MLOps engineer), and one person keeps the whole classroom running (SRE).

MLOps fails more often from unclear ownership than from missing tooling. A workable split for a mid-size org:

RoleOwnsTypically does NOT own
Data engineerIngestion, ETL/ELT, feature pipelines, data quality SLAsModel architecture, training code
ML / Applied scientistModel design, offline evaluation, feature selectionInfra provisioning, serving SLAs
MLOps / Platform engineerPipelines, CI/CD, registry, serving infra, monitoring, costModel architecture decisions
SRE / Platform opsCluster health, networking, IAM, incident responseFeature engineering, model logic

In small teams one or two people wear all four hats — that's fine, but explicitly naming the four responsibilities avoids the classic gap: "I thought monitoring was your job."

IntermediateCore Pillar

Data & feature versioning

🎈 In plain words

If you baked an amazing cake, you'd want to write down the exact recipe and where you bought each ingredient so you could bake that exact cake again next year. Data versioning is writing down the “recipe card” for exactly what data trained a model.

You cannot reproduce a model without reproducing the exact data it saw. "Data versioning" means being able to answer: what rows, with what feature values, trained model v42?

Patterns

  • Immutable snapshots. Never overwrite a training dataset in place; write `s3://bucket/dataset/2026-09-02T04-00Z/` or an Azure ML data asset version, and reference the exact version in the training job.
  • Delta/time-travel tables. Delta Lake, Apache Iceberg, or Databricks give you `AS OF VERSION` queries — train against a historical state of a table that keeps getting new rows appended.
  • Hash-based lineage. Store a content hash of the training set alongside the model artifact so two "v1.3" models trained on different data are provably different, even if someone forgot to bump a version tag.
python — dataset versioning pattern
# Works the same conceptually on Azure ML data assets or SageMaker FeatureStore/S3 prefixes
dataset_version = f"customer_churn/{run_date}_{git_sha[:8]}"
snapshot_path = f"s3://ml-data/{dataset_version}/"

# Write once, never mutate
df.write.mode("error").parquet(snapshot_path)

# Record the hash so the registry can prove data identity later
data_hash = hash_dataframe_content(df)
log_metadata(dataset_version=dataset_version, data_hash=data_hash)
Pitfall

Point-in-time correctness bugs are the single most common source of training/serving skew: a feature like "customer's total orders" computed with data up to today during training, but the label was generated 30 days ago — leaking future information into the model. Always join features "as of" the label timestamp, not "as of now."

ExpertCore Pillar

Feature stores

🎈 In plain words

A feature store is a shared recipe box in the kitchen: the person practicing recipes and the person cooking for real customers both grab measurements from the exact same box, so nobody accidentally uses a different-sized cup and ruins the dish.

A feature store solves exactly one problem at scale: guaranteeing that the feature value your model saw offline during training is bit-for-bit the same computation used online at serving time — while serving the online path in single-digit milliseconds.

Offline store

Large, cheap, batch-queryable (Parquet/Delta on blob storage, or a warehouse table). Used for training-set generation with point-in-time joins.

Online store

Low-latency key-value store (Redis-compatible) holding only the latest value per entity, for real-time inference lookups.

Cloud-native options

  • Azure: Azure ML managed Feature Store (preview → GA), backed by an offline materialization store (ADLS Gen2) and an online store (Redis via Azure Cache for Redis).
  • AWS: SageMaker Feature Store — a single API with an offline store (S3 + Glue/Athena catalog) and an online store (backed internally by a low-latency store), plus get_record for real-time reads.
  • Cloud-agnostic: Feast (open source) — deployable on either cloud when you want to avoid platform lock-in for feature definitions.
python — SageMaker Feature Store: define + ingest
from sagemaker.feature_store.feature_group import FeatureGroup

fg = FeatureGroup(name="customer-churn-features", sagemaker_session=session)
fg.load_feature_definitions(data_frame=features_df)

fg.create(
    s3_uri="s3://ml-data/feature-store/offline/",
    record_identifier_name="customer_id",
    event_time_feature_name="event_time",
    role_arn=role,
    enable_online_store=True,   # turns on the low-latency serving path
)
fg.ingest(data_frame=features_df, max_workers=4)
python — Azure ML managed Feature Store: define + register
from azureml.featurestore import FeatureStoreClient
from azureml.featurestore.contracts import FeatureSetSpec, TransformationCode

fs_client = FeatureStoreClient(credential=credential, subscription_id=sub_id,
                                 resource_group=rg, name="churn-fstore")

spec = FeatureSetSpec(
    source=parquet_source,
    transformation_code=TransformationCode(path="./transform.py", transformer_class="ChurnTransformer"),
    index_columns=["customer_id"],
    source_lookback="P90D",   # point-in-time correctness window
)
fs_client.feature_sets.create_or_update(name="churn_features", version="3", spec=spec)
War story

A ride-sharing company's fraud model used a feature "driver's average trips/day over 7 days," computed in Spark for training and re-implemented in a Java microservice for serving. The two implementations rounded timestamps to different timezones. The model's offline AUC was 0.91; production precision was effectively random for one specific region for four months before anyone diffed the two feature computations. A feature store with a single transformation definition shared by both paths eliminates this class of bug entirely.

BeginnerCore Pillar

Experiment tracking

🎈 In plain words

This is like keeping a science notebook every time you run an experiment: what you changed, what happened, and a snapshot of the result — so you never have to guess “wait, which version of my experiment got the good result?”

Every training run should log: code version, data version, hyperparameters, metrics, and artifacts — automatically, not by hand in a spreadsheet.

Both Azure ML and SageMaker speak MLflow natively — this is the closest thing to a portable standard for tracking.

python
import mlflow
mlflow.set_experiment("churn-model")
with mlflow.start_run(run_name="xgb-depth6-lr01"):
    mlflow.log_param("max_depth", 6)
    mlflow.log_param("learning_rate", 0.1)
    model = train(X_train, y_train, max_depth=6, lr=0.1)
    mlflow.log_metric("val_auc", evaluate(model, X_val, y_val))
    mlflow.xgboost.log_model(model, artifact_path="model")
    mlflow.set_tag("git_sha", git_sha)
    mlflow.log_input(mlflow.data.from_pandas(X_train), context="training")

Azure ML's job/run tracking is MLflow-compatible under the hood — mlflow.log_metric calls inside an Azure ML job land in the Studio UI automatically, no extra wiring.

yaml — job.yml
$schema: https://azuremlschemas.azureedge.net/latest/commandJob.schema.json
code: ./src
command: python train.py --max_depth ${{inputs.max_depth}}
inputs:
  max_depth: 6
environment: azureml:sklearn-env@latest
compute: azureml:cpu-cluster
experiment_name: churn-model
python
from sagemaker.experiments.run import Run

with Run(experiment_name="churn-model", run_name="xgb-depth6",
         sagemaker_session=session) as run:
    run.log_parameter("max_depth", 6)
    run.log_metric(name="val_auc", value=0.912)
    run.log_file("model.tar.gz", is_output=True)
Tip

Log the data version, not just hyperparameters. Six months from now, "which dataset produced this AUC" is the question you'll actually be asked, and hyperparameters alone won't answer it.

IntermediateCore Pillar

Model registry & lineage

🎈 In plain words

The model registry is a locker where you keep only the best, labeled versions of your project — with a note describing which experiment it came from and who approved it for the science fair.

The registry is the contract between "training produced something" and "serving is allowed to use it." A good registry entry captures a model version's stage (None → Staging → Production → Archived), its lineage (data + code + run), and its evaluation results — and is the single source of truth both clouds and any downstream deployment system query.

CapabilityAzure ML Model RegistrySageMaker Model Registry
VersioningAuto-incrementing versions per model nameModel package groups with versions
Approval workflowStage tags + Azure DevOps/GitHub gatesNative approval status: PendingManualApproval → Approved/Rejected
LineageLinked job → data asset → environmentLinked training job, lineage via SageMaker ML Lineage Tracking
Cross-account/workspace sharingRegistries (separate from workspaces) for org-wide sharingCross-account model package groups via resource policies
Pitfall

Teams often register the model artifact but not the evaluation report that justified promotion. When a model is rolled back six weeks later, "why did we ever ship this" becomes archaeology. Attach the evaluation metrics, the approval actor, and the approval reason to the registry entry itself, not a separate doc that will rot.

ExpertCore Pillar

CI / CD / CT pipelines

🎈 In plain words

Imagine a toy-factory assembly line: CI checks that no part is broken, CD moves good toys onto store shelves, and CT means the factory automatically designs a new toy whenever kids' preferences change — almost no humans required.

Three distinct automations, often confused as one:

  • CI (Continuous Integration): on every commit — lint, unit test the pipeline code, validate data schemas, build the training container.
  • CD (Continuous Delivery): promote a trained, evaluated, approved model artifact through environments (dev → staging → prod) with progressively stricter gates.
  • CT (Continuous Training): automatically re-trigger the training pipeline itself — on a schedule, on drift detection, or on new label volume crossing a threshold.

Example: gated promotion pipeline

python — evaluation gate used identically on either cloud
current_prod_auc = get_metric(model_stage="Production", metric="auc")
candidate_auc   = get_metric(run_id=new_run.id, metric="auc")

if candidate_auc < current_prod_auc - 0.01:
    raise PromotionBlocked(f"Candidate AUC {candidate_auc} regresses vs prod {current_prod_auc}")

if fairness_gap(new_run) > MAX_FAIRNESS_GAP:
    raise PromotionBlocked("Fairness gate failed — see Responsible AI dashboard")

promote_to_registry(new_run, stage="Staging")  # never straight to Production
Tip

Never let a pipeline promote directly to Production. Force every promotion through Staging with a shadow-traffic or canary period, even if the "human approval" step is a Slack bot auto-approving after 30 minutes of clean canary metrics.

IntermediateCore Pillar

Deployment patterns

🎈 In plain words

This is like taste-testing a new recipe on a few customers before serving the whole restaurant (canary), secretly cooking it in the back without serving anyone (shadow), or having two full kitchens ready and instantly switching which one serves customers (blue/green).

Blue/Green

Two full environments; switch traffic atomically. Instant rollback, but 2x infra cost during the switch window.

Canary

Route a small % of traffic (1–10%) to the new model; watch metrics; ramp up gradually. Both Azure ML managed online endpoints and SageMaker endpoints support native traffic-split configs.

Shadow / dark launch

New model receives a copy of production traffic but its predictions are logged, not served. Zero user risk; validates real-world performance before canary.

Multi-armed bandit

Traffic allocation adapts based on observed reward in near-real time — used when you're optimizing a business metric (CTR, conversion) rather than just checking for regressions.

Serving topology choices

  • Real-time synchronous endpoint — low-latency, always-on. Highest cost, needed for user-facing inference (fraud check at checkout).
  • Serverless / on-demand inference — scales to zero, pay-per-invocation, tolerates cold-start latency. Good for spiky, low-volume workloads.
  • Batch inference — score millions of rows on a schedule, no latency constraint. Cheapest per-prediction.
  • Async inference — queue-based, for large payloads (video, long documents) where sync response isn't feasible.
Azure

Managed online endpoints support native blue/green via deployment traffic percentages (az ml online-endpoint update --traffic "blue=90 green=10"), and Kubernetes-based (AKS/Arc) endpoints for teams needing full cluster control.

AWS

SageMaker real-time endpoints support production variants with weighted traffic splitting natively; SageMaker Serverless Inference and Asynchronous Inference are distinct endpoint types you choose at creation, not settings you toggle later.

Monitoring & drift detection

🎈 In plain words

Monitoring is a smoke detector for your model. Checking uptime is like checking the lights still turn on. Checking for drift is like checking if the smoke detector's batteries are dying — you want to know before there's an actual fire, not after.

Four distinct things people lump together as "monitoring" — track them separately, because they have different owners, different alert channels, and different remediation:

TypeQuestion it answersTypical signal
OperationalIs the service up and fast?Latency p99, error rate, throughput
Data driftAre inputs changing shape?PSI / KL-divergence between training and live feature distributions
Concept driftIs the input→output relationship changing?Rolling accuracy/AUC once ground truth labels arrive
Prediction/output driftAre predictions shifting even without confirmed labels?Distribution of predicted class/score over time
python — population stability index (works identically on any cloud's captured logs)
def psi(expected, actual, buckets=10):
    breakpoints = np.percentile(expected, np.linspace(0, 100, buckets + 1))
    e_pct = np.histogram(expected, breakpoints)[0] / len(expected)
    a_pct = np.histogram(actual, breakpoints)[0] / len(actual)
    e_pct, a_pct = np.clip(e_pct, 1e-4, None), np.clip(a_pct, 1e-4, None)
    return np.sum((a_pct - e_pct) * np.log(a_pct / e_pct))

# Rule of thumb: PSI < 0.1 stable, 0.1-0.25 moderate shift (investigate), > 0.25 significant drift (retrain)
Azure

Azure ML Data Collector + Model Monitoring jobs compute drift on scheduled cadence against a registered training-data baseline, surfacing alerts through Azure Monitor and Application Insights.

AWS

SageMaker Model Monitor runs scheduled monitoring jobs comparing captured inference data (via Data Capture) against a baseline computed from the training set, with violations surfaced to CloudWatch and optionally EventBridge for automated retraining triggers.

War story

A telco's churn model had rock-solid operational monitoring — five nines uptime, sub-50ms latency, zero PagerDuty alerts for eight months. Retention spend based on its predictions crept up 40% with no matching improvement in retention. Root cause: a schema change upstream silently zero-filled a key tenure feature for three million records. Nothing broke; the model just got confidently wrong. Only a business-metric review caught it, not the monitoring stack — the org added data drift and prediction-distribution monitors the next quarter.

IntermediateCore Pillar

Governance, cost & responsible AI

🎈 In plain words

Governance is the rulebook that makes sure the robot is fair to everyone (not just good at guessing for one group of people), keeps a diary of every big decision, and that nobody leaves expensive machines running all night for no reason.

  • Access control: workspace/domain-level RBAC, secrets never in code (Azure Key Vault / AWS Secrets Manager), least-privilege service principals/IAM roles per pipeline stage.
  • Audit trail: every promotion, every deployment, every rollback logged with actor, timestamp, and reason — required for regulated industries (finance, healthcare, insurance).
  • Fairness & explainability: bias metrics across protected groups computed as a gate, not an afterthought (Azure Responsible AI dashboard, AWS SageMaker Clarify).
  • Cost control: spot/low-priority compute for training, autoscaling to zero for low-traffic endpoints, scheduled shutdown of idle notebook instances — GPU idle time is the single biggest unforced MLOps cost leak.
Pitfall

The most expensive line item in most mid-size MLOps budgets isn't training compute — it's forgotten always-on notebook/Studio compute instances and over-provisioned real-time endpoints sized for peak traffic that never arrives. Enforce auto-shutdown policies and right-size instance types against actual p95 load, not intuition.

Workspace & compute setup

🎈 In plain words

This is getting your backpack (workspace) and pencil case (compute) ready before homework — except this pencil case can grow more pencils when you have a big assignment, then shrink back down (and stop costing money) when you're done.

bash — az CLI: create workspace + compute cluster
az ml workspace create -n mlops-ws -g mlops-rg -l eastus

az ml compute create --name cpu-cluster --type AmlCompute \
  --min-instances 0 --max-instances 8 \
  --size Standard_DS3_v2 --workspace-name mlops-ws -g mlops-rg

# GPU cluster for training, scales to zero when idle
az ml compute create --name gpu-cluster --type AmlCompute \
  --min-instances 0 --max-instances 4 \
  --size Standard_NC6s_v3 --workspace-name mlops-ws -g mlops-rg

Setting min-instances 0 is the single most important cost lever in Azure ML — clusters scale down to zero nodes (zero cost) when there's no queued job.

IntermediateAzure ML

Pipelines — SDK v2 and YAML

🎈 In plain words

A pipeline is a step-by-step instruction list, like a recipe: wash the vegetables, then chop them, then cook them. Azure ML pipelines are recipes written either in Python or a simple settings file (YAML), and the computer follows the steps in order.

Azure ML pipelines are DAGs of reusable, versioned components. Two authoring styles, same underlying engine:

python — SDK v2 pipeline definition
from azure.ai.ml import MLClient, dsl, Input, Output
from azure.ai.ml.entities import Environment

train_env = Environment(image="mcr.microsoft.com/azureml/curated/sklearn-1.5:latest")

@dsl.pipeline(compute="cpu-cluster", description="churn training pipeline")
def churn_pipeline(raw_data: Input, min_auc: float = 0.85):
    prep = prep_component(input_data=raw_data)
    train = train_component(training_data=prep.outputs.processed, max_depth=6)
    eval_step = eval_component(model=train.outputs.model, test_data=prep.outputs.test, min_auc=min_auc)
    register_step = register_component(model=train.outputs.model, eval_report=eval_step.outputs.report)
    return {"registered_model": register_step.outputs.model_uri}

ml_client = MLClient.from_config(credential=DefaultAzureCredential())
pipeline_job = churn_pipeline(raw_data=Input(path="azureml:churn-raw:5"))
ml_client.jobs.create_or_update(pipeline_job, experiment_name="churn-training")
yaml — equivalent declarative pipeline.yml
$schema: https://azuremlschemas.azureedge.net/latest/pipelineJob.schema.json
display_name: churn_pipeline
compute: azureml:cpu-cluster
inputs:
  raw_data:
    type: uri_folder
    path: azureml:churn-raw@5
jobs:
  prep:
    component: azureml:prep_component@latest
    inputs: { input_data: ${{parent.inputs.raw_data}} }
  train:
    component: azureml:train_component@latest
    inputs: { training_data: ${{parent.jobs.prep.outputs.processed}} }
  evaluate:
    component: azureml:eval_component@latest
    inputs: { model: ${{parent.jobs.train.outputs.model}} }
ExpertAzure ML

Azure DevOps CI/CD for ML

🎈 In plain words

This is an automatic checklist that runs every time you turn in new homework: any spelling errors? Does the answer make sense? Only if it passes every check does a human teacher get asked to approve it going on the class bulletin board (production).

yaml — azure-pipelines.yml
trigger:
  branches: { include: [main] }
  paths: { include: [src/*, pipelines/*] }

stages:
  - stage: CI
    jobs:
      - job: LintAndTest
        steps:
          - script: pip install -r requirements-dev.txt && pytest tests/ -v
          - script: flake8 src/

  - stage: Train
    dependsOn: CI
    jobs:
      - job: RunTrainingPipeline
        steps:
          - script: az ml job create -f pipelines/pipeline.yml --stream
          - script: python scripts/check_eval_gate.py --min-auc 0.85

  - stage: DeployStaging
    dependsOn: Train
    jobs:
      - deployment: ToStaging
        environment: staging
        strategy:
          runOnce:
            deploy:
              steps:
                - script: az ml online-deployment create -f deploy/staging.yml --all-traffic

  - stage: DeployProduction
    dependsOn: DeployStaging
    condition: succeeded()
    jobs:
      - deployment: ToProd
        environment: production   # manual approval gate configured on this environment
        strategy:
          runOnce:
            deploy:
              steps:
                - script: az ml online-deployment update -f deploy/prod.yml --traffic "blue=90 green=10"

The environment: production reference lets you attach a manual-approval check in Azure DevOps' Environments settings — the pipeline pauses and waits for a named approver before the deployment step runs.

Endpoints, AKS & batch inference

🎈 In plain words

This is how the model actually answers questions once it's “live” — like a helpdesk that can either answer instantly (real-time endpoint) or handle a giant stack of questions overnight all at once (batch).

az ml online-endpoint update --name churn-endpoint --traffic "blue=90 green=10"
# watch metrics for N hours, then either:

SageMaker Pipelines SDK

🎈 In plain words

Same idea as the Azure recipe pipeline, but written entirely in Python code — a very detailed to-do list your computer follows step by step, only moving on if the previous step succeeded.

python — pipeline definition
from sagemaker.workflow.pipeline import Pipeline
from sagemaker.workflow.steps import ProcessingStep, TrainingStep
from sagemaker.workflow.condition_step import ConditionStep
from sagemaker.workflow.conditions import ConditionGreaterThanOrEqualTo
from sagemaker.workflow.model_step import ModelStep

prep_step = ProcessingStep(name="PrepChurnData", processor=sk_processor,
                            inputs=[...], outputs=[...], code="prep.py")

train_step = TrainingStep(name="TrainChurnModel", estimator=xgb_estimator,
    inputs={"train": TrainingInput(s3_data=prep_step.properties.ProcessingOutputConfig.Outputs["train"].S3Output.S3Uri)})

eval_step = ProcessingStep(name="EvaluateModel", processor=eval_processor,
    inputs=[...], outputs=[PropertyFile(name="EvalReport", output_name="evaluation", path="evaluation.json")])

register_step = ModelStep(name="RegisterModel", step_args=model.register(
    model_package_group_name="churn-models",
    approval_status="PendingManualApproval",
    content_types=["text/csv"], response_types=["text/csv"]))

condition_step = ConditionStep(
    name="CheckAUCGate",
    conditions=[ConditionGreaterThanOrEqualTo(
        left=JsonGet(step_name=eval_step.name, property_file="EvalReport", json_path="metrics.auc"),
        right=0.85)],
    if_steps=[register_step], else_steps=[])

pipeline = Pipeline(name="churn-training-pipeline",
    steps=[prep_step, train_step, eval_step, condition_step])
pipeline.upsert(role_arn=role)
pipeline.start()

The ConditionStep is SageMaker's native evaluation gate — the model only reaches the registry if the AUC condition passes, expressed declaratively in the DAG rather than as an imperative script.

LLMOps addendum

🎈 In plain words

This is everything above, but for chatbots like the one answering you right now — except you also have to track the exact wording of the instructions you gave it, and grade its answers even though there's no single “correct number” to check against.

Large language model systems inherit everything above, plus new failure surfaces that classic MLOps tooling doesn't cover out of the box.

  • Prompt versioning: treat prompts/system messages as versioned artifacts with the same rigor as model weights — a prompt edit is a deployment, and needs the same gate.
  • Evaluation is harder: no single "AUC." Use a blend of automated eval (LLM-as-judge with a fixed rubric, embedding-similarity to reference answers) and human review sampling, tracked over time like any other quality metric.
  • Retrieval pipeline (RAG) versioning: the vector index, chunking strategy, and embedding model version are all part of "the model" for reproducibility purposes — version them together.
  • Cost and latency as first-class metrics: token cost per request and p99 latency belong on the same dashboard as quality, since a "better" model swap can silently 5x your inference bill.
  • Guardrails as a pipeline stage: content-safety and jailbreak-resistance checks belong in the CI/CD gate, not bolted on only at the UI layer.

Azure

Azure AI Foundry (formerly Azure AI Studio) layers prompt flow, evaluation, and content safety on top of the same Azure ML workspace/registry primitives covered above.

AWS

Amazon Bedrock plus SageMaker's model evaluation and Guardrails features extend the same SageMaker Pipelines/registry pattern to foundation-model workflows and RAG evaluation.

Senior / 8+ year interview Q&A

🎈 In plain words

These are the kind of tricky “what would you actually do” questions a company asks someone applying for a senior job — the kind you can't answer by memorizing a definition, only by having actually dealt with the problem before.

The kind of questions that separate "has used SageMaker" from "has run MLOps at scale and been paged for it."

How do you decide between a shared feature store and letting each model own its feature pipeline?

Shared feature stores pay off when (a) multiple models consume overlapping features — churn, upsell, and fraud models all wanting "days since last purchase" — and (b) training/serving skew has already bitten the org once. They cost coordination overhead: a shared schema now needs a change-management process, and a bug in a shared feature blast-radiuses across every consuming model instead of one. For a single-model team, a well-tested local feature pipeline with strict point-in-time joins is often the right call until a second or third model shows up wanting the same features.

Your production model's offline eval metrics look fine but online business KPIs are degrading. Walk through your debugging process.

First separate "is the model getting different inputs" from "is the model behaving differently on the same inputs." Check prediction-distribution drift and input feature drift before touching the model itself — most of these incidents are upstream data issues, not model issues (see the churn/telco war story above). If inputs and predictions look stable, check for a training/serving skew bug — replay a batch of live production requests through the offline evaluation pipeline and diff. Only after ruling those out do you consider genuine concept drift requiring retraining.

How do you handle rollback when the "bad" model has already been serving for hours and downstream systems cached its outputs?

Rollback the serving traffic immediately (traffic-split flip, near-instant on both Azure managed endpoints and SageMaker production variants) — that stops new bad predictions. Separately, you need a remediation plan for outputs already consumed: if predictions were cached or wrote to a downstream store (e.g., a risk score persisted to a transactions table), you need a batch reprocessing job to correct those records, which is a different system than the serving rollback. Teams that only plan for "stop the bleeding" and not "clean up what already bled" get bitten on audits.

When would you choose a Kubernetes-based deployment (AKS/EKS) over the managed endpoint options on either cloud?

When you need capabilities the managed endpoint doesn't expose: custom sidecar containers, non-standard networking/service-mesh requirements, GPU-sharing across multiple models on one node for cost efficiency, or you're already running the rest of your microservices on that cluster and want one operational model instead of two. The cost is real: you now own node patching, cluster upgrades, and autoscaling tuning that the managed endpoint would have handled for you. Default to managed endpoints; justify Kubernetes with a specific unmet requirement, not "more control" as a vague preference.

How do you set a data-drift alert threshold that doesn't cry wolf?

Don't pick a PSI/threshold value from a blog post — compute the metric's natural variance on historical, known-stable periods first (e.g., week-over-week PSI across a quiet quarter) and set the alert threshold a few standard deviations above that baseline noise floor. Pair it with a minimum sustained-duration requirement (drift persisting 3 consecutive windows, not one blip) before paging anyone. Alerting on every daily fluctuation trains the on-call rotation to ignore the channel.

Explain the trade-off between shadow deployment and canary deployment, and when each is worth the cost.

Shadow costs double the inference compute (both models run on every request) but zero user risk — worth it when a wrong prediction is expensive (financial decision, medical triage) and you need real production-traffic validation before any user sees the new model's output. Canary costs less compute overhead but exposes a real slice of users to the new model — worth it when a wrong prediction is tolerable/recoverable (a slightly worse product recommendation) and you want faster iteration cycles than a full shadow-then-canary sequence allows.

How do you structure IAM/RBAC so a data scientist can iterate quickly without being able to accidentally push to production?

Separate roles by pipeline stage, not by person: a "training" role can read data, write to a scratch/staging registry namespace, and launch training jobs, but has no permission to update production endpoint traffic weights or approve a model package. Production promotion requires a distinct role, typically held by a service principal/pipeline identity that only acts after an explicit approval gate — not a personal credential, so "who can deploy to prod" is auditable as "which pipeline runs, triggered by which approval," not "who has the right IAM policy attached to their personal user."

Your team wants "one pipeline that works on both Azure and AWS." Is that a good goal?

Usually a partial goal, not a total one. Cloud-agnostic training code (plain Python/PyTorch/XGBoost, MLflow for tracking) is realistic and valuable — it protects you from platform lock-in on the part that changes most (model logic). Fully cloud-agnostic orchestration/deployment is usually not worth the abstraction cost: you end up building a thin, buggy re-implementation of whichever managed service you're avoiding, and lose native integrations (IAM, monitoring, cost tools) on both sides. The pragmatic split from the healthcare case study above — portable modeling code, forked infra/deployment layer per cloud — is the pattern that tends to actually ship.
