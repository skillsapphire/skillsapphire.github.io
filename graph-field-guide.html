01 · Foundations

What's a Graph Database?

The data structure that treats "how things connect" as first-class information, not an afterthought.

🧸 Explain it like I'm 8

Imagine a big piece of paper. You draw a dot for every person you know — that's your friend Sam, your teacher, your dog. Then you draw a line between dots that know each other. Sam is connected to your teacher because Sam is in your class. Your dog is connected to you because it's your dog. A graph database is just a computer's version of that paper — except it can hold millions of dots and lines, and it can answer questions like "who is connected to Sam, who is connected to THEM, and so on" super fast.

Formally: a graph database stores data as nodes (things — a person, an account, a transaction), relationships (the connections between things — OWNS, TRANSFERRED_TO, LIVES_AT), and properties (facts attached to either — a name, an amount, a date). Unlike a relational database, the relationship is stored physically as a pointer at write time, not computed at query time with a JOIN.

Why not just use a normal (relational/SQL) database?

🧸 Explain it like I'm 8

A normal database is like a filing cabinet of index cards, sorted into drawers — one drawer for "people," one for "accounts." If you want to know how two cards are related, you have to search through drawers over and over, matching numbers. A graph database already has string tied between the cards. You just follow the string — you don't have to search.

Relational (SQL)Graph (Neo4j)
Relationships are implicit — recomputed on every query via JOINRelationships are explicit — stored physically, walked in O(1) per hop
A 5-hop query ("friend of friend of friend...") means 5 expensive JOINsA 5-hop query is 5 pointer traversals — cost barely changes with hop count
Schema is fixed columns/tablesSchema is flexible — new relationship types added without migrations
Best for: reporting, transactions, tabular dataBest for: fraud rings, recommendations, network analysis, lineage
Not a silver bullet: graph databases are usually not the best choice for simple aggregate reporting ("total revenue by region last quarter") — a columnar warehouse still wins there. Graphs win when the question is about connectivity, not aggregation.

The property graph model

Nodes carry labels (:Customer, :Account) and properties. Relationships carry a type (:OWNS, :SENT) and their own properties (amount, date). This is exactly how Neo4j stores it on disk.
02 · Foundations

Neo4j Deep Dive

The most widely deployed graph database in production, and the reference implementation for the property graph model.

🧸 Explain it like I'm 8

If a graph database is the idea of "dots and strings," Neo4j is an actual box you can buy that does dots and strings really, really well — and lets you ask it questions in a language called Cypher that reads almost like drawing the picture with words.

Cypher: querying by drawing ASCII art

Cypher's core trick: the query looks like the pattern you're searching for. Parentheses are nodes, dashes and arrows are relationships.

cypherfind money mule rings
// Find accounts that received money from 5+ different sources
// within 48 hours, then moved it out within 2 hours — classic mule pattern
MATCH (source:Account)-[t1:TRANSFER]->(mule:Account)-[t2:TRANSFER]->(sink:Account)
WHERE t2.timestamp - t1.timestamp < duration('PT2H')
WITH mule, count(DISTINCT source) AS fan_in, sink
WHERE fan_in >= 5
RETURN mule.accountId, fan_in, collect(sink.accountId) AS outflow_targets
ORDER BY fan_in DESC;

Core architecture

  • Native storage engine — relationships are stored as physical pointers ("index-free adjacency"), so traversal cost depends on the pattern size, not the total database size.
  • Causal Clustering — one leader (writes) plus core + read-replica members for horizontal read scaling and high availability, with causal consistency (a client always reads its own writes).
  • ACID transactions — unlike many NoSQL stores, Neo4j is fully transactional, which matters a lot in banking.
  • Neo4j Graph Data Science (GDS) library — in-database implementations of PageRank, Louvain community detection, node similarity, and ML pipelines (node classification, link prediction) that run on the graph directly.
  • Neo4j Fabric / sharding — federates queries across multiple graph databases for very large deployments.

03 · Foundations

Knowledge Graphs

A graph database is the storage engine. A knowledge graph is what you get when the dots and strings represent real-world facts, meaningfully typed and connected.

🧸 Explain it like I'm 8

Think about everything you know about your family: Mom works at a hospital. Grandpa lives in Chicago. Chicago is a city. A hospital is a kind of building. If you drew ALL of that as dots and lines — not just your family, but how jobs, cities, and buildings relate to each other too — that giant, organized web of facts is a knowledge graph. It's not just data, it's data that understands what it's talking about.

Technically, a knowledge graph = a graph database + an ontology/schema (what types of things and relationships are allowed to exist, e.g. a Person can be EMPLOYED_BY an Organization, but not EMPLOYED_BY a City) + entity resolution (deciding that "J. Smith," "John Smith," and "Smith, John" are the same real person).

Banking example: a customer knowledge graph

One customer's 360° view. The power shows up when a second customer shares the same phone number or address — that's how synthetic-identity rings get caught.

Ontology vs schema-free graph

You can build a graph with zero upfront modeling ("schema-free") — great for exploration. Production knowledge graphs in regulated industries almost always define an ontology: allowed node labels, allowed relationship types between them, required properties, and data-quality constraints — often expressed and validated with SHACL or simply enforced through ingestion pipelines and Neo4j constraints.

Graph Algorithms You'll Actually Use

The mathematical tools that turn "a bunch of dots and lines" into a ranked list of suspicious things.

🧸 Explain it like I'm 8

If your dot-and-string drawing is huge, you can't just stare at it and know what's important. Graph algorithms are little games you play on the drawing: "which dot has the most strings touching it?" or "which group of dots are all tightly tangled together, like their own little clump?" Playing these games tells you interesting things without you having to look at every single dot yourself.

AlgorithmWhat it findsBanking use
PageRankWhich nodes are most "influential" based on who points to themRank accounts by centrality in a payments network to spot hub accounts (often mules)
Louvain / LeidenCommunities — tightly-connected clustersCluster accounts into "rings" for fraud-ring or collusion detection
Betweenness CentralityNodes that sit on the most shortest-paths between othersFind "broker" accounts that bridge otherwise unconnected fraud clusters
Shortest Path / DijkstraCheapest route between two nodes"How is this new applicant connected to a known fraudster, and through how many hops?"
Node Similarity / JaccardNodes that share many of the same neighborsEntity resolution — "these two customer records probably describe the same human"
Weakly Connected ComponentsGroups of nodes reachable from each other, ignoring directionQuickly bucket the whole transaction graph into isolated sub-networks before deeper analysis
Node2Vec / GraphSAGE (embeddings)Turns each node into a vector that encodes its graph neighborhoodFeed into an ML fraud-scoring model alongside transaction features

05 · AI + Graphs

GraphRAG

Retrieval-Augmented Generation, upgraded so the "retrieval" part walks a knowledge graph instead of just matching similar-sounding chunks of text.

🧸 Explain it like I'm 8

Normal RAG is like asking a librarian for "books that use similar words to my question," then reading them to answer you. That works for simple questions, but fails at "how is my grandpa connected to my cousin's dog's vet?" — because no single book has that whole chain in it. GraphRAG instead lets the librarian walk through the giant dots-and-strings web, hopping from fact to fact, collecting the whole chain, and THEN explaining it to you.

Why plain vector RAG breaks on connected questions

  • Multi-hop questions — "Which of our merchants share a settlement account with a merchant we terminated for fraud last quarter?" No single document chunk contains that answer; it's a chain across three entities.
  • Global / aggregation questions — "What are the main themes across all fraud-investigation case notes this year?" Chunk-similarity retrieval can't summarize across a whole corpus; graph community summaries can.
  • Precision on structured facts — dates, amounts, ownership chains are exact facts, not "semantically similar" text — a graph traversal returns the exact fact; a vector search returns a probably-related paragraph.

GraphRAG pipeline

Offline: docs → extracted entities/relations → knowledge graph → community summaries + vector index. Online: query → hybrid retrieval (vector similarity finds seed nodes, graph traversal expands context) → assembled subgraph → grounded LLM answer.

Two GraphRAG retrieval patterns

PatternHow it worksGood for
Local searchVector-match the query to a few seed entities, then expand N hops outward in the graph to build contextSpecific, fact-based questions ("What's the ownership chain of Merchant X?")
Global searchPre-computed community summaries (via Louvain + LLM summarization) are searched directly — no live traversalBroad, thematic questions across a whole corpus ("What are common patterns in Q3 fraud cases?")

Minimal LangChain + Neo4j GraphRAG

pythongraph_rag.py
from langchain_neo4j import Neo4jGraph, GraphCypherQAChain
from langchain_anthropic import ChatAnthropic

graph = Neo4jGraph(url="bolt://localhost:7687", username="neo4j", password="...")
llm = ChatAnthropic(model="claude-sonnet-5")

# The chain: NL question -> Cypher -> graph result -> NL answer
chain = GraphCypherQAChain.from_llm(
    llm=llm, graph=graph, verbose=True,
    allow_dangerous_requests=True  # you MUST scope DB permissions read-only in prod
)

result = chain.invoke({"query": "Which merchants share a settlement account with a terminated merchant?"})
print(result["result"])
Production note: never let an LLM-generated Cypher query run with write permissions or against unbounded traversals. Use a read-only DB user, query timeouts, and row/hop limits — an unconstrained MATCH can walk millions of nodes.
06 · AI + Graphs

Graphiti — Temporal Knowledge Graphs for Agents

An open-source framework (from Zep) purpose-built for giving AI agents a memory that is a live, time-aware knowledge graph, not a static document dump.

🧸 Explain it like I'm 8

Most knowledge graphs are like a photograph — they show facts as they are right now. But real life changes: your best friend today might not be your best friend next year, and a company's CEO changes over time. Graphiti is like a photo album with dates on every picture. It doesn't erase the old photo when a new one comes in — it keeps both, and knows which one is "true" for which point in time. That way, an AI assistant can answer "who was the CEO in 2022?" AND "who's the CEO now?" correctly.

What makes it different from a normal KG

  • Bi-temporal model — every edge/fact has both a valid time (when it was true in the world) and a transaction time (when the system learned it). This lets you query "what did we believe on March 1st?" separately from "what was actually true on March 1st?" — critical for audit trails in banking.
  • Incremental, non-destructive updates — new facts don't overwrite old ones; they invalidate them with an end-timestamp, preserving full history automatically.
  • Built for agent memory — designed to ingest streaming conversation turns, tool outputs, and events in real time, not just batch-processed documents (the core GraphRAG use case).
  • Hybrid retrieval — combines semantic (embedding) search, keyword (BM25) search, and graph traversal, so an agent can recall "the fact" and "the reasoning path" to it.

GraphRAG (static corpus) vs Graphiti (live agent memory)

Classic GraphRAGGraphiti
Data sourceBatch-ingested document corpusStreaming events, conversations, tool calls
UpdatesPeriodic full/partial re-indexContinuous incremental writes
Time awarenessUsually none / single snapshotBi-temporal by design
Primary consumerAnalyst / RAG chatbot over documentsAn autonomous agent's working + long-term memory

Banking angle

A relationship-manager copilot needs to know that a client's risk appetite changed after a life event, not just their current stated preference — and needs to show a regulator exactly what the system knew and when. That's a bi-temporal graph problem, which is exactly what Graphiti targets.

pythongraphiti — adding an episode
from graphiti_core import Graphiti

graphiti = Graphiti("bolt://localhost:7687", "neo4j", "...")

# An "episode" is a timestamped chunk of new information —
# a conversation turn, a document update, a system event
await graphiti.add_episode(
    name="advisory_call_2026_08_20",
    episode_body="Client stated they now prefer low-volatility "
                 "instruments following a change in retirement timeline.",
    source_description="CRM call transcript",
    reference_time="2026-08-20T14:30:00Z",
)

# Query: Graphiti resolves this against prior facts, invalidating
# the old "risk appetite" edge rather than deleting it
results = await graphiti.search("What is the client's current risk appetite?")
07 · AI + Graphs

Python Integration

The plumbing that connects your graph to everything else — ETL, agents, APIs, dashboards.

🧸 Explain it like I'm 8

Python is like a universal remote control. It can talk to the graph database, talk to the AI model, talk to other company systems — and pass messages between them so they work together, even though each one speaks its own "language."

The official driver — talking to Neo4j directly

pythonneo4j official driver
from neo4j import GraphDatabase

driver = GraphDatabase.driver("bolt://localhost:7687", auth=("neo4j", "password"))

def find_shared_devices(tx, account_id):
    query = """
    MATCH (a:Account {accountId: $id})<-[:USED_BY]-(d:Device)-[:USED_BY]->(other:Account)
    WHERE other.accountId <> $id
    RETURN other.accountId AS linkedAccount, d.deviceId AS sharedDevice
    """
    return tx.run(query, id=account_id).data()

with driver.session() as session:
    linked = session.execute_read(find_shared_devices, "ACC-88213")
    print(linked)

08 · Banking in Production

Real-World Production Use Cases

Generalized patterns modeled on how graph databases are actually deployed across retail and commercial banking — not vendor marketing claims.

🧸 Explain it like I'm 8

Banks care about graphs because bad guys don't act alone in neat little boxes — they share phones, addresses, devices, and money with each other. A spreadsheet can't see that web. A graph lights the whole web up at once.

Fraud

Real-time fraud ring detection

Every new transaction is checked in-graph against shared devices, IPs, and beneficiaries within milliseconds — flagging "first-party fraud rings" where dozens of seemingly unrelated accounts share a fingerprint.

Typical pattern: Neo4j + streaming ingestion (Kafka) + GDS similarity scoring
AML

Anti-money-laundering: layering detection

Money launderers move funds through many accounts to obscure origin ("layering"). Graph traversal finds cyclic and fan-out/fan-in transaction patterns that a rules engine scanning one transaction at a time will never see.

Typical pattern: cycle detection + temporal windowing over the transaction graph
Entity Resolution

KYC / Know Your Customer

Resolving "is this new applicant the same person as an existing customer, or related to a sanctioned entity?" across messy, inconsistent records — matched via shared identifiers and graph similarity, not exact string match.

Typical pattern: node similarity + probabilistic matching + sanctions-list linking
Credit Risk

Connected-party credit risk

Corporate lending risk isn't just one company's balance sheet — it's their ownership chains, guarantors, and shared directors. A graph surfaces hidden concentration risk (e.g., 40 "unrelated" borrowers all controlled by one holding structure).

Typical pattern: ownership-chain traversal + centrality scoring for concentration limits
Customer 360

Relationship-manager copilot

Wealth and commercial bankers query a unified view spanning accounts, products, household relationships, and interaction history in one hop, instead of stitching together five siloed systems.

Typical pattern: knowledge graph + GraphRAG chatbot over CRM + product data
Regulatory

Data lineage & regulatory reporting

Regulators increasingly ask "prove where this reported number came from." A lineage graph tracks every transformation from source system to regulatory report, answerable in one traversal instead of an audit archaeology dig.

Typical pattern: metadata graph + Change Data Capture from ETL pipelines
Fraud

Synthetic identity detection

Fraudsters blend real SSNs/PANs with fake names to build a credit history over months before "busting out." Graphs catch it early by surfacing identity fragments (phone/address/device) shared across supposedly unrelated new applicants.

Typical pattern: shared-attribute clustering + velocity features on new-account graphs
Recommendation

Next-best-product / cross-sell

Product recommendations based on what similar customers (by graph proximity, not just demographics) purchased next — capturing behavioral similarity that flat tables miss.

Typical pattern: node embeddings (Node2Vec/GraphSAGE) + collaborative filtering

Why banks specifically (regulatory + scale reality)

  • Explainability requirement: regulators want to know why a transaction was flagged. "This account is 2 hops from a sanctioned entity via a shared beneficiary" is auditable; a black-box ML score alone often isn't sufficient on its own.
  • Sub-second SLAs: card-present fraud checks must return in well under 100ms — this is why real-time graph engines (or precomputed graph features feeding a fast model) matter, not ad hoc analytics jobs.
  • Adversarial and evolving: fraud patterns shift constantly, so static rules decay; graph + ML approaches adapt faster because they detect structural patterns, not just known signatures.
09 · Production Architecture

Agentic Solution — Architecture & Design

A production design for an autonomous or semi-autonomous agent that reasons over a graph-backed knowledge base inside a regulated bank.

🧸 Explain it like I'm 8

An "agent" is like giving the AI hands and feet, not just a mouth. Instead of only talking, it can go look things up, use tools, take a few steps, check its own work, and come back with an answer — kind of like sending a very capable intern to go investigate something and report back, except you get to watch every step it takes.

Orchestrator agent plans steps and calls scoped tools (graph query, GraphRAG retrieval, temporal memory, core banking API, graph analytics). Every write action passes through the policy/guardrail engine; everything is logged for audit.

Design decisions that matter in production

1. Read-only by default, human-approved writes

The agent's graph and API tools run under a database role with read-only permissions. Any action with real-world effect (freezing an account, filing a suspicious-activity report) requires an explicit human approval step — the agent proposes, a human disposes.

2. Bounded tool calls

Every Cypher tool call enforces a query timeout, a max-hop limit, and a max-row cap server-side — never trust the LLM-generated query to be well-behaved on its own.

3. Planner / sub-agent separation

A single "do everything" agent is hard to evaluate and secure. Split into an orchestrator (decides which specialist to call) and narrow sub-agents/tools (graph lookup, GraphRAG Q&A, memory) each with a tight, auditable scope of what they're allowed to touch.

4. Temporal memory via Graphiti

Multi-turn investigations ("we discussed this customer last week — what changed since?") need memory that respects time, not just the last N chat messages — this is exactly Graphiti's niche.

5. Full observability

Every tool call, retrieved subgraph, and generated Cypher query is logged with the final answer — required both for debugging agent behavior and for regulatory audit trails.

Common failure mode: letting the agent's natural-language-to-Cypher tool run unconstrained against production. Always sandbox with a replica, enforce timeouts/row-limits, and never expose write Cypher directly to an LLM-controlled tool.
10 · Production Architecture

Production RAG System — Architecture & Design

The full lifecycle: ingestion, indexing, hybrid retrieval, generation, evaluation, and the operational concerns that only show up at scale.

🧸 Explain it like I'm 8

RAG is like an open-book test for the AI. Instead of making it memorize everything (which it forgets or gets wrong), you let it look things up in the right book, at the right page, right before it answers. A "production" RAG system is the whole library system behind that — how books get added, organized, found quickly, and kept up to date, plus someone checking the AI didn't misquote the book.

Offline ingestion builds the graph + vector + keyword indexes once; the online path fans a query out to hybrid retrieval, re-ranks, assembles a token-budgeted context with citations, then generates. Evaluation, caching, and governance wrap the whole system.

Key production decisions

Hybrid retrieval, not vector-only

Combine dense vector similarity (semantic match), sparse BM25 (exact keyword/ID match — critical for account numbers, ticket IDs), and graph traversal (multi-hop facts) — then re-rank the merged candidate set with a cross-encoder before it reaches the LLM.

Groundedness over fluency

Every generated answer should carry citations back to the specific nodes/chunks used, and a groundedness check (does the answer actually follow from retrieved context, or did the model add unsupported claims?) should run before the answer reaches a customer-facing or compliance-sensitive surface.

Evaluation as a first-class pipeline stage

  • Retrieval metrics: precision@k, recall@k against a labeled test set of real questions.
  • Generation metrics: groundedness/faithfulness, answer relevancy, citation accuracy.
  • Regression testing: re-run the eval suite on every index or prompt change before deploying — RAG systems silently degrade when source data or chunking changes.

Freshness

Decide per data source whether it needs real-time (Change Data Capture streaming into the graph), near-real-time (micro-batch every few minutes), or batch (nightly) updates — indexing everything in real time is usually unnecessary cost.

Security & governance specific to banking

  • Row/entity-level access control — a relationship manager should only retrieve context for customers they're authorized to serve, enforced at the retrieval layer, not just the UI.
  • PII redaction at ingestion and, defensively, again before any external-facing generation step.
  • Prompt-injection defenses — treat retrieved graph/document content as untrusted input; it can contain adversarial instructions if any ingested source is user-editable (support tickets, chat transcripts).
  • Full audit trail — log the query, retrieved context, and generated answer together, retained per regulatory record-keeping requirements.
11 · Rounding it out

Concepts Worth Adding to the Picture

Things that don't fit neatly under the headings above but matter once this goes to production.

Vector databases vs. graph databases — not competitors

🧸 Explain it like I'm 8

A vector database is great at "find me things that feel similar." A graph database is great at "find me things that are actually connected." A GraphRAG system usually uses both together — like using both your eyes (similarity) and your memory of who's related to whom (structure) to answer a question.

Modern Neo4j (5.x+) actually ships a native vector index, so many teams run a single database for both — simplifying the architecture versus stitching together a separate vector store (Pinecone, Weaviate, pgvector) and graph store.

Entity resolution

The unglamorous but essential process of deciding two records describe the same real-world entity ("Robert Chen" vs "Bob Chen" vs "R. Chen, DOB 1985") — usually a blend of deterministic rules (matching national ID), probabilistic scoring (fuzzy name + address match), and graph similarity (shared neighbors). Get this wrong and every downstream fraud/KG feature inherits the error.

Graph embeddings

Techniques like Node2Vec and GraphSAGE convert each node into a fixed-length vector that captures its neighborhood structure, so standard ML models (XGBoost, neural nets) can consume "graph-shaped" information as ordinary features — this is how graph structure quietly ends up inside a bank's existing fraud-scoring models without replacing them.

Change Data Capture (CDC)

The mechanism (often Debezium + Kafka) that streams every insert/update/delete from core banking systems into the graph in near-real time, so the knowledge graph doesn't silently go stale — essential for any fraud use case with a sub-minute detection SLA.

Multi-agent orchestration frameworks

Beyond a single agent + tools, production agentic systems often use frameworks like LangGraph, CrewAI, or the Model Context Protocol (MCP) to define explicit state machines for how sub-agents hand off work, retry, and escalate to a human — worth a dedicated look once a single-agent design proves out.

Graph schema governance

As a knowledge graph grows past a handful of contributors, uncontrolled schema drift (five different relationship types that all mean "owns") becomes the biggest quality risk — not the database technology. Treat the ontology itself as a reviewed, versioned artifact.

Observability for graph + RAG systems

Standard APM isn't enough — you also want: query latency percentiles per traversal depth, retrieval hit-rate dashboards, embedding drift detection (are new documents semantically different from what the index was tuned on?), and LLM-specific tracing (LangSmith, Langfuse, or Anthropic's own tooling) showing every tool call an agent made.

Cost management

LLM calls for entity extraction during ingestion, and for generation at query time, are usually the dominant cost in a GraphRAG system — not the graph database itself. Caching, cheaper models for extraction, and batching are the usual levers.
