NovaRetail IT Support Copilot (Agentic RAG on Azure)

An enterprise IT support assistant for 3,000 employees. It answers from the company's private IT knowledge base first, checks whether the evidence is good enough before answering, falls back to public web search only when needed, and hands the problem to a human instead of guessing.

Everything runs on Azure services. Nobody stores passwords: services authenticate to each other with managed identities.

Status, stated plainly. This is a complete, reviewed implementation, but it has not been run against live Azure resources. What was verified: 24 unit and workflow tests pass (chunking, hashing, incremental diff, and the full LangGraph routing with every Azure call faked); every module imports against current SDK releases; the Bicep template compiles with Bicep CLI 0.48. Section 17 lists what you should verify first on a real subscription.

1. The idea in plain words (for a 10th-class student)

Imagine a very careful school librarian.

  1. A student asks a question.
  2. The librarian first checks the school's own books.
  3. She asks herself: "Do these pages really answer the question?" (this is the judge).
  4. If yes, she answers and shows which book she used.
  5. If no, she checks a trusted newspaper (the web), and asks herself the same question again.
  6. If she is still not sure, she rewrites the question and tries again (at most twice).
  7. If she still can't find a good answer, she says "I'm not sure" and asks a teacher (a human) to help. She never guesses.

When new books arrive, she does not rebuild the whole library. She gives every page a fingerprint, compares it with her logbook, replaces only the pages that changed, and puts an "Old" sticker on pages that were removed (they are shredded 30 days later).

4. How a question is answered

  1. guard_input: Prompt Shields checks the question for attacks. If the safety service is unreachable the request is blocked (SAFETY_FAIL_CLOSED=true).
  2. route (small model, structured output): rewrites the message as a standalone question using chat history, classifies it (it_support, greeting, out_of_scope), and flags time_sensitive ("latest outage").
  3. retrieve: hybrid search (BM25 + vector) + semantic reranker, filtered to chunks that are status = active, not expired, and visible to the caller's Entra groups. Identical chunks are removed and at most 3 chunks per document are kept (final top 5). Retrieved text is also screened by Prompt Shields for hidden instructions.
  4. grade_private (the judge): see below.
  5. generate (large model): answers only from numbered sources, cites [1], [2], and labels web answers "from the public web, not NovaRetail policy".
  6. check_answer (optional): Content Safety groundedness detection; one regeneration, then escalation.
  7. escalate: creates a ticket through a webhook and tells the employee honestly.

The LLM judge

The judge scores six factors and returns JSON (Structured Outputs guarantee the format; reason is written before verdict so the model thinks first):

Factor Meaning
relevance (1-5) Is it about the topic?
sufficiency (1-5) Together, do chunks contain everything needed?
specificity (1-5) Right product / OS / version?
freshness_ok Recent enough (matters for "latest ..." questions)?
authority_ok Official source, not a draft or forum?
conflict_detected Do chunks contradict each other?

missing_info becomes the seed for the query rewrite. A deterministic backstop downgrades GOOD to WEAK if the model's own scores disagree (needs relevance >= 4, sufficiency >= 4, specificity >= 3, no conflict, authority ok, and freshness ok when time-sensitive). If the judge call fails, the verdict is WEAK, never "answer anyway".

Combining the judge with the search score:

Reranker score Judge Decision
high GOOD answer from the private KB
high WEAK trust the judge: web or rewrite
low (< RERANK_MIN) GOOD answer with a low-confidence caution
low WEAK web or rewrite

Web evidence is judged the same way, plus a rule that at least one citation must come from TRUSTED_WEB_DOMAINS. Privacy rule: only a scrubbed, generic query leaves the company boundary (names, emails, IPs, ticket numbers, internal hosts are removed), never raw company text.

The offline judge (evals/run_evals.py) uses the larger model to score groundedness, relevance and completeness on a golden set, and fails CI when thresholds are missed.

5. Chunking strategy

Implemented in ingestion/chunking.py.

  • Layout first. Document Intelligence prebuilt-layout returns Markdown with headings, lists and tables. Page headers/footers/numbers (HTML comments in that output) are stripped.
  • Heading-based sections with a breadcrumb path (VPN Guide > Remote Access > Windows).
  • Size: target 550 tokens, hard maximum 900, tiny trailing chunks (< 80 tokens) merged into the previous one.
  • Overlap (about 12%) only when a long paragraph must be split, never across heading boundaries.
  • Special rules: numbered/bullet procedures are never split (a procedure keeps its intro sentence); tables stay whole, or split by rows with the header row repeated; code blocks are never cut; each FAQ question + answer is its own chunk.
  • Breadcrumb in the embedding text (Document: ... | Section: ...) so "Click Connect" is not ambiguous.
  • Tunables: CHUNK_TARGET_TOKENS, CHUNK_MAX_TOKENS, CHUNK_OVERLAP_RATIO. Choose final numbers by testing 300/500/800 against your golden set (hit rate, groundedness, cost).

6. Duplicates, obsolete chunks and incremental ingestion

Three building blocks: fingerprints (hashes), a ledger (Cosmos DB, one record per document listing its live chunk IDs), and a status on every chunk (active, superseded, expired, deleted). Every search filters status eq 'active'.

Chunk ID = hash(doc_id + section_path + cleaned text). It is content-based, not positional, so inserting a paragraph at the top does not make every later chunk look new.

Incremental flow (ingestion/pipeline.py) 

file hash same as ledger?  -> stop (metadata-only refresh if tags changed)
same content, other doc_id? -> reject, notify uploader
parse -> clean -> chunk -> chunk IDs
diff against ledger:
   in both   -> unchanged   (no re-embedding; metadata refreshed)
   only new  -> add         (embed with cache, upload FIRST)
   only old  -> retire      (soft delete, AFTER the add succeeded)
update ledger

Example: a 40-chunk VPN guide where 3 paragraphs changed and 1 was removed costs 3 embeddings, not 40. The order is make-before-break, so a question asked mid-update never finds the guide missing. Uploads use mergeOrUpload with content-based IDs, so processing the same event twice is harmless (idempotent).

Duplicate types

Type Handling
Same file uploaded twice file hash match: stop, no cost
Same content, different file name rejected, logged to review_queue
Repeated headers/footers stripped before chunking
Overlap duplicates intentional; one kept at query time (identical-hash and per-document cap)
Repeated chunk inside one document dropped at ingestion
Near-duplicates (>= 0.95 cosine, other documents) flagged for human review, never auto-deleted ("30 days" vs "90 days" can be 96% similar)

Obsolete content

  • New version: old chunks become superseded (soft delete) and vanish from answers immediately.
  • Blob deleted: Event Grid BlobDeleted triggers soft delete of the whole document.
  • valid_until passed: nightly job marks it expired; searches also filter on valid_until, as a second safety net.
  • review_by approaching: nightly job logs REVIEW DUE warnings (alert on them or wire a Logic App).
  • Hard delete after RETENTION_DAYS (30). Until then a wrong upload is undone by re-uploading the old file; Blob versioning keeps previous files.
  • Weekly/nightly orphan check removes active chunks the ledger does not know about (with a 60-minute grace period so in-flight ingests are safe).

When a full rebuild is needed (blue-green)

Changing the embedding model or chunking rules changes every vector or ID. Build a second index beside the live one, evaluate, then switch the alias (kb-live), with zero downtime. See runbook 13.1.

Embedding cache

hash(embedding model + breadcrumb + text) -> vector in Cosmos. Re-uploads, rollbacks and reverted edits reuse vectors instead of paying again. Different models never share cache entries.

Model names and capacities are parameters (smallModel, largeModel, embeddingModel). Replace the defaults with models available in your region. The ingestion and API apps read deployment names from settings, so keep names and settings in sync.

9.2 Entra ID app registration

  1. Register an API app. Expose a scope such as access_as_user; its Application ID URI is your entraApiAudience (v2 tokens carry the client ID GUID as aud; set accessTokenAcceptedVersion to 2 in the manifest).
  2. Register a SPA app for the UI (redirect URI = your UI origin) and grant it the API scope.
  3. In the API app manifest set groupMembershipClaims to SecurityGroup so tokens include group IDs. Prefer assigning only relevant groups to the app (users in >200 groups hit the "groups overage" limit, see section 17).
  4. Create the KB Editors group; put its object ID in kbEditorGroupId.

9.3 Web fallback (Foundry + Grounding with Bing)

Create these in the Azure AI Foundry portal (not in the Bicep, because the resource model is still evolving):

  1. A Foundry resource + project, with a model deployment available to the Agent Service.
  2. A Grounding with Bing Search resource, connected to the project (this gives a connection ID).
  3. Grant the API's managed identity the Azure AI User role on the project.
  4. Set FOUNDRY_PROJECT_ENDPOINT and BING_CONNECTION_ID on the Container App:
az containerapp update -g rg-novacopilot -n <api-app> \
  --set-env-vars FOUNDRY_PROJECT_ENDPOINT=<endpoint> BING_CONNECTION_ID=<connection-resource-id>

Review Microsoft's terms for Bing grounding with your compliance team: web queries leave your tenant boundary. To switch the fallback off, set WEB_SEARCH_ENABLED=false (the copilot then rewrites and escalates).

9.7 Production hardening (not in the Bicep)

Put Front Door + WAF and API Management in front of the Container App (JWT validation, per-user rate limits), host the UI on Static Web Apps, move services behind private endpoints with public network access disabled, enable zone redundancy, and add a secondary region if IT support is business-critical. 10. Adding knowledge

Through the API (KB Editors only):

curl -X POST https://<api>/api/admin/documents \
  -H "Authorization: Bearer $TOKEN" \
  -F file=@VPN_Guide.pdf -F version=3.3 -F owner_team=NetworkOps \
  -F allowed_groups=all-employees -F valid_until=2027-06-30 -F review_by=2027-03-31

Or directly to Blob Storage with metadata keys version, owner_team, allowed_groups (comma separated Entra group IDs, or all-employees), valid_until, review_by, title.

  • The document ID is the file name (VPN_Guide.pdf becomes vpn-guide). To publish a new version, upload a file with the same name; Blob versioning keeps the old one.
  • Supported: PDF, DOCX, TXT, Markdown.
  • Restricted content: set allowed_groups to the group object IDs that may see it. The answer cache is keyed by group so restricted answers never leak.

13. Operations runbooks

13.1 Change the embedding model or chunking rules (blue-green) 

# set the NEW embedding deployment / CHUNKER_VERSION in the environment of this job first
python -m ingestion.reindex --new-index kb-index-v2           # builds beside the live index
SEARCH_INDEX_ALIAS=kb-index-v2 python -m evals.run_evals       # compare with v1
python -m ingestion.reindex --new-index kb-index-v2 --swap     # switches alias and updates ledger
# then set SEARCH_INDEX_NAME=kb-index-v2 on the Function App; delete kb-index-v1 after a few days

Pause uploads while the rebuild runs, or re-run it afterwards to pick up changes.

13.2 A wrong file was uploaded

Soft delete makes this reversible: re-upload the correct file (same name). The previous chunks are re-added from the embedding cache, and the bad ones are retired. After 30 days retired chunks are physically deleted.

13.3 Failed ingestion

Messages that fail 5 times go to the Service Bus dead-letter queue (kb-ingest/$deadletterqueue). Fix the cause (corrupt file, quota), then resubmit from the portal or by re-uploading the file.

13.4 Near-duplicate and duplicate-file review

Items are in the Cosmos container review_queue with status = needs_review. A human decides which chunk is canonical and sets the other document's content to superseded (re-upload or delete the blob).

13.5 Useful queries

Cosmos DB (Data Explorer, container traces):

-- escalation rate by day
SELECT SUBSTRING(c.ts, 0, 10) AS day, COUNT(1) AS total, SUM(c.escalated ? 1 : 0) AS escalated
FROM c WHERE c.type = 'trace' GROUP BY SUBSTRING(c.ts, 0, 10)

-- questions that needed the web or a ticket (knowledge gaps to fill)
SELECT c.standalone_question, c.evidence_source, c.escalated FROM c
WHERE c.type = 'trace' AND (c.evidence_source != 'private' OR c.escalated = true)

-- thumbs-down feedback
SELECT * FROM c WHERE c.type = 'feedback' AND c.rating = 'down'

Log Analytics (ingestion): traces | where message has "ingest result" or message has "nightly maintenance". Alert on REVIEW DUE, dead-letter queue depth > 0, p95 /api/chat latency, and 5xx rate.

14. Security model

  • Identity: managed identities everywhere (OpenAI, Search, Cosmos, Storage, Service Bus, Content Safety, Document Intelligence all have disableLocalAuth/key access off). The API and ingestion app have separate identities.
  • Document-level security: every chunk stores allowed_groups; every search adds a filter built from the validated token's groups (group names are sanitised against OData injection).
  • Prompt injection: Prompt Shields on the question and on retrieved text; the judge and generator prompts treat evidence as data; the bot never reveals secrets; retrieved text cannot trigger actions.
  • Privacy: audit traces mask emails and IPs and hash user IDs; traces expire after 90 days; only generic scrubbed queries go to the web.
  • Failure behaviour: judge failure means WEAK; safety outage means blocked (configurable); web failure means rewrite then ticket.

15. Cost controls

Small model for the many cheap judgments, large model only to write the final answer; answer cache for repeated questions; embedding cache and incremental ingestion; rate limits at API Management; Cosmos serverless; Container Apps scale rules. Track cost per question in Application Insights by logging token usage (extend llm.py).

16. Testing, evaluation, CI/CD

  • pytest -q: chunking rules, hashing, incremental diff, and the whole agent graph (private answer, web fallback, retries then ticket, rubric downgrade, untrusted web domain, low-confidence caution, greetings, prompt attacks, judge failure).
  • python -m evals.run_evals: golden-set routing accuracy plus LLM-as-judge scores; exits non-zero below thresholds (routing 0.85, groundedness 0.90, relevance 0.85). Replace evals/golden_set.jsonl with 100-200 real questions, including ones that should end in "I don't know". Calibrate the judge against ~100 answers labelled by two IT staff (aim for about 85% agreement).
  • GitHub Actions: tests and Bicep validation on every PR; build in ACR and roll out a new Container Apps revision on main (OIDC login, no stored secrets). Use revisions and traffic splitting for canary releases and fast rollback.

17. Known limitations and what to verify first

  1. Not yet run on live Azure. Start in a dev subscription. SDKs move quickly: validated here against openai 3.24, azure-search-documents 12.0, azure-ai-projects 2.8, azure-ai-agents 1.1, langgraph 1.2, but requirements.txt uses minimum versions. After your first green run, pin exact versions (pip freeze).
  2. Web agent code (app/retrieval/web.py) follows the Foundry Agent Service pattern for Grounding with Bing. Verify method names against the SDK version you pin. No domain restriction is available through this tool, so the code enforces TRUSTED_WEB_DOMAINS on citations after the fact.
  3. Durable Functions were not used. The same safety is achieved with Service Bus sessions (ordering), 5 delivery attempts with a dead-letter queue, and an idempotent pipeline. If you later need long multi-step orchestration, wrap the ingest_document steps in activities.
  4. Groundedness detection is a preview API with regional limits; it is off by default and fails soft (marks the check unavailable).
  5. Document Intelligence Markdown: the code assumes page headers/footers/numbers are emitted as HTML comments and tables as HTML <table>. Run a few real PDFs and inspect the chunks.
  6. Reranker thresholds (RERANK_MIN, RERANK_STRONG) are starting points; tune against the golden set.
  7. Groups overage: users in more than 200 groups get no groups claim; they only see all-employees content until you use group filtering or app roles (a Graph lookup would be the alternative).
  8. Service Bus lock: the maximum lock duration is 5 minutes. Very large PDFs that take longer need lock renewal tuning or a Durable/async design.
  9. tiktoken downloads its vocabulary on first use. In a network-restricted Function App, pre-bundle it (TIKTOKEN_CACHE_DIR); otherwise token counts fall back to an approximation (chunk sizes still work).
  10. Redis uses an access key held in Key Vault. Move to Entra authentication (Azure Managed Redis) to remove it.
  11. Cached answers can be up to CACHE_TTL_SECONDS stale after a document update.
  12. Search paging: maintenance jobs read through all chunks; beyond about 100,000 chunks, page by doc_id filter.
  13. Not in the Bicep: Front Door/WAF, API Management, Static Web Apps, private endpoints, Foundry project and Bing resource, Event Grid subscription, alerts. Role assignments are resource-group scoped for brevity.
  14. Model names and regional availability change. Verify before deploying.

19. Roadmap

Pilot with ~100 IT staff for 4 weeks, then one or two departments with feedback buttons and cost dashboards, then all 3,000 employees. Success measures: fewer repeat tickets, share of answers with sources, a healthy non-zero "I don't know" rate, p95 latency, and cost per question. Review unanswered questions monthly and give every document an owner and a review date.
