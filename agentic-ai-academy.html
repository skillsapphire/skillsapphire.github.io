📚
Level 1

RAG — Retrieval-Augmented Generation

An AI model only knows what it learned during training — like a kid who read a lot of books but hasn't seen today's newspaper. RAG hands the model the newspaper right before it answers.

🧸 Explain it like I'm 8

Imagine asking a super-smart friend a question. Instead of guessing from memory, they run to the library, pull the exact right book off the shelf, read the right page, and then answer you — pointing to the page as proof.

That's RAG: fetch the facts first, then write the answer.

🌍 Real world example

A washing machine company builds a chatbot. Instead of the AI guessing your model's manual from memory (and getting it wrong), it searches the actual PDF manual for your exact model, then answers using that page.

How a RAG pipeline flows
A tiny retrieval step, in plain code
# The core idea of RAG in ~10 lines
def answer_question(question):
    # 1. Turn the question into a list of numbers ("embedding")
    question_vector = embed(question)

    # 2. Find the most similar chunks in the vector database
    top_chunks = vector_db.search(question_vector, top_k=3)

    # 3. Hand those exact chunks to the model as context
    context = "\n".join(chunk.text for chunk in top_chunks)
    prompt = f"Answer using only this context:\n{context}\n\nQuestion: {question}"

    # 4. The model writes an answer grounded in real facts
    return llm.generate(prompt)

🎓 Architect-level version (what to say in the interview)

In production this becomes: chunking strategy matched to document structure, hybrid search (dense embeddings + BM25 keyword search) for recall, a reranker (cross-encoder) to sort the top candidates by true relevance, semantic caching for repeated queries, and a confidence threshold that triggers "I don't know" instead of a hallucinated guess.

🧩 Try it yourself

Pick a real product (a phone, a car, a video game). What "documents" would you feed a RAG system so it could answer customer questions about it perfectly? Sketch the 4 boxes above with your own example.

✅ Suggested answer

Start with a chunking strategy tied to document structure (headers, sections) rather than fixed character counts. Use hybrid retrieval — dense embeddings plus BM25 keyword search — to catch both semantic and exact-term matches. Add a reranking stage (cross-encoder) so the top candidates are sorted by true relevance, not just raw similarity. For sub-second latency, use approximate nearest-neighbor indexing (HNSW), shard the index, and add a semantic cache for repeated queries. Finally, include a fallback: if retrieval confidence is low, return "insufficient information" instead of letting the model guess.

Why this answer works: it shows you think about the full pipeline (ingestion → retrieval → generation) and about failure modes, not just the happy path — which is exactly what a Staff/Principal interviewer is listening for.

Level 2

Vector Databases — The Magic Bookshelf

A vector database doesn't store words — it stores meaning, as points in space. Similar meanings end up sitting close together, like a librarian who shelves books by topic instead of alphabetically.

🧸 Explain it like I'm 8

Think of Spotify. You like a song, and it recommends ten more that "sound similar" — even if the titles are totally different words. It's not matching letters, it's matching vibe. A vector database is a giant map of "vibes," and it finds the closest ones to your question.

🌍 Real world example

A hospital stores thousands of doctors' notes. A vector DB lets a nurse type "patient with chest pain and shortness of breath" and instantly find similar past cases — even if those notes used completely different wording.

Similarity search — nearest neighbors in "meaning space"

🎓 Architect-level version

Milvus is a dedicated vector engine — great when you need raw ANN performance at huge scale (HNSW / IVF_PQ indexing, sharding). Amazon Aurora PostgreSQL + pgvector is great when your vectors live alongside relational business data and you want transactional consistency and simpler ops. Many enterprise designs use both: metadata and access control in Postgres, high-volume embeddings in Milvus.

🧩 Try it yourself

If Netflix used a vector database for movies, what "closeness" would matter most — genre, mood, actors, or pacing? There's no wrong answer — that's literally the design decision an architect makes.

✅ Suggested answer

Choose Milvus when you need raw ANN performance and scale — billions of vectors, advanced indexing like IVF_PQ or HNSW, and dedicated infrastructure tuned purely for similarity search. Choose Aurora + pgvector when your vectors need to live alongside relational business data — you want transactional consistency, SQL joins between vectors and structured records, and simpler operations (one system instead of two). Many real architectures use both: business metadata and access control in Postgres, high-volume embeddings in Milvus.

Why this answer works: it avoids a "one is better" trap and instead frames the decision around scale, ops overhead, and data-locality trade-offs — the language an architect actually uses.

Level 3

Multi-Agent Systems — A Team of Little Robots

One AI trying to do everything is like one kid trying to cook, serve, and wash dishes alone. A multi-agent system is a kitchen crew — each robot has one job, and someone coordinates them.

🧸 Explain it like I'm 8

Think of a class group project: one kid researches, one kid writes, one kid checks for mistakes, and the team leader decides what happens next. Each "agent" is like one of those kids — good at one thing, working together toward a shared goal.

🌍 Real world example

An insurance company automating claims: one agent reads the claim form, one agent checks the policy rules, one agent looks for signs of fraud, and a "supervisor" agent combines their findings into a final decision.

Supervisor–worker pattern (the most common enterprise pattern)
A minimal agent graph (LangGraph-style pseudocode)
# A supervisor routes work to the right specialist, step by step
graph = StateGraph(ClaimState)

graph.add_node("policy_lookup", policy_lookup_agent)
graph.add_node("fraud_check", fraud_check_agent)
graph.add_node("decision", decision_agent)

graph.add_edge("policy_lookup", "fraud_check")
graph.add_edge("fraud_check", "decision")

# conditional routing = the "thinking" part
graph.add_conditional_edges(
    "decision",
    lambda state: "human_review" if state.risk_score > 0.7 else "auto_approve"
)

app = graph.compile(checkpointer=redis_checkpointer)  # state survives restarts

🎓 Architect-level version

Supervisor-worker is easier to debug, trace, and audit — important when regulators ask "why was this claim approved?" Decentralized/blackboard collaboration is more flexible for open-ended research tasks, but harder to guarantee termination and harder to govern. Always pair autonomy with a max-step budget and a token/cost ceiling so agents can't loop forever.

🧩 Try it yourself

Design a 3-agent team for planning a birthday party. Who's the supervisor? What do the workers each own? Where would a human need to approve something (like the budget)?

✅ Suggested answer

Supervisor-worker fits well-defined task decomposition — it's easier to debug, trace, and audit, which matters most in regulated enterprise workflows like claims or finance where you must explain "why did the system do that." Decentralized/blackboard collaboration fits open-ended, exploratory tasks where the right path isn't known upfront, but it's harder to guarantee termination and harder to govern. Most enterprise deployments default to supervisor-worker for auditability, and reserve decentralized patterns for research or creative tasks.

Why this answer works: it ties the technical choice back to a business consequence (auditability vs. flexibility) instead of just describing the mechanics.

Level 4

MCP & A2A — Teaching Robots a Common Language

If every tool speaks its own secret language, every agent needs a custom translator for every tool. Protocols fix that by giving everyone one shared plug.

🧸 Explain it like I'm 8

MCP (Model Context Protocol) is like USB-C. Before USB-C, every gadget had its own weird cable. Now one plug works everywhere. MCP is a USB-C port for AI agents to plug into tools, files, and data — no custom wiring per tool.

A2A (Agent-to-Agent) is like agents learning a shared language — like two kids from different countries agreeing to speak English so they can play together, even though they go to different schools (built by different companies).

🌍 Real world example

Your claims-triage agent needs to check a policy database, send an email, and look up a customer's history in a CRM — three completely different systems. With MCP, it connects to all three through the same standard interface instead of three custom integrations.

MCP: one plug, many tools

🎓 Architect-level version

MCP standardizes agent-to-tool access (context, resources, function calls). A2A standardizes agent-to-agent discovery and task delegation across vendors and frameworks — so a LangGraph agent could hand off a task to a Bedrock agent built by another team, without custom glue code. Both are still maturing standards, so when proposing them, pair adoption with a fallback plan and a way to evaluate vendor support.

🧩 Try it yourself

List 3 tools a school-scheduling assistant agent would need to plug into (e.g., calendar, room booking, attendance system). Notice how each one used to need its own "cable" — that's the N×M problem MCP solves.

✅ Suggested answer

Without a standard, every agent needs custom integration code for every tool — the N×M problem. MCP defines one common interface for tools, resources, and context, so any MCP-compliant agent can plug into any MCP-compliant tool without bespoke glue code. That gives portability across agent frameworks and lower integration maintenance cost. It's worth being honest that the standard is still maturing, so I'd pair adoption with an evaluation of vendor support and a fallback integration plan for critical tools.

Why this answer works: it explains the "why" (N×M problem), not just the "what," and shows calibrated judgment by flagging the maturity risk instead of overselling it.

Level 5

Guardrails & Governance — Safety Rules for Smart Robots

The more autonomous a system gets, the more it needs rules, checkpoints, and a way to explain itself — just like a kid gets more freedom as they earn trust, but always within house rules.

🧸 Explain it like I'm 8

Bowling with bumpers! The ball can move freely, but the bumpers stop it from going in the gutter. Guardrails do the same for AI: the model can think freely, but can't say harmful things, leak private info, or take a risky action without a check.

🌍 Real world example

A bank's AI can freely answer "what's my balance," but before it moves money out of your account, it must pause and ask a human to confirm — that pause is a human-in-the-loop guardrail.

Where guardrails sit in the flow
A simple guardrail check
def check_before_acting(action, risk_score):
    # Irreversible or high-risk actions always pause for a human
    if action.type in ["send_payment", "delete_record", "deny_claim"]:
        return "needs_human_approval"

    if risk_score > 0.7:
        return "needs_human_approval"

    # Low-risk, reversible actions can proceed autonomously
    return "auto_approved"

🎓 Architect-level version

Production guardrails span input filtering (PII/toxicity/jailbreak detection, e.g. Bedrock Guardrails), output grounding checks against retrieved context, an eval harness with golden datasets and LLM-as-judge scoring, and a full audit trail for compliance (SOC2, GDPR, HIPAA depending on industry). Not every step needs a human — place approval gates where the cost of being wrong is high or irreversible.

🧩 Try it yourself

For a homework-helper AI used by kids, list 3 things it should never do without a teacher checking first.

✅ Suggested answer

Placement is risk-based, not blanket. I'd add a checkpoint before irreversible actions (payments, deletions, external communications), high-ambiguity decisions, or whenever the model's confidence is low. In a claims-triage example, that means only claims above a dollar-amount or risk-score threshold route to a human adjuster — low-risk, clearly-covered claims auto-approve. Adding a human to every step doesn't scale and defeats the purpose of automation; the goal is friction exactly where the cost of being wrong is highest.

Why this answer works: it shows you can balance autonomy against risk instead of defaulting to "always ask a human," which interviewers often probe for.

Level 6

Cloud Infrastructure — The Robot Factory

You could build your own kitchen, own power plant, and own delivery trucks — or you could rent a fully-equipped commercial kitchen and just cook. Cloud infrastructure is the rented kitchen.

🧸 Explain it like I'm 8

Instead of building a robot factory from scratch, AWS rents you all the machines: a pantry to store ingredients (S3), a recipe binder that's always organized (Aurora/RDS), on-demand short-order cooks that appear only when needed (Lambda), and a whole kitchen crew working together (EKS/Kubernetes).

🌍 Real world example

An insurance company's claims agents run as containers on EKS, use Lambda to fire off quick actions (like sending a notification email), store documents in S3, and keep session state in DocumentDB so a conversation can pause and resume later.

AWS building blocks, mapped to their job

🎓 Architect-level version

Split stateless compute (agent reasoning workers on EKS, autoscaled by queue depth) from stateful storage (DocumentDB/Aurora for session state). Use Lambda for short, event-driven tool actions. CI/CD for non-deterministic AI outputs means eval-gated deployments, shadow traffic canaries, and statistical pass/fail thresholds instead of exact-match tests.

🧩 Try it yourself

Which AWS piece above would you use to store a photo a customer uploads with their claim? Which one remembers that the customer already answered "yes" to a question 5 minutes ago?

✅ Suggested answer

The key is separating stateless compute from stateful storage. Agent reasoning workers run as stateless pods, horizontally autoscaled (HPA) based on queue depth or concurrent session count. Session and conversation state lives outside the pod — in DocumentDB, Redis, or Aurora — so any pod can pick up any session, and restarts or scale-downs don't lose state. Session affinity is only used where it genuinely helps latency, not as a substitute for externalized state.

Why this answer works: "don't put state in the pod" is the single sentence that signals real production experience with stateful workloads on Kubernetes.

Level 7

Observability — The Mission Control Room

If an autonomous agent takes an action, you'd better be able to answer "why did it do that?" afterward. Observability is the flight recorder that makes that possible.

🧸 Explain it like I'm 8

Airplanes have a black box that records everything, so if something goes wrong, engineers can replay exactly what happened. Observability gives every AI agent a black box: what it thought, what tool it called, how long it took, and how much it cost.

🌍 Real world example

A claim gets denied and the customer complains. With good observability, an engineer can replay the exact reasoning trace — which documents were retrieved, which agent made the call, and why — in minutes instead of days.

Logging a trace for one agent step
trace.log(
    agent="fraud_check",
    tool_calls=["lookup_claim_history"],
    tokens_used=842,
    latency_ms=310,
    outcome="no fraud signals found",
    confidence=0.91,
)
# Every hop gets logged, so any decision can be replayed and explained

🎓 Architect-level version

Distributed tracing across every agent hop (OpenTelemetry-style spans), token usage and cost attribution per agent/session, latency breakdowns per tool call, and failure-state classification (tool error vs. model error vs. timeout) — all feeding alerts tied to real SLAs.

🧩 Try it yourself

If your homework got graded wrong by an AI teacher's assistant, what 3 pieces of information would you want logged so someone could figure out what went wrong?

✅ Suggested answer

Distributed tracing across every agent hop, using OpenTelemetry-style spans so a full session can be replayed step by step. Token usage and cost attribution per agent and per session, latency broken down per tool call, and failure-state classification — tool error vs. model error vs. timeout — so incidents can be triaged fast. All of it feeds alerts tied to real SLAs, not just raw logs nobody looks at.

Why this answer works: naming the specific dimensions (cost, latency, failure type) rather than just saying "we'd add logging" shows you've actually run one of these systems in production.

Level 8

Evaluation & CI/CD — The Report Card

You can't test an AI system the way you test a calculator — the same question can get two different, equally correct answers. So how do you know a change made things better or worse?

🧸 Explain it like I'm 8

Grading a math test is easy — there's one right answer. Grading an essay is harder — a teacher reads it and judges quality against a rubric. Testing AI outputs is like grading essays: you need a rubric (eval criteria) and a grader (a human, or another AI acting as judge) instead of a simple right/wrong checker.

🌍 Real world example

Before shipping a new version of the claims-triage agent, the team runs it against 200 real past claims with known correct outcomes ("golden dataset"). If the new version's accuracy drops, or it starts approving claims it shouldn't, the deployment is blocked automatically — just like a report card catching a slipping grade before report-card day.

Eval-gated deployment pipeline
A simple eval gate
# Runs automatically in CI before any deploy
def run_eval_gate(new_model, golden_dataset, threshold=0.85):
    scores = []
    for case in golden_dataset:
        output = new_model.run(case.input)
        # an LLM "judge" grades faithfulness, correctness, tone
        score = llm_judge.grade(output, case.expected, rubric=case.rubric)
        scores.append(score)

    avg_score = sum(scores) / len(scores)
    if avg_score < threshold:
        raise DeploymentBlocked(f"Eval score {avg_score:.2f} below threshold {threshold}")

    return "safe to deploy ✅"

🎓 Architect-level version

Production eval pipelines combine golden datasets (regression protection), LLM-as-judge scoring for scale with periodic human audits to keep the judge honest, statistical pass/fail thresholds instead of exact-match assertions, and shadow deployments that compare the new version against production traffic before a full rollout. Prompt and model versions are tracked like code, so any regression can be bisected to the exact change that caused it.

🧩 Try it yourself

If you were grading an AI tutor's answers to math word problems, what would your "rubric" check for besides just the final number being right?

✅ Suggested answer

You can't rely on exact-match assertions because outputs vary run to run. Instead, run every change against a golden evaluation dataset, score outputs with an LLM-as-judge (periodically audited by humans to catch judge drift), and gate deployment on a statistical threshold rather than a single pass/fail case. Before full rollout, run a shadow deployment comparing the new version against the current one on live traffic. Track prompt and model versions like code so regressions can be bisected.

Why this answer works: it directly names the core problem (non-determinism breaks exact-match testing) before describing the solution, which shows you understand why the practice exists, not just that it exists.

Level 10 — Bonus Boss Level

Banking: Fast, Cheap RAG Across Messy Data — With Locked Doors

A bank's knowledge isn't one tidy library — it's scanned loan PDFs, Excel risk models, Word policy docs, KYC ID photos, call-center recordings, and rows in Core Banking, CRM, and ERP systems. And not every employee is allowed to see all of it. This level covers the four hardest asks in one system: many formats, speed, cost, and per-employee access control — plus keeping it all fresh without rebuilding everything.

🧸 Explain it like I'm 8

Picture a huge library where books arrive as photocopies, voice recordings, spreadsheets, and even locked filing cabinets. The librarian has to be able to read all of them. But some shelves have a sign: "Managers only," "Compliance officers only," "Ask a supervisor." The librarian never hands a restricted book to the wrong person — even if they ask nicely.

🌍 Real world example

A bank builds one internal AI assistant used by relationship managers, call-center agents, compliance officers, and credit-risk analysts. A relationship manager can ask "what's this customer's mortgage status" and get product and payment info. The same question from a compliance officer can also surface flagged SAR (suspicious activity report) notes. A call-center agent asking the same question sees neither — just enough to answer the customer on the phone.

🗃️ Ask 1: Many formats, one system

PDFs and Word docs (loan agreements, policy manuals) → text + layout extraction. Excel (risk models, transaction exports) → structured tables, not flattened text. Images (scanned KYC IDs, signatures) → OCR + vision. Call recordings → speech-to-text transcription. Core Banking DB, CRM, ERP → change-data-capture (CDC), not one-time dumps.

🔒 Ask 2: Not everyone sees everything

Every chunk is tagged at ingestion with metadata: sensitivity tier, department, product line, customer-consent flag. Retrieval applies these tags as filters before anything reaches the model — permissions are enforced by the retrieval layer, never left to the LLM's judgment.

⚡ Ask 3: Fast and cost-effective

Hot/cold storage tiers (frequently-asked policies stay in fast indexes; rarely-touched archives sit cheaper), a small/cheap model handles simple lookups and only escalates to a larger model for complex reasoning, and semantic caching avoids recomputing answers to common questions.

🔄 Ask 4: Partial, not full, updates

When one loan policy page changes, the system shouldn't re-embed the entire knowledge base. Each chunk is hashed; only chunks whose hash changed get re-embedded and swapped in — a delta update instead of a full rebuild.

Retrieval that respects who's asking
# Access control is enforced at retrieval time, not left to the model
def retrieve_for_user(query, user):
    query_vector = embed(query)

    # Pull the user's permitted tags from IAM/AD, not from the request itself
    allowed_tiers = get_clearance(user)  # e.g. ["public", "product", "compliance"]

    results = vector_db.search(
        query_vector,
        top_k=5,
        filter=f"sensitivity_tier IN {allowed_tiers} AND department IN {user.departments}"
    )
    # The LLM only ever sees chunks that already passed the filter
    return results

🚫 Document-level denial, not just answer-level filtering

Chunk-tag filtering (above) controls which pieces of content can surface. Some documents need a harder rule: certain files should never appear in a certain role's search results at all — not partially, not summarized, not even acknowledged as existing. Board minutes, SAR filings, and executive credit-risk models are typically document-level restricted, not just chunk-filtered. This is enforced by tagging the whole document with an allowed_roles list at ingestion, and rejecting it from the candidate set before vector search even runs — the same mechanism as chunk filtering, applied at the document boundary instead of the passage boundary.

Document-level allowlist, checked before chunk-level retrieval
# Two layers: a document must pass BOTH checks to ever reach the user
def retrieve_for_user(query, user):
    query_vector = embed(query)
    allowed_tiers = get_clearance(user)

    results = vector_db.search(
        query_vector,
        top_k=5,
        filter=f"""
            sensitivity_tier IN {allowed_tiers}          # layer 1: chunk-level tier
            AND document_id NOT IN {get_denied_documents(user)}  # layer 2: doc-level deny
        """
    )
    # A restricted document was never a candidate — nothing to filter after the fact
    return results
Delta reindexing — cheap, incremental knowledge base updates
# Runs on every CDC event from Core Banking / CRM / ERP, or on document re-upload
def sync_chunk(chunk, chunk_store):
    new_hash = sha256(chunk.text)
    old_hash = chunk_store.get_hash(chunk.id)

    if new_hash == old_hash:
        return "unchanged — skip embedding, save cost"

    # Only the changed chunk gets a fresh, costly embedding call
    new_vector = embed(chunk.text)
    vector_db.upsert(chunk.id, new_vector, metadata=chunk.metadata)
    chunk_store.set_hash(chunk.id, new_hash)
    return "updated ✅"

🎓 Architect-level version (how to say all of this in one breath)

Format diversity is solved at ingestion: format-specific extractors (document parsers, OCR/vision for scans, speech-to-text for calls, CDC connectors for DB/CRM/ERP) normalize everything into one chunk schema. Access control works at two layers: chunk-level sensitivity tags filter individual passages, while a document-level allowlist keeps certain files (SAR filings, board reports) out of a role's candidate set entirely — both enforced as pre-filters at retrieval, mirrored from IAM/Active Directory, never as a prompt instruction to the model. Cost and speed come from hot/cold storage tiers, a small-model-first routing strategy that escalates to a larger model only for complex reasoning, and semantic caching for repeat queries. Partial updates come from chunk-level hashing plus event-driven CDC pipelines, so a single changed policy page triggers one cheap re-embed instead of a full, expensive reindex.

🧩 Try it yourself

Design the sensitivity tiers and a document-level deny list for a bank's internal assistant: what would "public," "product," "compliance," and "executive" tiers each contain, and which specific document types should be completely invisible to a call-center agent?

✅ Suggested answer

I'd split this into four concerns. First, ingestion: route each format to the right extractor — document parsers for PDF/Word, structured table extraction for Excel (not flattened text), OCR/vision for scanned KYC images, speech-to-text for call recordings, and CDC connectors for Core Banking, CRM, and ERP so structured data stays fresh without full re-pulls. Everything lands in one normalized chunk schema with metadata. Second, access control: tag every chunk with a sensitivity tier and department at ingestion, mirrored from the source system's own IAM/AD permissions, and enforce that as a metadata filter at retrieval time — before the LLM ever sees the content, not as a prompt instruction. Third, cost and speed: hot/cold storage tiers so frequently-asked content stays in fast indexes while archives sit cheaper, a small-model-first routing strategy that only escalates to a larger model for complex reasoning, and semantic caching for repeated questions. Fourth, partial updates: hash each chunk and only re-embed chunks whose hash changed, triggered by CDC events or document re-uploads, so a single policy change doesn't require rebuilding the whole index.

Why this answer works: it addresses all four constraints explicitly instead of just describing a generic RAG pipeline, and it repeatedly makes the point that access control is enforced structurally (metadata filters, mirrored permissions) rather than trusted to the model — which is exactly the distinction a banking security reviewer would probe for.

Level 11 — Deep Dive

V3: Turning the Banking RAG Sketch Into a Production Engine

Level 10 was the architecture sketch. V3 is what happens when that sketch has to survive real production traffic: two search methods blended with a real formula instead of guesswork, questions split into sub-questions, policy versions that change over time, numbers that must never be hallucinated, and every claim checked against its source before it reaches the user.

🧸 Explain it like I'm 8

Imagine two search parties looking for the same missing treasure: one that recognizes the treasure by shape (meaning) and one that recognizes it by its exact label (keywords). Instead of you comparing their two lists by hand, you give both lists to a referee with a fair scoring rule — that's what a database like Qdrant does natively now, so nobody has to referee the lists in application code.

🌍 Real world example

A credit officer asks two very different questions: "How can a loan be restructured for a borrower facing financial hardship?" (a natural-language, meaning-heavy question) and "RBI/2026-27/45 DOR.CRE.REC.123" (an exact regulatory identifier). The first should lean on meaning-based search; the second should lean almost entirely on exact keyword matching. A production system detects the difference and reweights search accordingly, instead of treating every question the same way.

V3 target architecture — the whole request, end to end

🔀 V3.1 — Fusion moves out of Python, into the database

Earlier versions ran dense search and sparse search separately, then merged the two ranked lists (Reciprocal Rank Fusion, or RRF) in application code. Modern vector databases like Qdrant now support this natively: send both searches as a single request with a fusion instruction, and let the database return one merged, ranked list — fewer network round-trips, less code to maintain, and a consistent scoring rule.

Native hybrid retrieval — one request, database does the fusion
# Dense (meaning) + sparse (keyword) search, fused inside the vector DB itself
prefetch = [
    Prefetch(query=dense_vector, using="dense", limit=50),
    Prefetch(query=SparseVector(indices=sparse_idx, values=sparse_vals),
             using="sparse", limit=50),
]

results = vector_db.query_points(
    collection_name="bank_chunks",
    prefetch=prefetch,
    query=RrfQuery(rrf=Rrf(k=60)),   # reciprocal rank fusion, tunable k
    limit=30,
    query_filter=security_filter,          # access control applied here too — see V3.7
    with_payload=True,
)
V3.2 — Query-dependent weighting: not every question trusts meaning and keywords equally

🥈 V3.3 — Two-stage reranking

After hybrid retrieval returns the top 30, a dedicated reranker (a cross-encoder, e.g. a BGE reranker) re-scores those 30 by reading the question and each candidate together, cutting to the true top 10. This second pass catches relevance nuances that similarity scores alone miss.

🧪 Experimental third stage

Embedding models like BGE-M3 can also produce ColBERT-style "late interaction" representations — a finer-grained, token-level comparison. It's a promising third stage, but it adds latency, so it should stay experimental until benchmarks prove it lifts recall/nDCG enough to earn its cost — never switch it on globally by default.

🧩 V3.4 — Multi-section retrieval

A question like "what are the eligibility, documentation, and exception requirements for a gold loan?" is really three questions stitched together. The planner splits it into sub-queries, retrieves for each separately, and merges the resulting sections into one evidence set — far more reliable than just cranking up top_k on a single search.

🕸️ V3.5 — Evidence graph

Each retrieved chunk carries relationships to its neighbors: parent section, previous/next chunk, sibling sections, and which document version it supersedes or is superseded by. A retrieval hit on "Income" can pull in the related "Eligibility," "Documentation," and "Exceptions" sections automatically — without every one of them needing to score high on similarity alone.

V3.6 — Version-aware retrieval: which policy was actually in force?
A 2025 policy chunk can be highly similar in wording to a 2026 update — similarity alone would confidently return the wrong, outdated answer.

🔐 V3.7 — Security filtering happens before search, not after

The flow is User → IAM → resolved permissions → ACL filter → vector database — the database is only ever allowed to search points the user is cleared to see. Permissions are resolved server-side from the bank's identity provider; a client is never trusted to simply declare its own role.

📊 V3.8 — Excel gets its own path, not a RAG chunk

A 5-million-row loan portfolio spreadsheet shouldn't be embedded and handed to an LLM to "calculate" from — LLMs are unreliable at arithmetic over huge tables. Instead, Excel is profiled into a governed SQL schema. "Total outstanding in Odisha" becomes an actual SUM() query, with the SQL itself shown as the citation.

V3.9 — Guarding LLM-generated SQL before it ever runs
# Generated SQL must pass every gate below — never execute it directly
def run_safe_sql(generated_sql, connection):
    ast = parse_sql(generated_sql)

    if ast.statement_type not in ["SELECT", "WITH"]:
        raise Rejected("only read queries are allowed")

    if not ast.tables.issubset(ALLOWED_TABLES):
        raise Rejected("table not on the allowlist")

    return connection.execute(
        generated_sql,
        readonly=True,
        row_limit=10_000,
        timeout_seconds=5,
    )

✅ V3.10 — Citation verification

Before an answer ships, every cited claim is traced back to its source chunk and checked: does the evidence actually support what the model said? If not, the answer is rejected or regenerated. This is what separates retrieval quality (did we find the right documents) from generation faithfulness (did the model actually say only what those documents support) — the two most-confused failure modes in RAG systems.

📏 V3.11 — Evaluation, automated

Standard RAG metrics (context precision/recall, faithfulness, answer relevancy — the kind Ragas measures) cover generic quality. A bank needs its own on top: SectionCoverage, CitationCorrectness, VersionCorrectness, ACL-leakage rate, numerical accuracy, and abstention accuracy (did it correctly say "I don't know" when it should have).

🗂️ V3.12 — The golden dataset

Each test case records the question, its category (simple factual, policy, multi-section, version-sensitive, Excel aggregation, unauthorized, conflicting policies, ambiguous, and more — roughly 18 categories), the documents and sections it should retrieve, and the exact citations expected. A production-ready target is on the order of 1,000+ labeled questions, not a handful of spot checks.

V3.13 & V3.14 — Latency and cost: cache carefully, separate CPU from GPU work
Caching without including the user's authorization context in the key is a real risk: it can return an answer generated for someone else's permission level.

🎓 Architect-level version (the whole thing, in one breath)

V3 moves hybrid fusion into the vector database itself (native RRF, tunable and weighted), classifies each query so dense/sparse weighting adapts to whether it's semantic or an exact identifier, adds a reranking stage with an experimental late-interaction option, decomposes multi-part questions into sub-queries merged through an evidence graph, resolves the correct policy version by effective date, enforces access control as a pre-search filter never a post-hoc trust exercise, routes tabular/numeric questions to governed SQL instead of embedding-based guessing, verifies every citation against its source before answering, and evaluates all of it — retrieval, generation, and security — against a large, categorized golden dataset. Deployment separates cheap always-on CPU services from batched GPU workloads, and caching is keyed on the user's authorization context so nobody ever gets an answer meant for someone else.

Level 12

Evaluation & Observability — How Do You Actually Know It Works?

"It seemed to work when I tried it" is not an evaluation strategy. A production RAG system needs layers of measurement — before it ships, while it's live, and after something goes wrong — each answering a different question.

🧸 Explain it like I'm 8

Think about how a school checks a new teaching method actually works: a practice test before rolling it out to everyone (offline eval), watching how the whole class does once it's live (online monitoring), and a teacher spot-checking a few notebooks by hand to catch anything the test missed (human review). You need all three — a practice test alone won't catch a teacher misreading the room.

🌍 Real world example

A bank's RAG assistant passes its offline eval with 92% faithfulness. Two weeks after launch, live monitoring shows answer quality quietly dropping for questions about a newly-updated loan policy — the golden dataset never had questions about it. A human auditor flags the pattern before a customer gets a wrong rate quoted to them. Each layer caught something the others missed.

Three layers of evaluation, each catching different failures

📐 Retrieval-level metrics

Recall@K — did the right chunk appear anywhere in the top K results? Precision@K — how much of the top K was actually relevant? MRR (Mean Reciprocal Rank) — how high up was the first correct result? nDCG — rewards correct results appearing near the top, not just present. These answer: "did we find the right material at all?"

✍️ Generation-level metrics

Faithfulness / groundedness — is every claim in the answer actually supported by the retrieved context? Answer relevancy — does the answer address what was asked? Answer correctness — is it factually right against a known answer? Hallucination rate — how often does the model state something the context doesn't support? These answer: "given good material, did the model use it honestly?"

🧪 Automated eval frameworks

Tools like RAGAS, TruLens, and DeepEval use an LLM as a judge to score faithfulness, relevancy, and context quality at scale — far cheaper than having a human grade every response, but the judge itself should be periodically spot-checked by a human so it doesn't quietly drift.

🙋 Human evaluation

Expert grading against a rubric, pairwise comparison ("which of these two answers is better?" — often more reliable than absolute scoring), and red-teaming (deliberately trying to make the system leak restricted data or produce unsafe output). Human eval is slower and pricier, so it's used to calibrate and audit the automated methods, not replace them.

A minimal retrieval eval loop
# Recall@K — the simplest, most important retrieval metric to start with
def recall_at_k(golden_dataset, retriever, k=5):
    hits = 0
    for case in golden_dataset:
        retrieved_ids = [c.id for c in retriever.search(case.question, top_k=k)]
        if case.expected_chunk_id in retrieved_ids:
            hits += 1
    return hits / len(golden_dataset)

# Faithfulness — did the generated answer stay grounded in retrieved context?
def faithfulness_score(answer, context):
    claims = extract_claims(answer)          # split answer into atomic statements
    supported = [c for c in claims if llm_judge.is_supported(c, context)]
    return len(supported) / len(claims)
Observability: what you watch once the system is live

🎓 Architect-level version

Ship an eval-gated CI/CD pipeline (golden dataset + statistical thresholds, from Level 8) so regressions never reach production. In production, run distributed tracing across every agent/retrieval hop, dashboards for p50/p95 latency, token cost, and error classification, and alerting tied to real SLAs. Feed user feedback (thumbs up/down, explicit corrections) back into the golden dataset so it grows from real failures, not just what the team thought to test upfront. Monitor for drift — embedding distributions and query patterns shift over time as products, policies, and customer language change — and schedule periodic human red-teaming specifically targeting access-control leakage, since that's the failure mode automated metrics are worst at catching.

📋 Banking-specific metrics worth adding

CitationCorrectness (does the cited source actually say that), VersionCorrectness (right policy version for the date asked), ACL-leakage rate (did any restricted content ever surface for an unauthorized role — target: zero, tested adversarially), NumericalAccuracy (for anything routed through SQL), and AbstentionAccuracy (did it correctly say "I don't know" instead of guessing).

Level 13 — Reference

Glossary — Speak Like a Pro

Every term below gets two definitions: the one you'd give an 8-year-old, and the one you'd give a hiring panel. Use the simple version to build intuition, then the technical version to sound like you've shipped this in production — because by now, you basically have.

🧠 GenAI & LLM Foundations

Token
🧸 Simple:a small piece of a word the AI reads one bite at a time.
🎓 Technical:the base unit of text an LLM processes; words often split into multiple subword tokens via byte-pair or similar encoding, and both input and output length are measured in tokens.
Context window
🧸 Simple:how much the AI can "remember" at once during a conversation.
🎓 Technical:the maximum number of tokens (input + output combined) a model can attend to in a single request; exceeding it forces truncation or summarization.
Parameters
🧸 Simple:the tiny knobs inside the AI's brain that got tuned during learning.
🎓 Technical:the learned weights of a neural network; model "size" (7B, 70B, etc.) refers to parameter count, which loosely correlates with capability and cost.
Temperature
🧸 Simple:how playful vs. predictable the AI's answers are.
🎓 Technical:a sampling parameter controlling randomness in next-token selection; near 0 is deterministic/greedy, higher values increase diversity at the cost of consistency.
Hallucination
🧸 Simple:when the AI confidently makes something up.
🎓 Technical:output that is fluent and confident but unsupported by training data or provided context — mitigated by grounding (RAG), faithfulness scoring, and confidence thresholds.
Fine-tuning
🧸 Simple:giving the AI extra practice on your specific kind of questions.
🎓 Technical:further training a pretrained foundation model on a smaller, task-specific dataset to shift its behavior, style, or knowledge without training from scratch.
Prompt engineering
🧸 Simple:asking the question the right way to get a better answer.
🎓 Technical:systematically designing instructions, examples, and structure in a prompt to reliably steer model behavior — includes few-shot examples, role framing, and output-format constraints.

📚 RAG Concepts

Embedding
🧸 Simple:turning words into a list of numbers that captures their meaning.
🎓 Technical:a dense vector representation produced by an encoder model, positioned so semantically similar text lands near other similar text in vector space.
Vector database
🧸 Simple:a library organized by meaning instead of alphabet.
🎓 Technical:a data store optimized for approximate nearest-neighbor search over embeddings (e.g. via HNSW or IVF indexing), often paired with metadata filtering.
Chunking
🧸 Simple:cutting a big document into bite-sized pieces before storing it.
🎓 Technical:splitting documents into retrievable units, ideally aligned to semantic or structural boundaries rather than a fixed character count, to balance retrieval precision and context completeness.
Hybrid search
🧸 Simple:searching by both "sounds similar" and "exact words match."
🎓 Technical:combining dense (embedding) retrieval with sparse (keyword/BM25) retrieval, typically merged via reciprocal rank fusion, to improve recall on both semantic and exact-match queries.
Reranking
🧸 Simple:double-checking the search results and putting the best ones first.
🎓 Technical:a second-pass scoring step, usually a cross-encoder, that jointly evaluates the query and each candidate to reorder results by true relevance.
Grounding
🧸 Simple:making sure the AI's answer is based on real facts it was shown.
🎓 Technical:constraining generation to be verifiably supported by retrieved context, measured via faithfulness/groundedness scoring.
Knowledge base
🧸 Simple:the whole collection of documents the AI is allowed to look things up in.
🎓 Technical:the curated, ingested, and indexed corpus a RAG system retrieves from — typically versioned, access-tagged, and kept fresh via incremental updates.

🤖 Agentic AI Concepts

Agent
🧸 Simple:an AI that can take actions, not just talk.
🎓 Technical:an LLM-driven system that plans, calls tools/functions, observes results, and iterates toward a goal, rather than producing a single one-shot response.
Tool use / function calling
🧸 Simple:the AI reaching for a calculator, a search bar, or a database instead of guessing.
🎓 Technical:a model outputting a structured call to an external function with typed arguments, which the system executes and feeds the result back into context.
Multi-agent orchestration
🧸 Simple:a team of specialist AI helpers working together, with one coordinating.
🎓 Technical:coordination patterns (supervisor-worker, decentralized) for multiple specialized agents sharing state and handing off subtasks toward a common goal.
Memory
🧸 Simple:what the AI remembers — for right now, or for next time.
🎓 Technical:short-term (session-scoped conversation state) vs. long-term (persisted episodic/semantic memory across sessions) storage that agents read from and write to.
Planning loop (ReAct-style)
🧸 Simple:think, try something, look at what happened, think again.
🎓 Technical:an iterative reason-act-observe cycle where the model alternates between reasoning steps and tool calls, bounded by a max-step or token budget to guarantee termination.
Guardrails
🧸 Simple:bumper-lane rules that stop the AI from doing something risky.
🎓 Technical:input/output filters, action-risk classifiers, and policy checks (PII, toxicity, jailbreak detection, irreversible-action gating) enforced around model calls.
Human-in-the-loop
🧸 Simple:a person has to say "yes, go ahead" before something risky happens.
🎓 Technical:a workflow checkpoint that pauses autonomous execution for human approval, placed based on action risk, reversibility, or model confidence.

🧬 Multi-Model & Deployment

Model router / cascade
🧸 Simple:using a small helper for easy questions and a big expert only for hard ones.
🎓 Technical:a dispatch layer that routes requests to different-sized models based on estimated task complexity, trading cost and latency against capability.
Quantization
🧸 Simple:shrinking the AI so it runs faster, with a tiny bit less precision.
🎓 Technical:reducing numerical precision of model weights (e.g. FP16 → INT8/INT4) to cut memory and inference cost, at a small, measurable quality tradeoff.
LoRA / PEFT
🧸 Simple:teaching the AI something new without retraining its whole brain.
🎓 Technical:parameter-efficient fine-tuning methods (e.g. Low-Rank Adaptation) that train small additional weight matrices instead of updating the full model, drastically cutting training cost.
Distillation
🧸 Simple:a smaller AI learning to copy a bigger, smarter AI's answers.
🎓 Technical:training a smaller "student" model to mimic a larger "teacher" model's outputs, aiming to retain much of its quality at a fraction of the inference cost.
A/B testing / canary deploy
🧸 Simple:trying a change on a few people first before rolling it out to everyone.
🎓 Technical:routing a small percentage of live traffic to a new model/prompt version, comparing metrics against the baseline before full rollout.
Observability / tracing
🧸 Simple:a flight recorder that shows exactly what the AI did, step by step.
🎓 Technical:structured, replayable logs of every model/tool call in a request — typically OpenTelemetry-style spans — capturing latency, token cost, and outcome per hop.
Eval harness / golden dataset
🧸 Simple:a practice test with known right answers, used to grade the AI before it goes live.
🎓 Technical:a labeled benchmark dataset plus automated scoring pipeline (metrics + LLM-as-judge) run in CI/CD to gate deployments against regressions.
