PART A — FUNCTIONAL SPECIFICATION

A1. Purpose and Scope

The platform digitises the end-to-end issuance of an insurance policy that is sold and captured by field/branch employees on behalf of a customer (typically a farmer, given the Farmer Card verification requirement).

The system covers:

  1. Role-based login for two personas — Employee (maker) and Supervisor (checker).
  2. Retrieval of eligibility rules from a Drupal Content Management System so that business/underwriting teams can change eligibility wording and criteria without a code release.
  3. Outbound sharing of eligibility terms to the customer over SMS or WhatsApp through Twilio.
  4. Capture of the insurance issuance form and upload of KYC documents to Azure Blob Storage.
  5. Automated identity verification against Protean (Aadhaar, PAN) and a Farmer Card verification service, with an independently persisted status per document type.
  6. A maker–checker review workflow: applications sit in REVIEW until a supervisor either requests more information (with comments) or approves.
  7. On approval, hand-off to the Risk Assessment team with the complete registration payload.
  8. A scheduled poller that follows up with the Risk Assessment service every 24 hours until a policy decision and policy document URL are returned.
  9. Delivery of the issued policy document back to the originating employee for download and onward sharing with the customer.

Out of scope for v1.0: premium computation engine, payment collection/reconciliation, claims, renewals, customer self-service portal, and the internal implementation of the Risk Assessment team's own scoring engine.

A3. End-to-End Business Narrative

Step 1 — Login. The employee authenticates. The platform issues a JWT that carries the employee id, branch code and role. The landing dashboard is driven by role: an employee sees My Applications + Start Registration; a supervisor sees the Review Queue.

Step 2 — Start Registration. The employee clicks Start Registration. A DRAFT application shell is created and an application number is reserved. In the same call the backend fetches the current eligibility rule set from Drupal and returns it with the application.

Step 3 — Eligibility rules. The rules are rendered on screen for the employee to walk the customer through. The rule set carries a version; whichever version was shown is stamped onto the application for audit, so that a dispute two years later can be resolved against the exact wording presented on that day.

Step 4 — Share the rules (optional, repeatable). The employee may push the rules to the customer's mobile number as an SMS or a WhatsApp message. Each attempt is written to a notification log with the Twilio message SID and delivery status, so failures are visible and re-sendable.

Step 5 — Proceed. The customer accepts the terms. The employee clicks Proceed; the application moves to ELIGIBILITY_ACCEPTED and the form unlocks. Until this point the form is not editable — this is deliberate, so that terms are always presented before data capture.

Step 6 — Fill the form. Customer demographics, contact details, address, land/crop details, nominee, sum insured and the requested cover period are captured. The form auto-saves as a draft so a dropped network connection does not lose work.

Step 7 — Upload KYC documents. Aadhaar, PAN and Farmer Card images/PDFs are uploaded. Files are validated (type, size, virus scan hook) and streamed to Azure Blob Storage. Only the container + blob path is persisted in the database; the application never stores a permanently public URL. Read access is granted later through short-lived SAS URLs.

Step 8 — Verification. On submit, the platform calls Protean for Aadhaar, Protean for PAN, and the Farmer Card verification API. Each result is written to its own column on the application (aadhaar_verification_status, pan_verification_status, farmer_card_verification_status) plus a detailed row in verification_result holding the provider reference id, response code and attempt count.

Step 9 — Review. Regardless of individual verification outcomes, the application lands in REVIEW. A failed verification does not auto-reject: a human supervisor decides, because a legitimate mismatch (a name spelling difference, a stale farmer card) is common in the field.

Step 10 — Supervisor decision.

  • Needs more information: the supervisor adds a comment. Status becomes NEEDS_MORE_INFO. The application reappears on the employee's dashboard with the comment thread; the employee edits, re-uploads and re-submits, returning it to REVIEW.
  • Reject: terminal status REJECTED with a mandatory reason.
  • Approve: status becomes APPROVED_SENDFORRISK.

Step 11 — Risk hand-off. On approval an asynchronous job assembles the complete registration payload — form data, verification statuses, document SAS URLs, supervisor decision trail — and posts it to the Risk Assessment service. The returned riskRefId is persisted and the status becomes RISK_IN_PROGRESS. If the hand-off call fails, the application stays at APPROVED_SENDFORRISK and is retried by the submitter job; nothing is lost.

Step 12 — Polling. A scheduler runs daily. For every application in APPROVED_SENDFORRISK (submission still pending) it retries submission; for every application in RISK_IN_PROGRESS whose next_poll_at has elapsed it calls the risk status endpoint. While the answer is IN_PROGRESS, next_poll_at is pushed 24 hours forward.

Step 13 — Policy issued. When risk returns APPROVED, the response carries the policy number and a policy document URL. The platform copies that document into its own Azure container (so the platform is not dependent on the risk team's link lifetime), sets status to POLICY_ISSUED, and raises a dashboard notification for the originating employee. The employee downloads the policy and forwards it to the customer. If risk returns REJECTED, status becomes POLICY_REJECTED with the rejection reason and the employee is notified.

ID Requirement Priority

ID Requirement Priority
FR-R-01 On approval the system shall assemble the complete registration payload and POST it to the Risk Assessment service. Must
FR-R-02 The hand-off shall be asynchronous and retried; a failure shall leave the application in APPROVED_SENDFORRISK for the submitter job to pick up. Must
FR-R-03 The riskRefId returned shall be persisted and the status moved to RISK_IN_PROGRESS. Must

FR-R-08 The scheduler shall be safe to run on multiple instances — only one node may process a given application at a time. Must
FR-R-09 The employee dashboard shall surface a "New policy available" indicator and a download action for POLICY_ISSUED applications. Must

A6. Business Rules

ID Rule
BR-01 An application cannot move from DRAFT directly to REVIEW; eligibility acceptance is mandatory.
BR-02 All three KYC documents must be uploaded before submission, irrespective of verification outcome.
BR-03 A supervisor decision is required even when all three verifications pass — there is no straight-through processing in v1.0.
BR-04 NEEDS_MORE_INFO may recur any number of times; each cycle is retained in history.
BR-05 REJECTED, POLICY_ISSUED and POLICY_REJECTED are terminal; no further edits are allowed.
BR-06 Polling stops permanently once a terminal risk outcome is received.
BR-07 A rule set version once stamped on an application is never overwritten, even if the CMS content changes mid-flow.
BR-08 Documents are retained for 7 years from policy issuance or 90 days from rejection, whichever applies.

Why Feign for some integrations and not others

Feign is a declarative HTTP client and is a natural fit for the JSON REST APIs — Drupal CMS, Protean, Farmer Card and the Risk Assessment service. Azure Blob is deliberately not accessed through Feign: blob upload/download needs streaming, chunked transfer, SAS signing and retry semantics that the Azure SDK already implements correctly. For Twilio, either the official twilio-java SDK or a Feign client against the Twilio REST API is acceptable; this design uses a Feign client to keep all outbound HTTP under one interceptor/observability regime, with Basic auth built from the Account SID and Auth Token.

B2. Logical Architecture

The system is delivered as a modular monolith — one deployable Spring Boot service with strictly separated packages — because the workflow is transactionally cohesive and the volume does not justify distributed complexity in v1.0. Module boundaries are enforced with ArchUnit so that a later split into microservices (notification, document, integration-gateway) is a refactor and not a rewrite.

Deployment view

  • Two or more stateless pods behind an ingress; sticky sessions not required (JWT).
  • PostgreSQL with read replica for the supervisor queue and reporting.
  • ShedLock table in the same database guarantees single-node scheduler execution.
  • Azure Blob with private endpoints; the application authenticates with a Managed Identity in production and a connection string only in local development.
  • All secrets (Twilio auth token, Protean API key, CMS token, risk client secret) held in Azure Key Vault and injected as environment variables.

B3.2 Idempotency

Every outbound call that has a side effect or a per-call cost carries an idempotency key:

  • KYC: SHA-256(applicationId + verificationType + attemptNumber)
  • Risk submit: applicationNumber itself — the risk service must treat a repeat submit as a lookup and return the existing riskRefId.
  • Twilio: a client-generated notificationId stored before the call; if the process dies mid-call, the reconciliation job queries Twilio by that reference before re-sending.

@Service

public class EligibilityService {

    private final CmsFeignClient cmsClient;
    private final EligibilityRuleCacheRepository cacheRepo;

    @Cacheable(cacheNames = "eligibilityRules", key = "#product + ':' + #locale")

    public EligibilityRuleSet getRules(String product, String locale) {
        CmsEligibilityResponse res = cmsClient.fetchEligibilityRules(product, locale);
        cacheRepo.upsert(product, locale, res.version(), res.contentJson());

        return cacheRepo.findLatestActive(product, locale)

            .orElseThrow(() -> new CmsUnavailableException(product, t));
    }
}

B6.2 Document upload to Azure Blob

@Component
@RequiredArgsConstructor
public class BlobStorageAdapter {

    private final BlobServiceClient blobServiceClient;

    @Value("${azure.storage.container.kyc}")   private String kycContainer;
    @Value("${azure.storage.sas-ttl-minutes}") private int sasTtlMinutes;

    public BlobRef upload(String applicationNumber, DocumentType type, MultipartFile file) {
        String path = "%s/%s/%s/%s%s".formatted(
                YearMonth.now(), applicationNumber, type,
                UUID.randomUUID(), FilenameUtils.getExtensionWithDot(file));

        BlobClient blob = blobServiceClient
                .getBlobContainerClient(kycContainer)
                .getBlobClient(path);

        try (InputStream in = file.getInputStream()) {
            blob.upload(BinaryData.fromStream(in, file.getSize()), false);
            blob.setHttpHeaders(new BlobHttpHeaders()
                    .setContentType(file.getContentType()));
        } catch (IOException e) {
            throw new DocumentUploadException(path, e);
        }
        return new BlobRef(kycContainer, path, DigestUtils.sha256Hex(file.getBytes()));
    }

    public String generateReadSasUrl(String container, String path) {
        BlobClient blob = blobServiceClient.getBlobContainerClient(container).getBlobClient(path);
        BlobServiceSasSignatureValues values = new BlobServiceSasSignatureValues(
                OffsetDateTime.now().plusMinutes(sasTtlMinutes),
                new BlobSasPermission().setReadPermission(true));
        return blob.getBlobUrl() + "?" + blob.generateSas(values);
    }
}

Notes:

  • Upload happens before the database row is committed to the point of no return; the kyc_document row is written in the same transaction as the metadata, and an orphan-blob reaper job removes blobs with no matching row after 24 hours.
  • Antivirus scanning is delegated to Microsoft Defender for Storage; the active flag is only set once the scan callback reports clean, when that integration is enabled.

B6.3 Parallel KYC orchestration

@Service
@RequiredArgsConstructor
public class KycVerificationService {

    private final ProteanKycFeignClient protean;
    private final FarmerCardFeignClient farmerCard;
    private final VerificationResultRepository resultRepo;

    /** Runs the three checks concurrently; never throws for a single provider failure. */
    public KycOutcome verifyAll(InsuranceApplication app) {

        var aadhaar    = supplyAsync(() -> verifyAadhaar(app),   kycExecutor);
        var pan        = supplyAsync(() -> verifyPan(app),       kycExecutor);
        var farmerCard = supplyAsync(() -> verifyFarmerCard(app),kycExecutor);

        CompletableFuture.allOf(aadhaar, pan, farmerCard)
                         .orTimeout(20, SECONDS)
                         .exceptionally(t -> null)      // partial results are acceptable
                         .join();

        app.setAadhaarVerificationStatus(resolve(aadhaar));
        app.setPanVerificationStatus(resolve(pan));
        app.setFarmerCardVerificationStatus(resolve(farmerCard));
        app.setKycCompletedAt(OffsetDateTime.now());

        return new KycOutcome(app.getAadhaarVerificationStatus(),
                              app.getPanVerificationStatus(),
                              app.getFarmerCardVerificationStatus());
    }

    private VerificationStatus resolve(CompletableFuture<VerificationStatus> f) {
        return f.isCompletedExceptionally() || !f.isDone()
             ? VerificationStatus.MANUAL_REVIEW
             : f.join();
    }
}

A dedicated bounded ThreadPoolTaskExecutor (kycExecutor, core 10 / max 30 / queue 200) isolates KYC fan-out from the servlet pool. On Java 21 this can be replaced by virtual threads with no code change to the orchestration.

B6.6 The 24-hour risk polling scheduler

Two jobs, both cluster-safe via ShedLock:

@Component
@RequiredArgsConstructor
@Slf4j
public class RiskAssessmentScheduler {

    private final InsuranceApplicationRepository repo;
    private final RiskAssessmentService riskService;

    /** Retries hand-offs that never reached the risk team. Every 30 minutes. */
    @Scheduled(cron = "${scheduler.risk-submit.cron:0 */30 * * * *}")
    @SchedulerLock(name = "riskSubmitJob", lockAtMostFor = "PT25M", lockAtLeastFor = "PT1M")
    public void submitPendingApplications() {
        repo.findByStatusAndRiskRefIdIsNull(APPROVED_SENDFORRISK, PageRequest.of(0, 100))
            .forEach(app -> safely(() -> riskService.submit(app.getId()), app));
    }

    /** Polls risk outcomes. Runs daily; each application is polled at most every 24h. */
    @Scheduled(cron = "${scheduler.risk-poll.cron:0 0 2 * * *}")
    @SchedulerLock(name = "riskPollJob", lockAtMostFor = "PT2H", lockAtLeastFor = "PT5M")
    public void pollRiskDecisions() {
        List<InsuranceApplication> due =
            repo.findDueForPolling(List.of(RISK_IN_PROGRESS), OffsetDateTime.now(), 500);

        log.info("Risk polling cycle started, candidates={}", due.size());
        for (InsuranceApplication app : due) {
            safely(() -> riskService.pollAndApply(app.getId()), app);
        }
    }
}
@Service
@RequiredArgsConstructor
public class RiskAssessmentService {

    private final RiskAssessmentFeignClient riskClient;
    private final InsuranceApplicationRepository repo;
    private final BlobStorageAdapter blob;
    private final NotificationService notifications;

    @Value("${risk.poll-interval-hours:24}") private int pollIntervalHours;
    @Value("${risk.max-poll-attempts:30}")   private int maxAttempts;

    @Transactional
    public void submit(Long applicationId) {
        InsuranceApplication app = repo.findByIdForUpdate(applicationId).orElseThrow();
        if (app.getRiskRefId() != null) return;                 // already submitted

        RiskSubmitResponse res = riskClient.submit(
                RiskPayloadAssembler.assemble(app),
                app.getApplicationNumber());                    // idempotency key header

        app.setRiskRefId(res.riskRefId());
        app.setRiskSubmittedAt(OffsetDateTime.now());
        app.setNextPollAt(OffsetDateTime.now().plusHours(pollIntervalHours));
        app.transitionTo(RISK_IN_PROGRESS, null, "Submitted to risk: " + res.riskRefId());
    }

    @Transactional
    public void pollAndApply(Long applicationId) {
        InsuranceApplication app = repo.findByIdForUpdate(applicationId).orElseThrow();

        RiskStatusResponse res = riskClient.getStatus(app.getRiskRefId());
        app.setRiskLastPolledAt(OffsetDateTime.now());
        app.setRiskPollAttempts(app.getRiskPollAttempts() + 1);

        switch (res.status()) {
            case APPROVED -> {
                String blobPath = blob.copyFromExternalUrl(
                        res.policyDocumentUrl(), app.getApplicationNumber());
                app.setPolicyNumber(res.policyNumber());
                app.setPolicyDocumentUrl(res.policyDocumentUrl());
                app.setPolicyBlobPath(blobPath);
                app.setPolicyIssuedAt(OffsetDateTime.now());
                app.setNextPollAt(null);
                app.transitionTo(POLICY_ISSUED, null, "Policy " + res.policyNumber());
                notifications.notifyPolicyIssued(app);
            }
            case REJECTED -> {
                app.setRejectionReason(res.reason());
                app.setNextPollAt(null);
                app.transitionTo(POLICY_REJECTED, null, res.reason());
                notifications.notifyPolicyRejected(app);
            }
            default -> {   // IN_PROGRESS / PENDING
                app.setNextPollAt(OffsetDateTime.now().plusHours(pollIntervalHours));
                if (app.getRiskPollAttempts() >= maxAttempts) {
                    notifications.raiseSlaBreach(app);   // ops alert, status unchanged
                }
            }
        }
    }
}

  3. Aadhaar VERIFIED, PAN VERIFIED, farmer card timeout → application still reaches REVIEW with farmer card MANUAL_REVIEW.
  4. Supervisor requests more info twice; both comment threads visible, history shows REVIEW → NEEDS_MORE_INFO → REVIEW → NEEDS_MORE_INFO → REVIEW.
  5. Approval succeeds but risk submit returns 503 → status stays APPROVED_SENDFORRISK, submitter job succeeds 30 minutes later, riskRefId stored once (no duplicate submission).
  6. Risk returns IN_PROGRESS for four consecutive days then APPROVED → exactly four poll rows, next_poll_at cleared, policy copied to blob, employee notified.
  7. Two scheduler pods start simultaneously → ShedLock ensures a single execution; no duplicate Twilio message or duplicate risk submission.

APPENDIX B — Glossary

Term Meaning
Maker–checker Control pattern where the person who captures a record cannot be the person who approves it
SAS URL Shared Access Signature — a time-boxed, permission-scoped URL to an Azure blob
ShedLock Library that ensures a scheduled task runs on only one node in a cluster
Idempotency key Client-generated token that lets a server recognise and de-duplicate a repeated request
Protean Provider of Aadhaar and PAN verification services (formerly NSDL e-Governance)
Rule set version Immutable identifier of the eligibility content shown to a specific customer on a specific date
TAT Turnaround time — here, the time the risk team takes to return a decision
Circuit breaker Resilience pattern that stops calling a failing dependency for a cooling-off period
